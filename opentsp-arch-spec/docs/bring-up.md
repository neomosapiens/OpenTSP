# Bring-up (informative)

Status: informative; nothing in this document is a conformance requirement of specification 0.1. It lists what a person bringing up a chip, an FPGA or an RTL simulation needs, maps each need to what 0.1 defines and to the model and ISS observers that serve as the reference, and says what 0.1 does not provide. The conformance rule itself is [`platform.md` §7.1](platform.md#71-rtl-conformance).

## 1. What bring-up needs and where 0.1 provides it

| Need | What 0.1 defines | Reference in the model and the ISS |
|---|---|---|
| Know which chip, which interface and which profile | `CHIP_ID` (chip CSR 0x000); `ID`, `SPEC_VERSION`, `PROFILE_DIGEST`, chip functions with implementation-defined registers ([platform.md](platform.md) §6, §9.1) | `config_sha256` of the golden vectors (`microarchitecture.md` §12) |
| Put a program and data in and read results out | The IQ load window and the SRAM aperture (`platform.md` §2, §3), a cold reset that clears the SRAM (§1.1) | The `Q`, `S` and `D` lines of the harness; `W` lines in the output |
| Start, bound and stop a run | `CTRL.start`, `CTRL.stop`, quiescence, the host entry point `H start <cycle>` | `--max-cycles`; the exit codes of `tsp_sim` and `tsp-iss` |
| Find the first thing that went wrong | The error FIFO and `ERR_FIRST` (`platform.md` §7), the chip's diagnostic log `DIAG_COUNT`, `DIAG[i]` (the FIFO's mirror in the CSR space, `microarchitecture.md` §16.3), the chip's `ERR_STATUS`, `LOG`, `FIRST_ERR0/1` and the error interrupt (`microarchitecture.md` §16) | `E` line, `T diag` lines, `R` lines of the CSRs; `--on-irq stop` is a model construct, a chip does not stop |
| See what the machine did, cycle by cycle | Nothing on the chip: there is no trace port in 0.1 | `--trace` (stream and SRAM writes) and `--observe` (one `O` site record per dispatch and per visited wait cycle, with the queue, cycle and reason): the reference a capture from an implementation's own trace port is compared against |
| Compare the machine state after a run | The words of the SRAM through the aperture, the CSRs through the base address register | `sram_digest` and `state_digest` of the ISS binding: observers of the ISS, not chip registers (`platform.md` §1.3); for hardware, read the SRAM words and compare them with the `W` lines of the model |
| Exercise the memory protection | Single-bit correction, multi-bit detection, patrol scrub, `SBE_COUNT` and `MBE_COUNT` (`microarchitecture.md` §15, §16) | `F sram`, `F srf`, `F iq` lines; the software scrub sequence of §15; the fault points of [`platform.md` §5.1](platform.md#51-fault-points) |
| Exercise the links | `LINK_CORR[l]`, `LINK_UNCORR[l]`, `Transmit` and `Receive`, Deskew (`microarchitecture.md` §10, §17) | `--chips K`, `F link` lines. Chip-to-chip start alignment and drift are outside 0.1 hardware conformance (`platform.md` §1) |
| Run the conformance programs | The golden vectors of the declared profile (`microarchitecture.md` §12) | `tools/gen_model_vectors.py <tsp_sim> <config.json> <out.json>` for a profile that is not shipped |

## 2. A suggested order

1. Read `CHIP_ID`, `SPEC_VERSION` and `PROFILE_DIGEST`; refuse a profile that is not the one the vectors were generated for.
2. Cold reset; read back a pattern of SRAM words from every slice through the aperture and check that the memory is zero after reset and holds what was written after a write.
3. Pick the vectors by their obligation (the table below) and load the smallest `pass` vectors (one instruction class each). Run them and compare the five outputs of [`platform.md` §7.1](platform.md#71-rtl-conformance): the records that the log filter admits, the SRAM words at quiescence, the egress vectors, the `HostNotify` interrupts and the CSR values, the host inputs applied at the real cycle the vector names and the reads mapped by D (+ S) of `platform.md` §5.
4. Run the larger `pass` vectors; for any mismatch, run the same input on the model with `--trace --observe` and locate the first differing dispatch or write. A `none` vector is skipped. A mismatch on an `undecided` vector is not a failure: run the object with data that raise no data code (a witness) through `tsp-iss verify`; if that run is well-formed the object binds the RTL and the mismatch is a defect, and if it is not, the object has no obligation.
5. Inject faults with the test mode of the implementation and compare the error registers with the `T ecc` lines and the CSR reads of the fault vectors.

### The obligation of each vector

`opentsp-arch-spec/conformance/rtl/<profile>.json` lists for every vector of `conformance/model/<profile>.json` (or, for the combined-extension dump `all_ext`, of `conformance/model-extra/all_ext.json`) whether it binds an RTL (the frozen vector files carry no such field). It is generated by `tools/gen_rtl_obligations.py` from the verdict of `tsp-iss verify` on the vector's own program, data and host script, and `just iss-vectors` fails when it is stale. `pass`: the run is well-formed, the five comparisons of `platform.md` §7.1 bind the RTL. `none`: ill-formed (the run raises a `schedule` code that no `data` code precedes), a run with injected faults, or an `F mxm` vector. `undecided`: data-dependent, or the text uses a link (`verify` judges a manifest, not a lone object). Generate the current per-profile obligation summary with tools/gen_rtl_obligations.py:

| Profile | `pass` | `none` | `undecided` | Vectors |
|---|---|---|---|---|
| `ref` | 396 | 517 | 74 | 987 |
| `mini` | 394 | 512 | 68 | 974 |
| `all_ext` | 6 | 8 | 3 | 17 |

The cascade vectors with an SXM-001 first and a TIM-001 after it (`directed-239` and `directed-262` of `ref`, `directed-256` and `directed-313` of `mini`) are `undecided`, and their entry in the sidecar carries a `witness`: the same program with the identity map in the two slices that hold the map (`4:1` low bytes, `5:1` high bytes), which `tools/gen_rtl_obligations.py` runs through `tsp-iss verify` and finds well-formed. So the object is well-formed, the TIM-001 of the vector is the cascade of its SXM-001, and the vector binds an RTL as a cascade test of §7.1: the suppressions and partial effects must match, and the TIM-001 record may be absent. The other cascade vectors (generated ones, where an IQ-002 or DEC-003 comes first and a QUE-001, OPR-001 or TIM-001 follows: 10 on `ref`, 5 on `mini`) have no witness: they stay a question as above.

## 3. Coverage plan

Which vector family exercises which class of behaviour, for the `ref` profile (grouped by vector name and observable fields). What an RTL compares in each family is stated by the table of [`platform.md` §7.1](platform.md#71-rtl-conformance).

| Family (vectors on `ref`) | What it exercises | Host and fault fields it carries |
|---|---|---|
| `directed` (356) | one scenario per rule: the `schedule` and `data` codes, SXM-001 and its cascade (`directed-239`, `directed-262` of `ref`: SXM-001, then TIM-001) | none, one with an ECC finding |
| `generated` (312) | random programs of the oracle generator: the schedule codes in mixes, IQ-002 and IQ-004 | three with `dma` and `Y` events (a `PciSend` egress) |
| `coverage` (100) | one minimal program per catalogue entry | two with an `irq` event |
| `clean` (10) | an entry that issues without a diagnostic, where its coverage program reports one | none |
| `link` (3) | link overrun and the link codes | none |
| `host` (36) | the host path: DMA in and out, doorbells, CSR reads and writes, interrupts, remote CSR packets | `H`, `R` and `P` lines; `dma`, `Y`, `irq`, `X`, `csr` and `pkt` events |
| `ecc` (168) | SECDED on SRAM, streams and text; the link FEC; the matrix sum check | `F` lines, counted as lines and as vectors (130 vectors carry one): `F sram` 74, 42; `F srf` 5, 4; `F iq` 7, 5; `F link` 39, 33; `F mxm` 69, 46; `ecc`, `irq`, `X` events |

The classes and where the vectors stand:
- **Codes of class `data`** (SXM-001, DEC-003, IQ-002, IQ-004, and the OPR-001 and TIM-001 that the filter of `microarchitecture.md` §16.3 admits): SXM-001 is in the `directed` family only, IQ-004 in `generated` only, DEC-003 in `generated`, `coverage`, `directed` and `host`.
- **IQ-002** (an IQ that overflows) is in a `generated` vector of `ref` and in no vector of the main `mini` file; the side file `conformance/model-extra/mini.json` holds one vector `iq002-000`. **IQ-003** (a fetch that cannot stage its payload) is in no vector of the main files: it is in the side file of `mini` (`iq003-000`), of `ref`, `ref_hw` and `ref_patrol` (`iq003-000`, and `iq003-001` on `ref`, `ref_hw` and `ref_patrol`). The side files are the only vectors of these two codes; a `mini` RTL has them in `conformance/model-extra/mini.json`.
- **Codes of class `fault`** (ECC-001, ECC-002, ECC-003, LNK-004): the `ecc` family, compared only through a test-mode mapping of the `F` lines (`platform.md` §5.1); the 46 vectors with `F mxm` lines (69 lines) are for the model and the ISS only.
- **Host outputs** (`Y`, `HostNotify`, CSR reads): the `host` family and three `generated` vectors; 5 vectors carry egress (`Y`), 94 carry `X` lines.
- **Not covered by a vector:** a host input under the delay D (the `H` lines name model cycles, so a co-simulation applies the mapping of `platform.md` §5 itself), and an IQ-004 record read through the CSR space during the run (it exists only from quiescence on).

## 4. Tap-to-trace map for co-simulation

Idle-cycle skipping can omit optional wait samples. Compare architectural effects and their required order separately from the optional `O` records.

A simulation of an RTL with a trace port is compared with the model by the lines of `microarchitecture.md` §12. The map says where the RTL is tapped for each line, and which time it is read in; a superlane k and the implementation constant K make a tap lag the model by k + K cycles (`platform.md` §5), which the checker removes before it compares.

| Model line | Tap in the RTL | Cycle to report |
|---|---|---|
| `T srf <cycle> <row>:<stream> gap <gap> <value>` | the write port of a stream register: the merged value committed at the writer's gap | superlane-0 cycle: the tap's cycle minus (k + K); compare after sorting each cycle's run in the canonical order |
| `T sram <cycle> slice <slice> addr <addr> <value>` | the write port of a slice: the whole stored word after a masked Write, one line per Scatter tile | as above |
| `O` records (`--observe`): one per dispatch and per visited wait cycle, with queue, cycle and reason | the issue stage of each queue: a parcel leaves the IQ head, or a held queue waits | the dispatch cycle of superlane 0 |
| `T diag <cycle> queue <queue> <code>` | the report strobe of the unit that detects the rule; the end of the run for IQ-004 | the stamp of the model (the end-of-run records follow every run-time record) |
| `T ecc...` (SRAM, stream, text, link, matrix) | the corrected or uncorrectable output of the decoder at the reader, with the codeword position | the reader's cycle; the link finding at the vector's arrival cycle |
| `T dma <cycle> in`, `wait`, `out` and `Y` | the ingress FIFO entry, the DMA engine's wait, the egress to the host | the model cycle; compare with the delay D of `platform.md` §5 |
| `T irq <cycle> msix <n>` | the MSI-X delivery to the host | the cycle of the model plus D (D + S for the interrupt of a sum-check verdict) |
| `T csr`, `X` | the read data of the base address register | a read issued D cycles after the cycle the line names (D + S for a register that a sum-check verdict changes, and for the `X` lines after quiescence); a write line is applied at the cycle it names |
| `T pkt <cycle> csr` or `ctrl` | the link receive path of the control unit | the arrival cycle |

The digest `expect.trace_sha256` covers `T srf` and `T sram` only; the other lines are compared as lists (`expect.diagnostics`, `expect.ext_events`).

## 5. What 0.1 does not have

- **No performance counters, by design.** The CSR space has error and link counters only. There is no counter of dispatches, holds, stalls, bytes fetched or busy cycles, and the schedule-slip lint `OTS-W-IQ-001` is a simulator lint that an implementation need not report. A program with data-dependent holds cannot be profiled on silicon from the specification alone; the ISS reports dispatches, waits and fetched bytes in its statistics for software runs.
- **No debug port.** There is no breakpoint, stop-at-cycle, scan of internal state, checkpoint or resume protocol. A stopped machine is started again only after a reset (`platform.md` §1); investigating an earlier state needs a new run with the same inputs.
- **No architected trace.** The `T` and `O` lines are the output of the model and the ISS; an RTL that wants them provides its own trace port.
