# TSP encoding map (generated, spec version 0.1)

Generated by `opentsp-arch-spec/tools/gen_isa_doc.py` from the isa-db catalogue. Do not edit by hand. Normative source: the `encdec32/encdec64` mappings in the Sail model.

## Word formats

- A queue's text is a sequence of 32-bit units (`text_format`). An instruction is one unit (32-bit layout) or two units (64-bit layout, the high half first); there are no 128-bit instructions. AGT iteration replaced the fused compound instructions.
- Unit bit 31 is the **bundle bit** (1: the next instruction of the queue belongs to the same parcel and dispatches with this one) and is not part of the instruction; bits 30..28 are the slice tag, so the tag of every layout is 3 bits and bit 31 / bit 63 of every instruction word is 0.
- **32-bit layouts** (CU, MXM, C2C) occupy one unit: the slice tag is bits 30..28 (tags 0, 3, 5).
- **64-bit layouts** (MEM, VXM, SXM) occupy two units, the first unit holding bits 63..32: the slice tag is bits 62..60 (tags 1, 2, 4) and the opcode is 59..54. Every 64-bit layout has a fixed zero bit in 31..0, so that its second unit is never the padding unit 0xFFFFFFFF.
- **Control channel** (queue 0xFFFF): its text decodes with the same rule as a data queue's. A decoded instruction other than NOP, Sync, Notify and Config (Repeat, Ifetch, IfetchM, SetVL, every MXM and C2C instruction) is OTS-E-QUE-002.
- Decode rule (`decode_rule` in encoding.json): clear the bundle bit; the tag in bits 30..28 of the first unit selects the layout (0, 3, 5: one unit; 1, 2, 4: two units, the second unit following in the queue's text); tags 6 and 7 are OTS-E-DEC-003 and consume one unit; a word that matches no entry with legal fields is OTS-E-DEC-003. The queue does not change the decode; placement (QUE-002) is checked after it.
- Stream fields are 6 bits: bit 5 is the row (E = 0, W = 1), bits 4..0 the stream id. A `stream_group16` field is 2 bits: (32 × row + id) / 16, so E:0 = 0, E:16 = 1, W:0 = 2, W:16 = 3 (`stream_encoding`).
- Boolean element types (b8, b16, b32: codes 8, 9, 10) restrict a field with `bool_values` to those values (Cmp: eq and ne). `max_expr` uses the profile variables (`profile_variables`) `vlanes` = 16 × `geometry.superlanes`, `sram_words` = 2^`sram.addr_bits` and `acc_depth` = `mxm.acc_depth` (a factor of an expression is an integer, a configuration key, or an integer raised to a key).
- Every bit not listed as a field is reserved and must be zero (a word with a reserved bit set does not decode: OTS-E-DEC-003).
- VXM element type: a 5-bit code = type extension (bit 17) @ extension (bits 23..22) @ type (bits 53..52): i8=0, f16=1, i32=2, f32=3, u8=4, i16=5, u16=6, u32=7, b8=8, b16=9, b32=10, e4m3=11, e5m2=12, bf16=16. Unassigned codes 13..15 and 17..31 are reserved. The codes of a profile extension (bf16, wide_acc, block_fp8) decode only in a profile whose `extensions` list names it (`extension_codes` in encoding.json): in another profile the word does not decode (OTS-E-DEC-003). The destination type of a Convert is the same code, its bit 4 at bit 16. The MXM weight type is a 3-bit value = bit 12 @ bits 21..20 (bf16 = 4, with the same rule).
- Encoding distinctness is checked pairwise: no two entries can match the same word (`check_isa_db.py` (f)). The argument that this, with the per-field checks, makes the 64-bit encoding a round trip, and what no check covers, is in `validation.md`, section "Encoding round trip".
- `encoding.json` is self-sufficient: besides the entries it carries `decode_rule`, `field_rule`, `stream_encoding`, `boolean_codes`, `profile_variables`, `control_channel`, `units` (unit → queue ids), `queues` (names) and `diagnostics`. `test/isa_db/json_decoder.py` builds a text decoder from the JSON alone and compares it with the model on random words.

## Relation to the published format

The published TSP sources describe the instruction stream at the level of the VLIW word: instructions are bundled, and a NOP carries a delay. No bit layout is published.

This specification defines the layout itself (an opentsp decision, `isa-db/provenance.yaml` `encoding.all`):

- The unit of a queue's text is a 32-bit unit, a parcel is the instructions that dispatch together (the bundle bit), and a NOP is a timing prefix of the next parcel. This is the published VLIW word in its simplest form: bundling and the NOP that carries a delay are part of the architecture (`microarchitecture.md` sec. 3a). Narrower NOP encodings and instruction compression are transport details below the text level: they change how text reaches the ICUs, not what a queue issues, so the specification leaves them to the implementation. What the published compression sources address: instruction compression (packing, replication over cycles and columns, encryption, an instruction decompression unit; the problems are code-space storage, instruction-transfer bandwidth and instruction-cache area), a compressed VLIW sent over PCIe for host-link bandwidth and decompressed at the ICU fetch, with `Repeat` for density, and clock gating of NOP cycles for power (ISCA20 sec. III-A1). The data-compression families of the published sources (coefficients, images) address model data, not the instruction stream, and are unrelated to this encoding.
- Every instruction is a 32-bit or 64-bit word with a 3-bit slice tag (bits 30..28 or 62..60; bit 31 is the bundle bit and bit 63 is zero, neither is part of the tag) and a 6-bit opcode, so that a word can be decoded without its queue (except on the control channel) and every operand field has a fixed, range-checked position.
- The VXM encoding space is half sourced, half the specification's own: the SG4 forms follow ISCA20 sec. III-C, while the non-SG4 forms of Bin, Un, Mask, Select and Cmp, and the opcode map, are the specification's own forms; the published sources do not describe them (`provenance.yaml` `VXM`).
- MEM, VXM and SXM words are 64 bits. This is a **decision, not a necessity** for most of them: with the 10 bits of tag and opcode, 33 of the 54 64-bit entries need at most 22 operand bits and would fit a 32-bit word; only Read (23 bits), Write (23 bits), Add (26 bits), Add_sat (26 bits), Add_mod (26 bits), Sub (26 bits), Sub_sat (26 bits), Sub_mod (26 bits), Mul (26 bits), Mul_sat (26 bits), Mul_mod (26 bits), Max (26 bits), Min (26 bits), And (26 bits), Or (26 bits), Xor (26 bits), Mask (26 bits), Select (33 bits), Cmp (30 bits), Convert (23 bits), SelectS (30 bits) need more. The reasons for the choice are (1) one word width per slice, so the slice tag alone gives the layout and the decode rule needs no per-opcode width table; (2) fixed shared field positions within a slice (the MEM SRAM address in bits 44..32 and thread bit 53, the VXM element type in bits 53..52 and 23..22); and (3) reserved zero bits for later extension without changing the opcode map: every 64-bit entry has at least 21 reserved bits. CU, MXM and C2C operands fit 32 bits.
