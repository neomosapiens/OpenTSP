# TSP reference architecture: microarchitecture

Sail defines the cycle transitions and instruction effects below. The C harness provides external SRAM, links, host actions, fault injection and trace output. Read those interfaces together when implementing reset, replay or completion. The selected profile supplies dimensions, timing and capacities. Cycle numbers refer to superlane 0. ## 1. Execution model

The TSP has no branch and no speculation: each queue's instruction queue (IQ) holds the text the compiler placed, and the queue dispatches it in order, one parcel per cycle, with NOP prefixes specifying the earliest issue time and runtime holds able to delay dispatch (ISCA20 §III-A1, §III-A3; HC34 p.23, p.27). The model runs one function per cycle, `tick(c)` (`postlude/tick.sail`), in this order:

Before these phases, the C driver runs patrol through c−1 and processes the external events of c in the order given in the final section. The Sail tick then completes the second SRAM read of each local fetch due at c, in queue order. A completed payload becomes eligible for IQ delivery at c + fetch_latency (§3).

1. **Enqueue and barrier retirement:** the text that Ifetch and IfetchM delivered to each queue's IQ by cycle c is enqueued, queues in ascending order, the control channel last (§3, "Instruction front end"; an overflow loses the units and raises OTS-E-IQ-002). Then the Syncs whose release cycle has been reached stop parking their queues (§3).
2. **Commit:** results scheduled for cycle c enter the stream register file. A write at gap g in cycle c is visible at gap g+1 from cycle c+1 (`core/streams.sail`). Collisions are resolved here (§2).
3. **Execute:** complete the second stream-fetch samples due now in ascending queue order, before new execution. Then the elements whose execute cycle is c (dispatched at c − d_skew, below) execute, in dispatch order (`execute_due` in `postlude/tick.sail`). An element with d_skew = 0 executes in its dispatch step instead (step 5).
4. **Control channel:** its head parcel, if it is complete, due and not held, is decoded and dispatched (§3). Because this step comes before step 5, a control-channel Sync dispatched at c parks every data queue **from cycle c itself**: a data-queue parcel due at c waits. A data-queue Sync at c parks its own queue from **c + 1** (its own dispatch is step 5 of cycle c). Either way the window ends at N + 35, exclusive, for the first Notify N at or after the Sync (§3).
5. **Queues 0..143, in order.** For each queue:
   - (a) a pending **Repeat** iteration issues (not while the queue is parked);
   - (b) the queue's head parcel is decided: it dispatches this cycle if it is complete, due and not held (§3); otherwise it waits;
   - (c) the queue's AGT configurations end if this cycle dispatches no configuration instruction (§4);
   - (d) the AGT references due this cycle and the head parcel's instructions dispatch, in the exact order of §8, "Order within a queue's cycle" (§3, "Instruction front end").
6. **Unit-state flush:** the MXM plane and SXM map changes staged during the cycle are applied (below).

**Parallel issue and arbitration.** A circuit may service queues concurrently when their effects are independent. Shared consumptive resources retain the service order of phases 3–5. For example, if queues 128 and 129 both execute PciReceive in phase 5 with one DMA vector available, queue 128 pops it and queue 129 reports TIM-001 without writing a result. The same test with two vectors delivers the FIFO head to 128 and the next entry to 129. Preserve the specified order of diagnostics even when the datapaths run concurrently. The following resources have their own visibility rules:
- a read in cycle t sees only commits from cycles before t (step 2);
- the barrier depends only on dispatch cycles, and a Notify releases a Sync dispatched in the same cycle on any queue (§3);
- a queue's front end looks only at that queue's IQ, its last dispatch cycle and the state of its own paths, the barrier and the Repeat (§3), never at another queue's IQ;
- MXM and SXM instructions read their unit's internal state **as it was at the start of the cycle**. Their changes are staged and applied in step 6. If two queues stage a change to the same part of one MXM plane (the weight buffer, the installed weights, the ABC results, or one accumulator: each of the `mxm.acc_depth` accumulators is a part of its own; with `mxm.fp8_rate` 2 a plane accepts two FP8 ABCs in one cycle, §6) or to the same SXM map in one cycle, each of them raises **OTS-E-RES-003**, none of their changes takes effect, and the stream writes of an ACC among them are withdrawn (`slices/mxm/mxm_regs.sail`, `unit_state_flush` in `postlude/tick.sail`). A staged SXM map carries its bijective flag and its ready cycle (§7), which are applied with it.

**Timing parameters** (ISCA20 §III, Eq. 4): reference k of an instruction dispatched at t (k = the reference's issue cycle − t: 0 except for AGT references, §4, where a countdown makes it larger than the reference's index) **executes at t + k + d_skew** and commits its **stream results** at **t + k + d_func**. In its execute cycle it reads its stream operands, the SRAM and its unit's state, and reports its diagnostics; the dispatch checks (unit, slot rule, banks, IQ underflow) and the decision whether the parcel waits stay in the dispatch cycle t. ISCA20 defines d_skew as "the timing relationship between the instruction dispatch time relative to when its stream operands are required": it counts from dispatch to a later operand arrival, and the model follows it (the VXM, d_skew = 2, reads its operands two cycles after its dispatch cycle). An element with d_skew > 0 waits in a 16-slot execute ring (`execute_ring` in `postlude/tick.sail`) and executes in step 3 of its execute cycle; MXM readiness (a weight buffer ready for IW, installed weights ready for ABC, an ABC result ready for ACC) is stated in dispatch cycles: a stage is ready from its producer's dispatch + d_func.

**The timing table.** ISCA20 gives every instruction its own d_func and d_skew. The model's table has one row per catalogue entry (`entry_of` in the instruction slices; `entry_latency` in `core/timing.sail`): the entry's row in `timing.overrides` of the configuration, else the row of its timing class (`timing.cu`, `timing.mem`, `timing.vxm`, `timing.mxm_lw`, `timing.mxm_iw`, `timing.mxm_abc`, `timing.mxm_acc`, `timing.sxm`, `timing.sxm_cross`, `timing.c2c`). The shipped profiles override six entries (the table below); every other entry has its class's latency. The instruction words carry no timing field: ISCA20 publishes no such field (`provenance.yaml` `conflicts: timing.encoding`). An override is a row `{"entry": <catalogue name>, "d_func": 0..63, "d_skew": 0..15}` of the list `timing.overrides`, which every configuration has (six rows in the shipped profiles, none in the test profiles but `c2c_tx_delayed` and `ref_hw`; `config/schema.json`). **A row may be keyed by an element type**: its `entry` is `<catalogue name>.<type>`, the type spelled as the assembly spells it (`Max.i8`, `Add.e4m3`, `Exp.f16`; `core/types.sail` `eltype_name`). The row of an instruction of entry E and element type T is the row `E.T`, else the row `E`, else the class row, so a profile can time `max.i8` apart from `max.f32` and leave every other type at the entry's row (`entry_latency_typed` in `core/timing.sail`; `timing_type_of` in the instruction slices names the type of an instruction). The element type of an instruction is its `type` operand (the source type of `Convert` and of the `Conv_*` entries, which allow no other); an entry takes the types of the codes of that operand in the catalogue, and the entries that have none (every entry outside the VXM) take no typed row. The type is part of the key because a configuration row has no optional field (every key of a Sail `config` struct is required, and the reader rejects `null`); a profile with no typed row is unchanged, byte for byte. The key is the type's name, so a type that a later revision adds needs no change of the schema or of the table: it adds rows. The MXM entries (`LW`, `IW`, `IWS`, `ABC`, `ABC8`, `ACC`) are keyed by a weight or accumulator format, not by an element type, and have no typed row; `ABC8` is already an entry of its own. Every harness checks the effective table after loading the configuration (`timing_config_error` in `postlude/timing_check.sail`) and refuses, with exit status 2 and the offending key, a table where:
- an override names no catalogue entry and no `<entry>.<type>` (an element type of the encoding), or names one twice; or a typed row names a type its entry does not take (`Read.i8`, `Max.b8`, `Exp.i32`, `Conv_F16_I8.i8`);
- a typed row has d_skew ≥ d_func (it would commit before it executes), like any other row;
- an entry outside the control unit has d_skew ≥ d_func (it would commit before it executes);
- an effective Shift, Permute, ABC or ABC8 row has `d_func - d_skew < geometry.superlanes`, including overrides; or `sxm_map_ready < geometry.superlanes` (operands and map entries must arrive before they can be used);
- `timing.mxm_abc.occupancy_f16` exceeds ABC's d_func (§6);
- Read, Write, Gather, Scatter and IfetchM do not share one d_skew (the SRAM port and bank rule is checked at dispatch, so their accesses keep the dispatch spacing).

One case is not refused by the harnesses: a typed row of a type that only an extension defines (`Max.bf16`, with the extension `bf16` not declared) is read without a message, and no instruction of that profile has the type, so the row is never used. `tools/schema_invariants.py --check` refuses it (`model_check.sh` runs it on every shipped profile; `test/config/test_typed_row_extension.py`), so an author of a profile should run it.

The Python scheduler honours the typed rows: `Profile.timing` takes the operation with its type (`timing("max.i8")`, `timing("cmp.lt.f32")`, or `timing("max", "i8")`), using the assembly template's `{type}` field — the source type of `Convert` (`timing("convert.u8.f32")` is `Convert.u8`, as Sail `timing_type_of`), not the destination — and the `Builder` and `Flow` of the program generators (`opentsp_tools.programs`) time every VXM operation, its operands' reads and its result's commit with that type, so a program scheduled on `config/test/ref_hw` or `config/test/convert_src` runs without a timing diagnostic (`basic/vxm_typed`; the convert source-type case is `test_tsplib.py`). A bare mnemonic of an entry that the profile gives typed rows for is refused (`UntypedTiming`); `dtype=""` asks for the entry's own row on purpose. Every case generator of `tests/programs/gen` and the tinystories block generator name the type of each VXM operation: `TypedRowsEverywhere` (`tests/programs/gen/test_tsplib.py`) generates every checked-in case on a profile that gives typed rows to every (entry, type) pair the generators use, and fails at the first bare lookup; the cases generated on such a profile also run clean on `tsp_sim` and the ISS (54 cases, 258 runs; `mem/gather_partial`, which keys its address table on the profile name, fails there as it does on a plain copy of `ref`). Three cases are outside the test because their chained-add geometry (`kernels/context.py`) needs the reference VXM latency and fails on the plain profile `test/ref_slow` as well: `ship/ts_wide_context16`, `ship/ts_wide_context96`, `ship/ts_attention1x2`.

`test/isa_db/check_isa_db.py` checks that `entry_of` gives every catalogue word its catalogue name and that `timing_of` gives the catalogue's `timing` class. **Three latencies are keys of their own, not table rows** (each was a constant in the Sail, so no profile could reach it): `timing.sxm_map_ready` (cycles from a LoadMap's execute cycle to the first cycle a Permute may use the map, §7; ref 20, mini 1, the superlane count), `timing.mxm_abc.occupancy_f16` (cycles an f16 ABC holds its plane's MACCs, §6; 1 in shipped profiles, an engineering reconciliation of the published shape and quarter-rate throughput) and `timing.c2c.rtdeskew_floor` (the shortest hold of a RuntimeDeskew, §10; 1). The current defaults include the  FP16 rate correction; `config/schema.json` bounds them (1..63, 1..63 and at most ABC's d_func, 1..65535) and `test/directed/timing_rows.py` moves each and checks the trace.

**Granularity and status of the rows.** The table is **entry-granular by default and type-granular on request**: one (d_func, d_skew) pair per catalogue entry, whatever the element type, unless a `timing.overrides` row keyed `<entry>.<type>` (§1) gives one type its own. `Add` has one row for its 13 types; a profile in which `max.i8` is faster than `max.f32` says so with two typed rows (`config/test/ref_hw.json` does), and a profile that gives no typed row **declares the slowest type's latency for the entry**. **`ref` is a scheduling reference.** Its rows give programs a stable timing for the golden vectors; they are not a claim that an implementation can meet them: the `timing.overrides` rows of `ref` (override rows of the entries Exp, Log, RSqrt and TanH at 5 and 2, Permute at 20 and 0, Transpose at 5 and 0) are placeholders, and the class rows it keeps (the multiply, ABC and Shift rows and the map-ready time) are placeholders or causal bounds. `config/test/ref_hw.json` is a test profile whose overrides are slower (Exp and Log 16 and 2, RSqrt 18 and 2, Permute 24 and 0, Reduce 12 and 2, Transpose 5 and 0): an opentsp choice, not a published value; it keeps TanH, the multiply, ABC and Shift rows and the map-ready time on the placeholders and bounds of `ref`, so it is no implementability claim either (`platform.md` §7.1, "Profile"). Hardware declares a profile of its own and conforms to it (§12, "Conformance is per profile"; `platform.md` §7.1).

**MXM execution delay and rate.** `timing.mxm_abc.d_func` = 20 is a **published** value: HC34 p.28 gives a 20-cycle execution latency. It is not the stagger term N of ISCA20 Eq. 4, which is 20 for every slice (the tile count); the MXM's 20 is the partial sum crossing the plane's 20 supercells, a second 20 that has the same value because the geometry has 20 tiles per slice and 20 supercells per plane. `timing.mxm_acc.d_func` = 20 is an **implementation choice**: ACC adds one product to an accumulator and does not run a dot product, no source gives it a latency, and the published floor is 1 (ISCA20 §III, "each instruction requires 1 or more cycles"). It has its own row (`timing.mxm_acc`, whose only entry is ACC) and keeps the value 20 that it had as a copy of ABC's, because changing it has no evidence and would move every accumulating program;  therefore moves no cycle count through it.

Row word classifies the effective d_func/d_skew pair; Rule word classifies an additional scheduling rule. The current 78 rows comprise 1 published, 2 derived, and 75 implementation choices. The individual citations and rationales in `provenance.yaml` are the evidence; a classification count does not establish fidelity. The six shipped overrides give Transpose, Permute, Exp, Log, RSqrt and TanH independently configurable timing.

The model requires d_func < 64 and d_skew < 16, so the 128-slot commit ring, the 16-slot execute ring and the 64-slot SRF ring cannot alias. Every class that writes a stream (all but `cu`) also needs d_func ≥ 1: `tick` applies the commits due at cycle c before it dispatches the parcels of c, so a result scheduled for its own dispatch cycle would land in a slot already drained and commit 128 cycles late. `config/schema.json` enforces both bounds on the class rows; on a `timing.overrides` row the schema bounds the values and `timing_config_error` enforces d_func ≥ 1 through d_skew < d_func. The C2C latencies obey 1 ≤ `link_latency_min` ≤ `link_latency` ≤ `link_latency_max` < `hac_period` (§10).

**SRAM writes are not delayed by d_func**. A MEM **Write** or **Scatter** dispatched at t (AGT reference k: at t + k) reads its stream in its execute cycle t + d_skew (+ k) and updates SRAM **in that same cycle** (`sram_write(exec_cycle, …)` in `slices/mem/mem_insts.sail`; the trace line is `T sram t …` with the execute cycle; the shipped profiles have MEM d_skew = 0, so that is the dispatch cycle). d_func applies only to values the instruction puts on a stream: a Read or Gather dispatched at t reads SRAM in its execute cycle and commits its stream value at t + d_func. Consequences:
- a Read at t + 1 or later of the address a Write updated at t sees the new word (whatever d_func is);
- a Read and a Write of the same address in one cycle must be one Read + Write pair on that slice's queue, which is a same-bank pair: both are OTS-E-MEM-001 and neither runs (§4). No other queue reaches that slice's SRAM, so no same-cycle read-after-write order arises.

Source: ISCA20 §III-B says only that the SRAMs are "capable of servicing a pair of read and write requests simultaneously assuming they are not targeting the same bank". The published sources do not give the cycle in which a write reaches the SRAM array. The execute-cycle update is an opentsp **decision**: it is the earliest cycle the written value exists in the slice (the stream is read in that cycle) and it makes the order of a Write and a later Read on the same slice independent of d_func.

## 2. Stream register file (`core/streams.sail`)

- Per (row, stream), the model keeps each write as (gap, diagonal = gap − commit cycle, value). A reader at gap G in cycle t looks up diagonal G − t and takes the write with the largest gap below G. That is the flow rule of `topology.md` §4, on a bounded ring (proof `p_srf_live_window`).
- **Collisions (OTS-E-SRF-002):** two writes to the same row, stream and gap committing in one cycle. Each colliding writer's queue reports SRF-002 once per collided stream; reports are in ascending queue order. The register keeps the value of the writer with the lowest (queue, byte plane); the others are discarded (`commit_due`).
- **One writer per (queue, byte plane).** A writer is a (queue, byte plane), not an instruction. On a MEM queue the two liquid threads can each issue an R-type reference (Read, Gather) in one cycle (§3). When both write one stream in one commit cycle they do not collide: each tile drives only its own superlane's 16 lanes, and the tiles are partitioned between the threads (each result is zero on the other thread's tiles, §3), so the register takes the per-tile merge (the bitwise OR of the two results) as **one** commit, with one `T srf` line. Against other writers of the same stream the merged pair is one writer.
- **SXM OR merge (HC34 p.31, ISCA20 Fig. 4).** Exception: when exactly two writes collide and one comes from the select queue (SEL) and the other from a transposer queue (TSP) of the same SXM hemisphere, they are not a collision: the register receives the bitwise OR of the two values and neither queue reports SRF-002. The result does not depend on the order of the two queues' dispatch. Any other group (a shifter or the permuter with SEL or TSP, two TSPs, three or more writers) is a collision as above.: `topology.md` §4.
- **VXM chained read (§5):** a VXM source operand with its chain bit set does not use the flow rule. A chained read at gap G in cycle t takes the write made at gap G in cycle t − 1 on that row and stream (`srf_read_chain`); with no such write it is OTS-E-TIM-001. An operand with its chain bit clear follows the flow rule, so it never sees a write at the VXM's own gap. No other unit has a chained read.
- **Missing values:** a read with no live value is OTS-E-TIM-001. If the stream has live writes on that row but all are at or downstream of the reader, it is OTS-E-DIR-001. A write is live while its value can still be on the row: writes that have fallen off the end of the row do not count.
- **Operand alignment:** a w-byte element at stream s needs s ≡ 0 mod w and s + w ≤ 32 (OTS-E-OPR-002). This applies to reads and writes alike (review R3).

## 3. Instruction front end, barrier and ICU (`slices/cu/cu_iq.sail`, `postlude/iq.sail`, `postlude/tick.sail`, `slices/cu/cu_insts.sail`)

**Instruction front end** (design  §7; sources: ISCA20 §III-A1 and §III-A3; HC34 p.27). The model replaces a per-cycle record input with the structure the published sources describe: a queue holds text, and the text decides when each instruction dispatches. The ICU of the published sources has four stages (Enqueue, Parcel, Decode, Dispatch); the model has the same four.
- **IQ.** Each of the 144 data queues and the control channel has an IQ of 32-bit **units**, of capacity `icu.iq_depth` bytes (the capacity is not published; default 1280, twice the 640 bytes one Ifetch brings; 64..4096, a multiple of 4). The program of a run is each queue's **initial IQ image** (the host's program load) and any later text supplied by data-queue fetches or timed host injection. A program is therefore a set of per-queue text images and an SRAM preload, and has no cycle numbers: time is in the text.
- **Text format.** See `encoding.md` under “Word formats.” OpenTSP defines the byte layout of fetched text. An instruction is one unit (the CU, MXM and C2C layouts: tags 0, 3, 5) or two units (MEM, VXM and SXM: tags 1, 2, 4; word bits 63..32 first). Bit 31 of the first unit is the **bundle bit** (1: this instruction and the next dispatch in one parcel); the decoder clears it, and bits 30..28 of the unit, which are part of the instruction word (bits 30..28 of a 32-bit word, bits 62..60 of a 64-bit word), are the slice tag. A one-unit instruction is the unit with bit 31 cleared; a two-unit instruction is the first unit's bits 30..0 as word bits 62..32 and the second unit as word bits 31..0. Tags 6 and 7 decode to nothing (OTS-E-DEC-003) and take one unit. The unit `0xFFFFFFFF` is **padding**: it is never enqueued. `NOP n` is the unit n (1..65535).
- **Capture.** A fetch supplies two vectors of text to the issuing IQ, 640 bytes on ref. Stream Ifetch names one stream. Its two values occupy successive cycles t and t+1. At t latch the first vector, its checked integrity state and the stream selector in the issuing queue. At t+1 sample the second vector after that cycle’s external inputs and stream commits, before newly executing instructions. Report a missing or bad operand on its own edge. A missing beat discards the pair. An uncorrectable superlane supplies poisoned text for that word. Complete the old pair before accepting a new first beat in the same cycle. A back-to-back issue can select a different stream, so its first-beat path and the completing second-beat path both need access to the station in that cycle. Reset clears the pending sample. It keeps the chip live until completion. Local IfetchM uses two actual reads of the issuing MEM slice, sampling data and stored check bits independently at t and t+1 (§3 below).
- **Admission.** Instruction fetches use `icu.fetch_staging_depth` to limit outstanding payloads per queue. Local fetch checks capacity before starting and again when the second word completes. It reserves the read path but does not reserve a staging slot. Stream fetch checks staging after its first read and again at completion. The capture latch is separate from the staging FIFO. At completion the stream form sees the FIFO after this cycle’s enqueue, while the local form tests before enqueue. A full staging FIFO at an admission check raises OTS-E-IQ-003 and discards that fetch. A host injection is a separate scripted producer (§14).
- **Delivery.** A successful instruction fetch becomes eligible at t+1+`icu.fetch_latency`. The enqueue stage drains ready units in FIFO order, up to `icu.fetch_bytes_per_cycle` bytes per cycle per queue. Padding consumes bandwidth and is discarded. On ref, for an otherwise empty path and a fetch executed at 10, bytes 0–15 are eligible at 15 and bytes 624–639 at 54. A unit delivered to a full IQ is lost. Enqueue raises OTS-E-IQ-002 once per affected queue and cycle and continues with the remaining units.
- **Physical availability.** Let S be the superlane count, b the beat (0 or 1), and k the tile (0 through S−1). Its 16 bytes are sampled at t+b+k. The first possible IQ delivery from this tile is t+1+L+floor(16(bS+k)/R) for fetch latency L and R bytes/cycle. Require that delivery strictly follow sampling: a stream sample taken in the execute phase cannot feed the earlier enqueue phase on the same edge. Later units in that tile and delays from other queued payloads can only increase delivery time. Check both beats. For R ≤ 16 the reader cannot outrun the tiles. For R > 16 each step to the next tile increases the earliest delivery time by at most one cycle, so the last tile of each beat is the limiting one. The bound describes source availability. Additional interconnect delay must fit in the profile latency.
- **Completion.** At the end of a run, stranded text such as half of a two-unit instruction raises OTS-E-IQ-004. NOP prefixes alone do not. The finish check exempts queues left parked at an unreleased Sync, HostWait or DeskewRecv and applies the global control-park exemption (`model_finish`, §12). A pending patrol repair by itself does not extend the run (§15.4).

- **Parcel.** The head parcel of a queue is the **leading NOPs** (units that are `NOP n` with bundle bit 0, before the first other instruction: a timing prefix) and then the instructions up to and including the first whose bundle bit is 0. A parcel is **complete** when all its units are in the IQ. A `NOP` with the bundle bit set, or after the first instruction of a parcel, is an instruction of the parcel (it breaks the slot rule below, unless alone). The parcel is decoded when it dispatches.
- **Due.** A queue dispatches at most one parcel per cycle. The head parcel is **due** at cycle `earliest` = (the queue's last dispatch cycle) + 1 + (the sum of its leading NOPs); the last dispatch cycle is −1 before the first, so the first parcel of a queue with no NOP is due at cycle 0. A NOP n therefore delays the next parcel by n cycles beyond the usual one (ISCA20 §III-A1: NOP n separates two instructions in program order by n cycles); a lone NOP entry (with bundle bit 0, no instruction after it in its parcel) is a prefix of the next parcel and dispatches nothing.
- **Dispatch or wait.** At each cycle ≥ `earliest` at which the parcel is complete and **no instruction of it is held**, it dispatches (its last dispatch cycle becomes this cycle, so a held parcel also shifts every parcel behind it). An instruction is **held** when the queue or the path it needs is occupied: the queue is parked by a Sync (a queue's own Sync and Notify are not held by its own barrier); the queue is busy (a Deskew or RuntimeDeskew hold, an AGT reference or Repeat iteration issued this cycle); a Repeat is pending on the queue; or the path is busy, in the trailing waits of a finished loop, runs a loop, or has an open configuration the instruction does not continue (below; an Ifetch needs no path, IfetchM needs the R path); an instruction that needs the whole queue is held while either path has a loop running **or an open configuration**, since an open configuration runs its loop with the fields received so far and a reference may be due in that very cycle (an AGT reference issued in cycle c also holds the queue for it, see §4). Whether any instruction of the parcel is held is decided as a whole: a parcel whose slot rule is violated, or that does not decode, is held by the whole-queue conditions only (it needs the whole queue). **Waiting is not an error:** a held parcel, an incomplete parcel and a parcel not yet due report nothing, and the queue's AGT references and Repeat iterations continue.
- **Underflow.** When a delivery of fetched text completes the head parcel after the cycle it was due, and the queue was free in the previous cycle (not parked, not busy, no Repeat, both paths idle), the IQ ran dry: a simulator may report the **lint OTS-W-IQ-001** at the parcel's dispatch, and the parcel dispatches (ISCA20 §III-A3: "It is imperative that IQs never go empty so that a precise notion of 'logical time' is maintained across the chip"). The lint is the first of the queue's reports in that cycle, before the dispatch checks of §8 (the order matters only among the `T` lines of one run with `--lint`), and the parcel still dispatches in that cycle: its effect is late relative to the schedule the compiler intended, which is what the lint tells the user. A parcel whose text was complete when it was due is never OTS-W-IQ-001, and a queue that waits for a barrier, a loop or a Deskew is not starved while it waits (the text arrives meanwhile).
- **Slot rule.** A parcel may carry only instructions that use distinct dispatch slots. On a non-MEM queue the parcel holds one instruction (HC34 p.23: "One instruction issued per cycle at each dispatch path"). A MEM queue has two dispatch paths, R (Read, Gather) and W (Write, Scatter), one per SRAM port, and a parcel may hold: one Ifetch or IfetchM; per liquid thread one R-type and one W-type reference; and one AGT configuration instruction (one per cycle). An IfetchM takes the fetch slot **and** the R port of every tile, so a parcel cannot hold it with a Read or Gather of either thread (below). Any other instruction needs the whole queue and must be alone. When a parcel with two or more instructions breaks these rules (two in one slot, a whole-queue instruction with another, an instruction that does not decode among several, a NOP among several), every instruction of it is **OTS-E-QUE-001** and none dispatches. QUE-001 means exactly this: a violation of the slot rule. It is no longer a report of a busy queue (a busy queue makes the parcel wait). Instructions that fit are each checked on their own path (an Ifetch needs no path). The rate conflict with ISCA20 ("one or more instructions per cycle") is recorded in `provenance.yaml` `conflicts: queues.dispatch_rate`.
- **Control channel.** Load the control IQ before start. Its initial image must fit `icu.iq_depth`. During execution the host may append units using timed `H inject` (§14). The control channel cannot issue Ifetch.


**Barrier** (ISCA20 §III-A2):
- **Sync** parks a queue. On the control channel it parks every data queue; on a data queue it parks that queue only.
- **Notify** on any queue releases every Sync dispatched at or before it, including a Sync dispatched in the same cycle on a lower or higher queue. Dispatch resumes 35 cycles after the **first** such Notify.
- The barrier is causal: it uses only Syncs and Notifies that actually dispatched. A Sync or Notify that is rejected (DEC-003, QUE-001, QUE-002) has no effect. A Sync with no later Notify parks for the rest of the program.
- A queue's own Sync and Notify are not held by its barrier. A parcel with any other instruction **waits** while the queue is parked, in order, and dispatches at the first unparked cycle at which it is due (it was OTS-E-BAR-001 before the front end; there is no such diagnostic now). Pending AGT references and Repeat iterations wait while the queue is parked and resume, with their spacing kept, at the first unparked cycle. The parcels behind a waiting parcel wait with it.

**Dispatch paths.** See the slot rule and the hold conditions above. The paths of a MEM queue are held separately (below).

**Queue occupancy.** A queue holds its head parcel (the parcel waits, with no report) while it is busy:
- for a **NOP n**: not at all. NOP is a timing prefix (above); the cycles it delays are cycles in which the queue has no due parcel, so a queue is not held by one. A Repeat, an AGT loop and its references continue through those cycles;
- for a **Repeat**: through the cycle of its last iteration;
- for an **AGT loop**: through its trailing waits, i.e. through cycle last + Σ countdown of its levels, where last is the cycle of its last reference. The loop is a set of nested `For` loops in which every level ends with an unconditional `Wait(countdown_x);` after its `Issue(instr);`, so after the last Issue the loop still waits countdown_a, …, countdown_d before it ends. A new reference on the path waits through that tail. On a MEM queue this holds only the loop's own path (each path has its own AGT): a W-type reference may issue while an R-path loop runs, but an R-type reference, or an instruction that needs the whole queue, waits. An Ifetch on a MEM queue is not held by either path; an IfetchM is held by the R path (it reads through the R port). A parcel waits if any of its instructions waits.
- per **path** of a MEM queue: a reference or AGT reference holds its path through its cycle.

**Repeat n, d** re-issues the queue's last dispatched instruction n more times. Iteration k (1..n) issues at p + k·(d + 1), where p is the cycle the repeated instruction issued. If p + d + 1 is before the Repeat's own cycle r, the first iteration issues at r and the rest follow d + 1 apart. Source: ISCA20 Table I: "Repeat n, d Repeat the previous instruction n times, with d cycles between iterations". The delay d is the number of cycles between two iterations, and the original instruction is iteration 0, so `max` at 10 followed by `rep 54, 1` at 11 issues at 10, 12, …, 118. d is 0..15 (4 bits): d = 0 is "no cycles between iterations", the iterations on consecutive cycles (spacing 1), so `rep 54, 0` at 11 after `max` at 10 issues at 10, 11, …, 64; n is 1..4095, and n = 0 does not decode (OTS-E-DEC-003). One queue can issue an iteration on every cycle. While the iterations run the queue's next parcel waits (the queue is busy through the cycle of the last iteration), so the Repeat and the instruction that follows it are two parcels, and the iterations delay everything behind them. The repeated instruction is the last one other than NOP, Repeat and AGT configuration. After a Repeat, p is the cycle of its last iteration, so a second Repeat continues the spacing; AGT references do not change p, and a Repeat after a loop repeats only its reference 0. An iteration repeats the instruction's execution only (§1: it executes at its issue cycle + d_skew), not the effects of its dispatch. So Sync, Notify, Deskew and RuntimeDeskew, whose effect is at dispatch (the barrier, the queue hold), leave nothing to repeat (the published examples show Repeat only on compute instructions). A repeated loopable MEM reference is one reference per iteration and opens no AGT loop. A repeated IfetchM reserves its second beat as an explicit IfetchM does (§3, IfetchM). With nothing to repeat, Repeat is OTS-E-RES-001.

**Control channel.** A convenience of the model and the assembler, not a published issue point: the published scheme ("one IQ is designated as the notifier … all other IQs are parked on a Sync") needs no control channel: it is expressed with data-queue Sync and Notify. A control Sync can additionally park queues that are busy or running a loop, where a data-queue Sync on such a queue waits for the busy condition to end. It carries **Sync, Notify and Config** only (and NOP as the timing prefix of the text, which is not an instruction). Repeat, Ifetch, IfetchM, SetVL and every slice instruction there are OTS-E-QUE-002; the control channel can receive additional text through host injection (§14). A 64-bit layout (tags 1, 2, 4) on the control channel decodes by its tag and is QUE-002 like any other instruction the channel lacks. **Hardware consequence of the control Sync:** because it parks every data queue from its own cycle (§1 step 4), an implementation decodes the head of the control IQ at least one cycle ahead of its dispatch and broadcasts the park to all 144 data queues in that cycle; the timing of the model is not changed by this and the channel stays a model convenience.

**Other ICU instructions** issue on every data queue (HC34 p.27). Any other instruction on a queue whose unit lacks it is OTS-E-QUE-002.

**Absent MEM slices.** On a profile with `geometry.mem_slices_per_hemisphere` < 44, the MEM slice s (queue s) does not exist when (s mod 44) ≥ that key. The queue map stays 144 ids, so its queue still has an IQ, accepts text and fetches nothing (an Ifetch always fills the issuing queue's own IQ, and an absent queue never executes one). Every instruction a parcel of that queue holds is OTS-E-QUE-002, one report per instruction, whatever it is: a Sync does not park the queue and a Notify does not notify, a Repeat repeats nothing, a word that does not decode is QUE-002 (not DEC-003) and a parcel that would break the slot rule is QUE-002 (not QUE-001); nothing else happens (`dispatch` in `postlude/tick.sail`, `queue_present` in `core/queues.sail`). The slice has no station (`topology.md` §4) and no SRAM: the harness `S` and `D` lines of an absent slice are input errors (§12). A program that waits for a Notify from an absent queue never finishes, as for any queue that cannot notify.
- **Ifetch s** reads the one stream s twice (640 bytes: the vector of cycle t and the next vector of s at t + 1; ISCA20 §III-A3) at the issuing unit's read gap, starting in its execute cycle (dispatch + d_skew; `timing.cu.d_skew` = 0 in the shipped profiles, so the dispatch cycle); a C2C RX queue, which reads no operand stream, fetches at its hemisphere's TX gap on the row arriving at the chip edge (`topology.md` §4); any stream is legal. A missing value in either read is TIM-001 or DIR-001, at the cycle of the failing sample, and nothing is fetched. The 2 × vlanes bytes read are the payload of the fetch: they are the next text of the issuing queue (instruction front end, above), the byte at lane 0 of the first vector first, then the second vector, four lanes per unit, little-endian.
- **SetVL n** (n = 1..32, a 6-bit field, on every profile; an opentsp instruction choice) sets the issuing queue’s active output/storage length, clamped to the profile’s superlane count: a value above the count is the count, so a program written for more superlanes runs on a narrower profile (n = 0 and n = 33..63 do not decode). Result superlanes beyond that length are zero; masked MEM writes leave stored bytes unchanged. Input integrity checks remain active across the consumed operand, so an error beyond the output length may still produce an ECC event, diagnostic or interrupt. This is a functional masking contract, not an ECC clock-gating or power model. Config’s liquid-thread split is separate.
  - SetVL does not change any encoding limit. The Shift amount limit is the configured lane count of the profile (`vlanes − 1`), whatever the SetVL.
  - **When it applies.** SetVL and Config take effect in their own execute cycle, and an element reads the queue's vector length and thread split in **its** execute cycle (the gating is applied when the element schedules its result, `write_planes` in `sys/operands.sail`, and when it writes SRAM). The order is that of execute cycles, not of dispatch: on a VXM queue an `add` dispatched at 40 (d_skew 2, executes at 42) after which `setvl 1` is dispatched at 41 (d_skew 0, executes at 41) produces a one-superlane result. Within one cycle the elements of the execute ring (§1 step 3) run before a SetVL or Config that executes in step 5, so an `add` dispatched at 39 (executing at 41) still produces a full-length result.
  - SetVL gates only result streams, SRAM writes and the tiles whose addresses Gather and Scatter check. Unit state loads and keeps whole vectors: the MXM weight buffer, installed weights and accumulators, and the SXM maps, are not masked.
- **Config v** on a MEM queue sets the liquid-thread split. Tiles 0..v are thread 0 and the rest thread 1; v >= geometry.superlanes - 1 puts every configured tile in thread 0. On other queues Config is an architectural no-op: it accepts a power hint with no state, result, diagnostic or timing effect, and models no physical power transition.

**Ifetch from local memory** (round 3,; `slices/cu/cu_insts.sail`, `slices/cu/cu_ifetchm.sail`, `slices/cu/cu_iq.sail`).
- **IfetchM a** is opentsp’s local-memory fetch form, inspired by ISCA20 Table I. It reads word a of its own MEM slice at execution t and word a+1 at t+1, capturing data and ECC separately. The pair must fit the slice segment. It reserves the R path for two dispatch cycles; a later R instruction waits. Each cycle uses only that word’s bank. A first-cycle bank conflict with Write/Scatter or a W-path AGT reference cancels both operations with MEM-001. On the second cycle, the already accepted fetch completes and only the conflicting new W operation is rejected. Repeat iterations closer than two cycles report QUE-001 for the overlapping iteration. **A repeated IfetchM reserves its second beat exactly as an explicit IfetchM issued in the same cycle does** (before it, an iteration reserved nothing): it holds the R path through the cycle of its second read (an R-type instruction waits for the cycle after it) and takes the bank of word a + 1 in that cycle, so a Write, Scatter or W-path reference dispatched in that cycle that meets the bank is OTS-E-MEM-001 and not a port overlap (TIM-001). `ifetchm a; nop 1; ifetchm a` and `ifetchm a; nop 1; repeat 1, 1` are two encodings of one schedule (`test/directed/frontend.py` section 16; Sail `reserve_local_fetch`, used by the dispatch and by the Repeat iterations). Payload delivery starts at t+1+`icu.fetch_latency`. In-flight fetch state participates in next-event calculation and completion, and is cleared by reset.
- **IQ occupancy.** IQ underflow is the simulator lint OTS-W-IQ-001, defined in the instruction front end above. It is **not a diagnostic**: it is not counted in the `E` line, is not in the golden vectors, and an implementation need not report it (`validation.md` §5). IQ overflow, the staging bound and the text left at the end of the run are diagnostics OTS-E-IQ-002, -003 and -004. The hardware behaviour is normative: a parcel whose text arrives late still dispatches when its text is complete, and the units that find the IQ full are lost, with a diagnostic. The IQ holds text units. A fetch delivers its bytes after `icu.fetch_latency` at `icu.fetch_bytes_per_cycle`, and a queue underflows when the compiler's prefetch is late (ISCA20 §III-A3), overflows when it is early or too large.

## 4. MEM (`slices/mem/mem_insts.sail`, AGT in `postlude/tick.sail`, tiles in `core/sram.sail`)

**Read / Write.** One word per instruction at the slice's station (ISCA20 §III-B).
- **Read + Write pairs:** an R-type (Read, Gather, IfetchM: §3) and a W-type reference of the same liquid thread (IfetchM: of either thread) in one cycle (instructions of the parcel, or an AGT reference due that cycle) must address different banks; otherwise both are OTS-E-MEM-001 and neither runs (an AGT reference so blocked still advances its loop). An indirect reference (Gather/Scatter) has no known bank at dispatch and clashes with any reference of its thread on the other path. A direct address outside the slice (0 ≤ address < `sram.words_per_slice` fails, for example an AGT reference stepped past the end, or IfetchM's word a+1 after the last word) accesses **no** bank: it clashes with nothing, and its execution reports OTS-E-OPR-001. References of different threads use different tiles and never clash.
- **AGT per path:** each path has its own AGT. A loopable reference opens its path's configuration when it issues with no other reference instruction on its path in the cycle; a reference instruction of the other thread on the same path, even one a dispatch check rejects, keeps the loop from opening. **Configuration routing:** configuration instructions carry no path field; one configures the path whose AGT is configuring; when both are (a Read + Write pair), the one that has received fewer so far, R on a tie, so a pair's configuration instructions alternate R, W, R, W. A read loop (address 0x1000, step 24) and a write loop (address 0x00ff, step 1) of 112 references each are written as read + write at 10, `step 24` at 11 (R), `step 1` at 12 (W), `iterations 112` at 13 (R), `iterations 112` at 14 (W) (Iterations n = n references, `conflicts: agt.iterations`). Each loop runs while its configuration arrives, with its own path's fields so far (period 1: R references at 10, 11, 13..122; W at 10, 12, 14..123). Both configurations end at the first cycle without a configuration instruction. While a path's configuration is open its loop holds that path: a new reference on it waits; only configuration instructions get through (decision `queues.mem_config_routing`). A Repeat after a cycle that issued more than one instruction has nothing to repeat.
- **Why not two queues:** ISCA20/HC34 count 144 queues, which leaves one per slice. The model keeps one queue per slice with two dispatch paths.
- **No ReadWrite:** there is no fused ReadWrite instruction.

**Tile gating:**
- Read, Write, Gather and Scatter carry a thread tag t (bit 53).
- Tile g executes the instruction only if both hold: g is below the queue's SetVL length, and g is in thread t (Config split).
- An inactive tile changes no SRAM and drives zero on its superlane of the result stream. For Gather and Scatter it also checks no address (each tile has its own). A Read or Write checks its one address whatever the active tiles, and a Write with no active tile still writes the word back unchanged, with its `T sram` line.

**Gather / Scatter** (each tile produces one element of the vector).
- Each active tile g takes its address from the little-endian bytes 0..1 of superlane g of the map stream (`sram.addr_bits` bits, 13 on `ref`: the low bits of the 16-bit value). **The bits from `sram.addr_bits` up to bit 15 are ignored, not checked:** a map entry with them set addresses the same word as with them clear, and raises no diagnostic (OTS-E-OPR-001 is raised only for an address outside the segment or the slice).
- Each moves **one element**, byte k, where k is the instruction's 4-bit lane field:
  - **Gather** puts byte k of SRAM[addr_g] on lane 16g + k and zeroes the other lanes.
  - **Scatter** writes lane 16g + k into byte k of SRAM[addr_g] and leaves the rest of the word unchanged.
- **Scatter is a same-bank read-modify-write (requirement).** A Scatter tile changes one byte of a word, so in its execute cycle it reads the word (to merge and to check its code, §15) and writes it back in the same cycle: one read and one write of **one bank** in one cycle. This is a deliberate exception to the pseudo-dual-port rule (a slice services a read and a write only in different banks, ISCA20 §III-B). An implementation provides it as an internal same-bank read-modify-write in the tile, or as a forwarded read-modify-write with the same observable timing (the word read is the word before the write; the write lands in the same execute cycle). The exception belongs to Scatter alone: it is one W-type reference with no known bank at dispatch, and the bank rule of "Read + Write pairs" above still applies to it as a reference of its thread, so a Read or Gather of the same thread in the same cycle clashes with it (MEM-001).

**Addresses.**
- The effective address is the instruction's address plus the AGT offset, with **no wrap-around**. Outside 0.. segment − 1 it is OTS-E-OPR-001.
- **SetSegment n** sets the segment (n at most 2^`sram.addr_bits`; the segment is never larger than `words_per_slice`).
- **Address width.** A slice is addressed by `sram.addr_bits` bits (13 on `ref`, 13 to 16 in a profile) and has `words_per_slice` words, at most 2^`sram.addr_bits`. The address of Read and Write is a 16-bit field in bits 47..32 whose bits from `sram.addr_bits` up are zero (a word with one of them set is OTS-E-DEC-003), the address of IfetchM is bits 15..0 under the same rule, SetSegment holds its bound in bits 32..16, and a Gather or Scatter map halfword is cut to its low `sram.addr_bits` bits. A 14-bit slice of 16384 words gives 440 MiB with 88 slices at 20 superlanes (the published figure of a later part is about 500 MB, secondary source), 15 bits 880 MiB, 16 bits 1760 MiB; the harness and the ISS allocate words when they are first written, so resident memory does not grow with the address width.
- The effective stream is the instruction's stream id plus the AGT StreamStep offset, on the same row. Outside 0..31 it is OTS-E-OPR-001.
- **Gather and Scatter** add the AGT Step offset to every tile's address from the map. StreamStep applies to Gather's destination and Scatter's source stream; the map stream never moves.
- **Address errors in Gather and Scatter.** Address validation takes place independently in each active tile. The resulting OPR-001 diagnostic can accompany a partial update. For integrity faults, collisions and other diagnostic effects, use the per-code rules in §8.
  - **Gather:** each active tile acts alone. A tile whose effective address is outside the segment or the slice drives zero on its lane `16g + k`; the good tiles' lanes are written to the destination stream, and the instruction reports **one** OTS-E-OPR-001.
  - **Scatter:** the tiles with a good address write their byte; a bad tile writes nothing; one OTS-E-OPR-001.
  - **Why:** superlane g runs g cycles after superlane 0 (`topology.md` §3), so a check over all 20 tiles before any acts is not causal. A tile's behaviour depends on its own address only. The tiles written are fixed by the map and the segment, not by the order of the tiles.
  - A failed stream-availability or destination-placement check suppresses the affected data operation. Operand integrity checks can still report errors and propagate poison (§15).
  - These errors are also reported in the spare bits of the stream registers (§15.5); the diagnostics are unchanged.

**AGT** (HC34 p.25). A loopable instruction (Read, Write, Gather, Scatter) can be followed, on the next consecutive cycles of the same queue, by configuration instructions:

| Record | Meaning | Default |
|---|---|---|
| `Countdown d` | Idle cycles after each reference of the level (`Wait(countdown)`): the period is d + 1. An explicit value below 1 counts as 1 (rule (3)) | 0 |
| `Step a` | Signed address stride, magnitude at most min(2^`sram.addr_bits` − 1, 32767) (−8191..8191 on `ref`) | 0 |
| `StreamStep s` | Optional: stream-id stride, 0..31 | 0 |
| `Iterations n` | The level makes n references (`Iter(3)`: 3). A value below 1 counts as 1 | 2 |

The defaults are countdown 0, step 0 and iterations 2. Each field of a level has a **received** flag, which is state: it tells a field that was not received (it keeps its default, so a Countdown that was never sent gives spacing 1) from one received with an explicit value (a received Countdown below 1 counts as 1, spacing 2). An implementation keeps one received flag per field of each of the four levels of each path. A loop of n iterations makes n references (`isa-db/provenance.yaml`, `conflicts: agt.iterations`).

- **Levels:** up to **4 nested loop levels**, configured inner to outer. A level exists once one of its fields has been received.
  - Within a level the fields go in the order Countdown → Step → StreamStep → Iterations.
  - A configuration instruction that does not advance in that order starts the next level. Skipped fields keep their defaults.
  - A fifth level is OTS-E-OPR-001 and aborts the loop: no further references issue.
- **End of configuration:** the first cycle in which the queue dispatches no configuration instruction ends it. A cycle in which the queue has no parcel to dispatch (none due, incomplete or held), or in which its parcel breaks the slot rule (every instruction QUE-001, §3), dispatches none and ends it. A configuration instruction that dispatches keeps the configuration open, whatever its own checks report. So a configuration instruction held by a barrier, or text not yet complete in the IQ, ends the configuration like a gap.
  - In that cycle the loop runs only if it still has references to issue or its trailing waits reach the cycle. Then an instruction that needs the loop's path or the whole queue waits (for the whole queue, also while the configuration remains open, even if no reference is due then), and a reference on the other path, or an Ifetch, dispatches. A reference 0 with no configuration instruction after it, or a loop whose levels are used up, leaves the path free.
  - A configuration instruction with no configuration open is a stray configuration instruction. It is routed to the R path (Configuration routing, above), so it waits while an R-path loop runs or is in its trailing waits, and then, or at once when none runs, for example while only a W-path loop runs, it is OTS-E-OPR-001. A new R reference in the same parcel does not hold the path against it: the configuration instruction is checked first (§8, "Order within a queue's cycle").
  - A loopable reference 0 that issues alone on its path opens the configuration **at dispatch**, whatever its execution (at dispatch + d_skew) reports: a reference 0 that raises a diagnostic still runs its loop, and each later reference reports its own diagnostics (directed test D9).
- **Issue** (`For (a =0; b<iters_a; a++) Issue(instr); If (a<(iters_a-1)) Instr.addr += step_a; Wait(countdown_a); If (b<(iters_b-1)) Instr.addr += step_b; Wait(countdown_b); …`, read statement by statement):
  - Reference 0 is the loopable instruction itself, at its dispatch cycle.
  - `Issue` takes one cycle, then each `Wait(countdown)` adds idle cycles. The `If` governs only the address step: every `Wait` is unconditional.
  - The next reference is the innermost level that has references left. It issues 1 + (the countdowns of every level that wrapped) + (the countdown of the advancing level) cycles after the previous one. So a level boundary waits the inner **and** the outer countdown. The advancing level's step and stream step are added; the outer step is added to the address of the last inner reference.
  - The loop runs while its configuration is still arriving. A configuration instruction is applied before the AGT reference of its own cycle, and each reference uses the fields received so far (defaults for the rest).
  - When every level received so far is exhausted while the configuration is still open, the AGT waits for the next configuration instruction (opentsp; the sources are silent). The loop ends when, with the configuration closed, no level can advance.
  - Worked examples (all reproduced cycle-exactly by `test/directed/directed.py`): `Op(A),Step(2),AGT→Op(A),Op(A+2)`; `Op(A),Cdwn(1), AGT →Op(A),NOP,Op(A)`; `Op(A),Step(0),Cdwn(1)→Op(A),Op(A),NOP,Op(A),Op(A)`; `Op(A),Iter(3),Cdwn(2),Step(1) →Op(A),Op(A),Op(A),NOP,NOP,Op(A+1),Op(A+1),Op(A+1)`; and the six cube traversals (`Rd, SetStep(+1), SetStep(+1), SetStep(+1)` for X, Y, Z, …).

- **Scatter loops.** An AGT Scatter loop whose Countdown was not received (spacing 1: a Scatter on every cycle; an explicit Countdown of 0 or 1 gives spacing 2) needs the read-modify-write above on every cycle of the loop on that slice's bank; the references of the same thread on the other path in those cycles clash with it as stated. The machine does not stall for it: the read-modify-write must complete in the cycle, so the spacing-1 case is the one that fixes the requirement (a loop with a larger countdown needs it less often).

**Power.** **PowerConfig** and **DeepSleep** are architectural no-ops: no power or sleep/wake state is modelled. They must not change any result, diagnostic or cycle count, and an implementation may use them as hints (`platform.md` §9.2).

## 5. VXM (`slices/vxm/vxm_insts.sail`, `core/numerics/*`)

- **Execution:** 16 ALU queues. Each instruction applies one lane kernel independently to all lanes (ISCA20 §III-C).
- **All 16 ALU queues are alike: decision `queues.vxm_alu_kinds`.** The published sources point at two ALU kinds. The ATPESC 2022 Track 1 Talk 4 slides (p.20-21) carry the labels "Small-ALU" and "Big-ALU" on their floorplan drawing, without saying which unit they belong to; the published sources do not say which ALUs are large or which operations need them. **opentsp:** every VXM queue executes every VXM instruction, each entry with its row of the timing table (`timing.vxm` unless `timing.overrides` gives the entry its own, §1).
- **Types:** i8, i16, i32, u8, u16, u32, bool8/16/32, f16, f32 (HC34 p.26).
  - Integers wrap (`_mod`, and plain add/sub/mul) or saturate (`_sat`), signed or unsigned per type.
  - Integer Neg and Abs wrap as well: neg and abs of the minimum value (−128 for i8) give the minimum value. ReLU gives max(x, 0).
  - **Unary kernels on unsigned and boolean elements.** The kernels `k_unary` read an integer element as signed or unsigned **according to its type**, like the binary kernels. No instruction encodes Neg, Abs or ReLU on an unsigned or boolean type (`unop_legal`; the next list), so these results are reachable only by calling the kernel, but the kernel is total and defined, and an implementation of the lane kernels (the ISS crate `tsp-numerics`, an FPGA ALU test bench) must give exactly these results:
    - **Not:** the bitwise complement inside the element width for every integer type, signed or unsigned (u8 0xF0 gives 0x0F). On a boolean it is logical: zero gives all ones, any other value gives zero.
    - **Neg:** the modular negation 2ⁿ − x inside the element width on every signed or unsigned integer type (u8 0x01 gives 0xFF, u8 0x80 gives 0x80, u32 2 gives 0xFFFFFFFE).
    - **Abs, ReLU:** the identity on an unsigned type (an unsigned value is never negative: u8 0xFF stays 0xFF and u8 0x80 stays 0x80, not 1 and 0 as a signed reading would give).
    - **Neg, Abs, ReLU on a boolean:** 0, as every binary operation a boolean does not define gives 0 (`k_binary`).
  - Booleans: an element is true when any of its bits is set. Results are canonical, all ones or zero. And, Or, Xor and Not are **logical** on truth values (b8 0x01 and 0x02 gives 0xFF), and Cmp eq/ne compares truth values.
  - **No exception flags; bf16 only as a profile extension.** The ISA has no IEEE exception flags (invalid, overflow, underflow, inexact, divide by zero) and no status register for them: results follow the rounding and NaN rules in this section and nothing else is observable. bf16 is not an element type of the base set of 0.1 (type codes 13 to 15 are illegal, and so are 17 to 31); it is an extension that a profile declares in `extensions` (next bullet), and a profile that does not declare it imports a bf16 value by converting it outside the ISA, as before. The range consequence of the import: an f16 has the largest finite value 65504, a bf16 reaches about 3.4e38, so a bf16 value above 65504 in magnitude becomes ±∞ when it is converted to f16 (and a small one may become subnormal or zero); an importer checks the range of every value it converts, as the compiler does for weights (the f16 range policy).
  - Floats are IEEE binary16/binary32 with round-to-nearest-even. Subnormals are kept on input and output (no flush to zero). There is one canonical NaN per format, 0x7E00 (f16) and 0x7FC00000 (f32). Sail defines the arithmetic with exact intermediate values and rounds the result to the destination format.
  - **Extensions and the `extensions` profile key (implementation choice, `extensions` in `isa-db/provenance.yaml`).** The profile key `extensions` is a list of extension names, `[]` in `ref`, `mini` and every test profile except `test/ext_bf16` (`["bf16"]`), `test/mini_ext` and `test/ref_ext` (`["wide_acc", "block_fp8"]`). A word that uses an extension the profile does not declare is not an instruction of that profile: it does not decode (OTS-E-DEC-003), exactly as a word with an unassigned type code, so the base set of version 0.1 is what a profile without extensions executes, with the traces and cycle counts of before. A name that is not an extension of this version, or that is listed twice, is a configuration error (`extensions: <name> is not an extension of this version`, exit 2). The catalogue marks the codes of an extension (`extension_codes` in `encoding.json`); a decoder given the catalogue and a profile accepts such a code only when the profile names the extension. The extensions of this version are `bf16`, `wide_acc` and `block_fp8` (§6.1).
  - **bf16, the extension (type code 16 behind the fifth type bit; implementation choice).** bfloat16 is the upper half of a binary32: 1 sign, 8 exponent bits (bias 127), 7 fraction bits, subnormals kept, infinities, canonical NaN 0x7FC0, round to nearest even, no exception flags. No published source names bfloat16 (the published type list is HC34 p.26), so every rule here is an implementation choice, made so that a bf16 weight matrix can be used without a conversion outside the ISA. **Encoding:** the VXM element type is a 5-bit code, the type-extension bit (word bit 17, reserved zero in 0.1) above the 4-bit code of; bf16 is code 16 (bit 17 set, the other four bits zero), and codes 17 to 31 stay reserved. The destination type of a Convert has the same bit 16 above its 4-bit code (bits 27..24). **Operations:** the 16-bit float operations, as f16 (Add, Sub, Mul, Max, Min, Cmp, Mask, Select, Neg, Abs, ReLU, Reduce, Convert, the SG4 form with two operations per lane, an element of two streams); not the integer, saturating, boolean or transcendental operations (their `*_legal` predicates are false for bf16, OTS-E-DEC-003). **Convert** follows the generic rule: a float converted to bf16 rounds to nearest even and overflows to infinity, a NaN gives 0x7FC0, a bf16 widened to f32 is exact. The decode of every bf16 word needs the extension in the profile (the previous bullet).
  - **FP8 element types e4m3 and e5m2 (type codes 11 and 12; implementation choice).** The published sources (ISCA20, ISCA22, HC34, the SHIP paper) name no 8-bit float format and no instruction on one, so everything in this bullet is an implementation choice, made to complete the type list ("a superset of all data types", HC34 p.26) with the two formats that the machine-learning practice uses; there is no feature gate, and an FP8 type is as legal as f16 where it is listed below. `abstractions.fp8_format` in `isa-db/provenance.yaml` records it.
    - **e4m3:** 1 sign, 4 exponent (bias 7), 3 fraction bits. There is **no infinity**: only 0x7F and 0xFF are NaN, the largest finite value is 448 (0x7E), the canonical NaN is 0x7F. A result that is too large, and an infinite input to a conversion, **saturates** to ±448 (0x7E, 0xFE); a NaN stays a NaN. OpenTSP specifies this saturation rule.
    - **e5m2:** 1 sign, 5 exponent (bias 15), 2 fraction bits: IEEE style, the binary16 exponent with a shorter fraction. ±∞ and NaN as in binary16, the largest finite value is 57344 (0x7B), the canonical NaN is 0x7E, overflow gives ±∞.
    - Both: subnormals are kept, rounding is to nearest even, and the NaN rules above hold with the canonical NaN of the format (§5 NaN rules; Max and Min ignore a NaN operand). Arithmetic is exact in Sail like f16 and f32 (`fround` of `core/numerics/fp.sail`, the format record has an `ieee` flag that selects the e4m3 range).
    - **Legal operations** (the `*_legal` predicates of `vxm_insts.sail`): Add, Sub, Mul, Max, Min, Cmp, Mask, Select, Neg, Abs and ReLU, and their SG4 forms. Convert (any supported source/destination type) and Reduce add/max/min also accept FP8, each in its ordinary encoding only. **Not legal** (OTS-E-DEC-003): And, Or, Xor, Not, the `_sat`/`_mod` forms, the transcendentals (TanH, Exp, RSqrt, Log: i8, f16 and f32 only) and the fixed `Conv_*` forms. Type codes 13 to 15 stay illegal.
    - **Convert** follows the rules below with the two formats: float to FP8 rounds to nearest even and (e4m3) saturates; an integer converts like an integer to a float, so that an out-of-range value gives ±448 (e4m3) or ±∞ (e5m2); FP8 to f16 and f32 is exact, FP8 to an integer rounds like a float to an integer, FP8 to the other FP8 format rounds once; the dtype field of Convert has codes 0 to 12.
    - The width is one byte, so an FP8 operand takes one stream, as i8, and the SG4 form does four operations per lane.
- **NaN rules** (`core/numerics/fp.sail`, `lanes.sail`):
  - Max and Min are IEEE maxNum/minNum: a NaN operand is ignored in favour of the other operand; two NaNs give the canonical NaN. −0 orders below +0: max(−0, +0) = +0, min(−0, +0) = −0.
  - Neg and Abs of a NaN give the canonical NaN. Every other operation with a NaN operand gives the canonical NaN.
  - ReLU of a NaN is the canonical NaN; ReLU of −0 is +0.
  - Cmp with a NaN operand is false, except `ne`, which is true.
- **Transcendentals** (TanH, Exp, RSqrt, Log) are correctly rounded, for i8, f16 and f32. This is the contract of the reference: a unit that is not correctly rounded does not conform to this specification. **Portability:** a kernel must not depend on the last ulp of a transcendental unless it targets a profile whose unit is correctly rounded; as guidance only (not a conformance bound, because two implementations that differ by an ulp differ in bits and the golden vectors pin the exact value), a portable kernel can assume a result within 1 ulp of the exact value. An approximate accuracy mode (a lookup table) is not part of 0.1. The model evaluates the exact value by interval refinement (`core/numerics/transcendental.sail`, Ziv's method). The exact value is never a rounding boundary of the destination, so the refinement always ends: exp, ln and tanh of a nonzero rational (ln: other than 1) are transcendental, and 1/√x of a float is never a midpoint. The one exception is the i8 integer rounding of rsqrt(4) = 0.5, an exact tie that rounds to 0. An evaluation that did not end would be a model error, not a value. Sail unit tests `test_transcendental_converges` checks every i8 and f16 input and every 2¹⁸th f32 bit pattern.
  - **Float special values** (`fp_tr_value`): a NaN gives the canonical NaN. +∞: tanh 1, exp +∞, rsqrt +0, log +∞. −∞: tanh −1, exp +0, rsqrt and log NaN. ±0: tanh ±0 (the canonical signed zero of the format, 0x0000 or 0x8000 for f16, 0x00000000 or 0x80000000 for f32; **never the raw lane input**: bits above the format width are dropped), exp 1, rsqrt ±∞, log −∞. A negative finite input to rsqrt or log gives NaN, and log(1) = +0. Large inputs round as the exact value does (exp of |x| ≥ 512 is +∞ or +0; tanh of |x| ≥ 64 is ±1).
  - **i8** (`i8_tr_value`,; the i8 forms exist for completeness: on integer inputs they give few distinct values, for example tanh ∈ {−1, 0, 1}; the sources tie the functions to lookup tables, `abstractions.vxm_lut_configuration`): the input is the integer value v; the result is the exact function value rounded to the nearest integer (ties to even), then saturated to −128..127. So v = 0 gives exp 1, rsqrt 127 (+∞ saturated), log −128 (−∞ saturated) and tanh 0; a negative v gives 0 for rsqrt and log (NaN maps to 0); exp(v) is 127 for v > 5 and 0 for v < −1; rsqrt(4) = 0.5 rounds to 0 (a tie) and rsqrt(1) = 1.
  - **Type legality is an opentsp decision.** HC34 p.26 says "Vector (VXM) processor supports a superset of all data types"; that is a statement about the unit, not about every operation on every type. opentsp restricts the transcendentals to i8, f16 and f32, gives booleans only the bitwise operations, Cmp eq/ne, Mask, Select and Convert, gives Neg, Abs and ReLU no unsigned types, and keeps `_sat`/`_mod` integer-only. The legal types are part of the encoding (`*_legal` in `vxm_insts.sail`; the operation text of every catalogue entry lists them).
- **Mask arity is an opentsp decision.** ISCA20 Table I: "unary operation z = op x point-wise operation on 1 operand, x, producing 1 result, z (eg. mask, negate)". The sources do not say where a unary mask's mask comes from. opentsp's Mask takes the mask as a second stream operand: dst = mask ≠ 0 ? lhs: 0. A source-literal unary form would need an implicit mask register, which no source describes.
- **SG4 group operands.** ISCA20 §III-C: "Each of the ALU's 32-bit input operands are organized along naturally aligned quad-stream group (SG4)", and §I-B: "int16 is aligned on a stream pair, and int32 is aligned on a quad-stream (e.g. SG4 0 is stream 0-3, SG4 1 is streams 4-7, and so forth)". The ALUs are 32-bit and do four 8-bit operations at once: ScaledML 2020 "The VXM has 16 PEs per lane 5,120 total each capable of up to one 32-bit computations per cycle, or four INT8 operations per cycle"; ISC 2020 "up to 5,120 total 32-bit computations per cycle (or 20k INT8 operations per cycle)"; Microprocessor Report 2020 "Each ALU can perform a 32-bit calculation using aligned groups of four stream bytes as operands". **opentsp:** Add … Xor, Not, Neg, Abs, ReLU, the transcendentals, Mask, Select and Cmp (the operations whose result has the operand width) have a **group bit** (bit 18; assembly `.sg4` after the type: `max.i8.sg4 W:0, W:0, W:4`). With it set, every operand, the destination included, is the 4-stream group at its stream, which must be SG4-aligned (else OTS-E-OPR-002), and the ALU performs 4 / w independent operations per lane on the w-byte parts of the group: four i8/u8/b8 operations, two i16/u16/b16/f16 operations, or one 32-bit operation (the same as the plain form). An example is `max.i8.sg4 E:0, E:0, E:4` followed by `repeat 0x36, 0x1` on one queue. With the bit clear an operation names one element per lane as before (an 8-bit operation one stream, a 16-bit one a pair), an opentsp form that the sources do not describe and that keeps an ALU to one 8-bit operation per lane per cycle. Convert, the fixed conversions and Reduce change or fold the element width and have no group bit (bit 18 is reserved there). Tests: `test_vxm_sg4` (`unit_tests/test_vxm_mxm.sail`), directed "" (the example on one ALU queue, with independently computed results), Python `vxm_sg4`.
- **Convert** converts between any two types (`k_convert_any` in `core/numerics/lanes.sail`):
  - integer to integer saturates to the destination range;
  - float to integer rounds to nearest even and saturates (±∞ to the extremes, a negative value to 0 for an unsigned destination); NaN gives 0;
  - integer to float rounds to nearest even, and a value whose rounding overflows gives ±∞ (for f16, |v| ≥ 65520, so most u32 values; u16 65510 gives 65504);
  - float to float rounds to nearest even; a NaN, also between equal types, gives the canonical NaN;
  - to bool means "value ≠ 0" (canonical true or false); NaN counts as true, ±0 as false;
  - bool to a number gives 1 or 1.0, or zero;
  - the fixed conversions `Conv_*` are Convert with their two types.
- **Mask and Select**: the mask element is true when any of its bits is set, whatever the type, so an f16 or f32 mask of −0.0 or NaN is true. The selected operand passes through unchanged (a non-canonical boolean stays non-canonical).
- **ALU chaining is explicit.** ISCA20 §III-C: "Each superlane implements a 4x4 mesh of vector ALUs … The TSP supports chaining together two or more vector ALUs within each lane, allowing multiple ALU operations to be performed without committing the intermediate results to main memory, saving a write and subsequent read of each intermediate result." The sources give no encoding or latency for the mesh. **opentsp:** each VXM source operand has a chain bit (bits 21, 20 and 19 of the word for the first, second and third source; a bit for an operand the instruction lacks is reserved and must be zero). In assembly the operand carries a `.chain` suffix: `add.i8 E:12, E:8.chain, E:8.chain`. A chained operand reads the result written at the VXM station in the previous cycle (§2); an ALU on queue q₂ dispatched at t₂ consumes the result of an ALU dispatched at t₁ on queue q₁ when its read cycle is the cycle after that commit: t₂ + d_skew = t₁ + d_func + 1, so t₂ = t₁ + d_func − d_skew + 1 (ref: t₂ = t₁ + 4). All 16 ALUs share one station, so without the bit a result written there flows away from every other ALU. The bit must be explicit because an implicit bypass changes published programs: an unchained read keeps the flow rule, so ISCA20 Listing 1 (`z = g.add(x_strm, y_strm, stream='S_0')`, a destination equal to a source, issued on consecutive cycles) reads fresh operands every cycle, and a VXM result on a stream does not replace the operand of another ALU reading that stream. The intermediate still passes the station on its stream, so a downstream unit could read it; it never needs a MEM write and read. The chain length is unbounded, and one ALU per step keeps the throughput at one vector per cycle per chain (16 queues). Tests: `test_vxm_alu_chain_gelu`, `test_vxm_alu_chain_timing`, `test_vxm_unchained_read_ignores_station`, `test_vxm_chain_encoding` (`unit_tests/test_vxm_mxm.sail`) and the `h1` section of `test/directed/directed.py` (Listing 1, `rep 54, 1`, cross-queue).
- **Reduce accumulation order is an OpenTSP choice.** The sources name a superlane reduction but give no order or rounding rule. opentsp folds each superlane g in ascending lane order: acc = lane 16g, then acc = op(acc, lane 16g + j) for j = 1..15, and writes acc to lane 16g. For floats each step rounds to nearest even in the element type, so the order is observable: f32 lanes [1.0, 1.0, 0 × 13, 2²⁴] give 2²⁴ + 2 (0x4b800001), not 2²⁴ (descending order). Integer add wraps at each step (the result is the same in any order); Max and Min follow the NaN rules above. Tests: `test/directed/directed.py` ascending-lane Reduce checks and the Python `reduce_order` template.
- **Multi-byte operands:** an f16 or 16-bit operand uses two consecutive streams s, s+1 (s even); a 32-bit operand uses four (`topology.md` §3).

## 6. MXM (`slices/mxm/*`)

**Planes:** `mxm.planes_per_hemisphere` per hemisphere, two on `ref` and `mini` (four planes: 0 and 1 west, 2 and 3 east; the plane of an east queue is `mxm.planes_per_hemisphere` plus its index in the hemisphere). The queue map is fixed (3 queues per plane at 104 to 115, `topology.md` §5), so the key takes 1 or 2: with 1 the second plane of each hemisphere does not exist, its queues (107 to 109 and 113 to 115) report OTS-E-QUE-002 as the queues of an absent MEM slice do, the matrix registers have two planes (0 west, 1 east), and **no plane can hold f16**, because an f16 pair (planes 2i and 2i + 1 of a hemisphere) exists only in a hemisphere with an even number of planes (an f16 LW, IW or ABC is OTS-E-RES-001). More planes than the queue map names need more queue ids, an encoding break that is not part of this version. Each plane holds:
- a weight buffer (filled by LW);
- the installed weights;
- the list of its ABC results;
- **`mxm.acc_depth` accumulators** (2 on `ref` and `mini`, the published MACC has two 32-bit accumulators; 2 to 32).

**Weight types:**
- **i8, u8:** a matrix of `mxm.rows` rows × `vlanes` columns on any plane (`mxm.rows` = 320 on `ref`, so 320 × 320; 16 on `mini`, so 16 × 16). The weight buffer and an installed matrix hold `mxm.rows` stream values.
- **f16:** one `mxm.f16_rows` × `vlanes` matrix **per hemisphere**: 160 × 320 on `ref` (`mxm.f16_rows` = `mxm.rows`/2; HC34 p.28), or 320 × 320 when `mxm.f16_rows` = `mxm.rows` (both byte planes of the pair in tandem; ISCA20 §III-D). The key sets the **capacity** only, between `mxm.rows`/2 and `mxm.rows` in steps of 8 (the configuration check of every harness refuses a value outside that range); the f16 rate is `timing.mxm_abc.occupancy_f16`. The weight buffer and an installed f16 matrix hold 2 × `mxm.f16_rows` stream values (two per row). It uses the **even plane** of the pair (0 or 2).
  - An f16 LW, IW or ABC on an odd plane is OTS-E-RES-001.
  - While the even plane holds f16 weights or buffered f16 rows, every instruction on its odd partner (1 or 3) is OTS-E-RES-001.
  - An f16 weight row is a **stream pair**: stream 2i is the low byte and 2i+1 the high byte. So 16 streams carry 8 rows.

**Stage timing:** each stage needs the previous stage **committed** (dispatch + d_func), otherwise OTS-E-RES-001:
- IW needs the last LW committed;
- ABC needs IW committed (integer weights with an integer ABC of either sign, f16 with f16);
- ACC needs an ABC committed.

**Buffer and install:**
- **LW** appends 16 stream values to the buffer. More than `mxm.rows` (i8, u8, fp8) or 2 × `mxm.f16_rows` (f16) is OTS-E-RES-002 (so `mxm.rows`/16 LWs fit: 20 on `ref`, 1 on `mini`; an f16 LW fits 2 × `mxm.f16_rows`/16, also 20 on `ref`; an i8 or u8 LW appends 16 rows and an f16 LW appends 8). Appending rows of another type to a non-empty buffer is OTS-E-RES-001.
- **IW** installs the buffer, or 16 streams directly (`iw.t src`, appending rows; ISCA20 Table I "from streams or LW buffer").
  - The first stream install after reset, a buffer install, or an ABC dispatched after the last stream install starts a new matrix.
  - IW from the buffer needs a non-empty buffer whose rows have the IW's type (else OTS-E-RES-001), and it empties the buffer. A stream install into an open matrix of another type is OTS-E-RES-001, and more than `mxm.rows` stream values (f16: 2 × `mxm.f16_rows`) in the matrix is OTS-E-RES-002.
- **Unit-state parts each instruction changes** (staged, §1): LW the buffer; IW from the buffer the installed weights **and** the buffer (so an LW and an IW from different queues that change one plane's buffer in one cycle are both OTS-E-RES-003); IW from streams the installed weights; ABC the ABC results; ACC accumulator a (each accumulator is a part of its own); LoadMap and LoadMapWide their map, with its bijective flag and ready cycle (§7).

**Several changes from one queue.** The RES-003 collision rule above compares different queues. Different operand skews can make two instructions dispatched on one queue in different cycles execute in the same cycle. Their staged values are computed from the unit state at the start of that cycle. The flush applies stages in reverse staging order, so the earliest staged change to each identical part remains; changes to other parts still apply. This is distinct from the cross-queue collision, which discards all staged changes of each conflicting queue (§1).

**ABC** computes product[r] = Σ_k W[r][k] · x[k]. f16 activations use two consecutive streams (low, high byte).
- **i8 / u8:** exact, with 32-bit wrap.
  - **Mixed signs** (: signed × signed, unsigned × signed, signed × unsigned, unsigned × unsigned). The **installed weight type** (i8 or u8) gives the weight sign and the **ABC type** gives the activation sign. So `abc.u8` on i8 weights is signed weight × unsigned activation, and `abc.i8` on u8 weights the reverse. *opentsp:* the published sources do not say how the multiplier mode is selected, and the two existing type fields express all four modes without a new encoding. f16 weights need an f16 ABC and vice versa, and so for bf16 (OTS-E-RES-001).
- **f16:** the exact sum of the exact products, rounded **once** to f32 (round to nearest even; ISCA20 §III-D, "a single rounding step").
  - Any NaN operand, Inf × 0, or +Inf and −Inf products together give the canonical NaN. Otherwise an infinite product gives that infinity.
  - An exact zero sum is −0 only if every product is −0.
  - Overflow rounds to infinity.
- **bf16 (the profile extension `bf16`, implementation choice):** `mxm_wtype` 4, a 3-bit value (bit 12 above bits 21..20, which are zero), declared by `lw.bf16`, `iw.bf16`, `iws.bf16` and `abc.bf16` and decoded only in a profile that names the extension (§5); bit 12 with bits 21..20 = 01 is `bfp8` (type 5, declared by `block_fp8`, §6.1), and the other values of bit 12 with a nonzero type are reserved (OTS-E-DEC-003), and bit 12 of ACC stays the accumulator select. **The capacity, the plane pair, the stream pairs and the rate are those of f16** (a row is two streams, low and high byte; `mxm.rows`/2 rows per matrix; the even plane only, its odd partner busy; one ABC per `timing.mxm_abc.occupancy_f16` cycles): `ABC` has the one timing row for both. The product is the exact sum of the exact products rounded **once** to f32, with the special values of f16 (NaN operand, ∞ × 0, +∞ and −∞ products: the canonical f32 NaN; −0 only if every product is −0). Every product is a multiple of 2⁻²⁶⁶ and below 2⁵²², so the model's integers are exact; a hardware unit needs an accumulator of about 530 bits or an exponent-aligned one (an f32 accumulation is not equal to this rule: `[2¹²⁷, 1, −2¹²⁷] · [1, 1, 1]` is 1, not 0). bf16 weights need a bf16 ABC and the reverse (OTS-E-RES-001); `acc.f32` is the accumulate form, as for f16. The sum check of §18 runs on bf16 in the same exact integers.
- **FP8 (implementation choice, `abstractions.fp8_format`):** the weights are installed as bytes with `lw.fp8`, `iw.fp8` or `iws.fp8` (`mxm_wtype` code 3; `LW`, `IW` and `IWS` take it like i8/u8/f16) and the activation is multiplied by `abc.e4m3 s` or `abc.e5m2 s` (catalogue entry `ABC8`: type 3 with bit 13 selecting the format). **One format selects both operands:** the installed weights and the activations are in the format of the ABC; a weight of one FP8 format with an activation of the other would need a third and a fourth multiplier mode, which no source asks for. The weights themselves carry no format tag, as an i8 weight carries no sign tag beyond its type: the ABC names the format in which the bytes are read.
  - The dot product is the exact sum of the exact products (every FP8 product is a multiple of 2⁻¹⁸ in e4m3 and 2⁻³² in e5m2, so the 320-term sum is exact in the model's integer arithmetic), rounded **once** to f32. The special values follow f16: any NaN operand, ∞ × 0 (e5m2), or +∞ and −∞ products together give the canonical NaN of f32; otherwise an infinite product gives that infinity; an exact zero sum is −0 only if every product is −0. An e4m3 operand has no infinity, so an e4m3 product is always finite or NaN.
  - **Capacity and rate are those of i8 by default** (320 rows, one ABC per cycle, 20 cycles): an FP8 weight occupies one byte-plane element. Giving FP8 the integer capacity and timing is an opentsp resource assumption, not a published FP8 circuit result. **`mxm.fp8_rate`** (1 on `ref` and `mini`, or 2) is the number of FP8 ABCs a plane accepts in one cycle, relative to INT8: with 2, two `ABC8` of one plane from two queues in one cycle both execute (decision of: the published sources give no FP8 circuit, and a doubled rate that keeps the stream widths is two activation vectors per cycle). A third ABC of the plane in that cycle, or an ABC of another type together with an `ABC8`, is OTS-E-RES-003 on every queue involved, as two ABCs are with rate 1. The plane then keeps two products of the same dispatch cycle; an `ACC` takes the one of the lower queue when its accumulator index is even and the one of the higher queue when it is odd (so two ACCs of one cycle on accumulators 0 and 1 drain both products). With a single ABC of the cycle the ACC rule below holds unchanged. Rate 1 profiles behave as before. `ABC8` has its own catalogue row (class `mxm_abc`, 20, 0) so that `timing.overrides` can name it; an override of `ABC` does not move `ABC8`. The result is an f32 product, so `acc.f32` is the accumulate form (`acc.i32` after an FP8 ABC is OTS-E-OPR-001), and the accumulator holds f32 as for f16.
  - **Type rules (OTS-E-RES-001):** FP8 weights need an FP8 ABC and an FP8 ABC needs FP8 weights, as f16 weights need an f16 ABC and the reverse. The bit 13 of an ABC of type 0, 1 or 2 is reserved and must be zero (OTS-E-DEC-003 otherwise).

**Arithmetic modes and physical boundary.** Installed weight type and the ABC operand type select integer (the four i8/u8 sign combinations), FP16, or FP8 arithmetic; there is no mode register. FP16 storage reserves an even/odd plane pair, and FP8 storage uses byte rows. ISCA20 §III-D describes byte planes operating in tandem for FP16, but that does not establish the number of primitive integer multipliers needed for each exact FP16 product. Sail computes exact products/sums and the specified rounding; it is not a gate-level implementation of mantissa multiplication, exponent alignment or reduction. FP8 throughput and the type-selection interface are opentsp choices. Unsupported weight/activation combinations report OTS-E-RES-001. Unit tests, directed FP8 tests and the independent arithmetic oracle check the functional contract; they do not prove its area, clock period or energy.

Each ABC adds an entry (dispatch, commit, type, product) to the plane's list. Product lane r is the dot product of installed row r; lanes at or beyond the installed row count are zero. An ABC produces `mxm.rows` lanes: a lane at or beyond `mxm.rows` is zero, and so is a lane at or beyond `vlanes` (the lanes of the vector the product is written to). On `mini` `mxm.rows` = `vlanes` = 16, so every row is observable and none is hidden.

**f16 MACC throughput and capacity.** The sources disagree on the f16 capacity (160 × 320 in HC34 p.28, 320 × 320 in ISCA20 §III-D, two byte planes in tandem); `mxm.f16_rows` selects either as a profile (`ref` and `mini` use half the rows). The published sources describe two INT8 320×320 matrices per hemisphere, one FP16 160×320 matrix per hemisphere, and quarter-rate FP16 arithmetic capacity (HC34 p.28; ALCF24 p.25). TPACC p.5 explicitly describes a 320-element fused dot product with single rounding in its FP16 discussion. This specification uses 160 output rows and 320 input elements per FP16 matrix, reserving the partner byte plane. Reference and mini profiles set `timing.mxm_abc.occupancy_f16` to **1**: each paired FP16 matrix can accept one ABC per cycle. Consequently the reference chip has two ×160×320 FP16 MACs/cycle versus four ×320×320 INT8 MACs/cycle. The comparison includes both hemispheres and all four planes; a one-plane comparison alone omits the pair reservation.

The 320-element reduction has direct source support. The mapping of matrix axes to output lanes and the one-cycle initiation interval are an engineering reconciliation of the published shape, density, pipelining and arithmetic rate. ISCA22 §5.2 instead describes K=160 FP16 suboperations; §5.5 describes 160×320 matrices and ABᵀ. No inspected author correction explains that difference. The specification does not assert exact commercial circuit or binary equivalence. The source comparison and alternatives are recorded in; `isa-db/provenance.yaml` labels the inference explicitly.

Research profiles may choose a larger `occupancy_f16`; their rate is then lower and must not be described as quarter-rate. During that occupancy an ABC on the busy plane reports OTS-E-RES-001; the queue is not otherwise held. `test/directed/execution_contract.py` checks actual accepted issues across all four reference planes, and `test/directed/timing_rows.py` checks configurable occupancy and installed rows.

**ACC** uses the **newest ABC result committed at or before its dispatch cycle**. With none, it is OTS-E-RES-001. So ABC and ACC pipeline: an ABC dispatched while an earlier product is being accumulated does not disturb it.
- ACC sets accumulator a (0 to `mxm.acc_depth` − 1; the index is bit 12 as its low bit and bits 11 to 8 above it, so every word with the index 0 or 1 keeps its meaning; an index at or above the depth is OTS-E-DEC-003 like a reserved bit) to the product (replace), or adds the product to it (accumulate: i32 wrap, or one f32 add). Its type must match the product: `acc.i32` needs an i8 or u8 product and `acc.f32` an f16, bf16, FP8 or bfp8 product, else OTS-E-OPR-001. `acc.x128` (extension `wide_acc`, §6.1) needs an f16, FP8 or bfp8 product (a bf16 sum is in units of 2^-266, which the wide accumulator cannot hold). The accumulator changes only when the result can be written.
- The result is written as 4 byte-plane streams.
- **One accumulator vector per accumulator.** Each accumulator holds one 320-lane vector (two 32-bit accumulators per MACC in the shipped profiles). Accumulating a dot product longer than 320 over several activation rows therefore keeps at most `mxm.acc_depth` rows in the accumulators (two on `ref` and `mini`); the others go through a stream and the VXM or MEM between partial sums. The sources do not settle the depth (`abstractions.mxm_accumulator_depth`): `mxm.acc_depth` is the profile choice, 2 to 32.

### 6.1 Optional extensions: the wide accumulator and block-scaled fp8 (`slices/mxm/*`, `core/geometry.sail`)

The three optional extensions are disabled in `ref`, `mini`, and the published-chip profiles. A profile declares each one by name in its `extensions` list (`"bf16"`, `"wide_acc"`, `"block_fp8"`; the list is a required key, empty in `ref` and `mini`; a name that is not an extension of this version, or one listed twice, is a configuration error) and the decoder rejects the encodings of an extension the profile does not declare, exactly as it rejects any unassigned encoding (the text decode reports OTS-E-DEC-003 at the word, an assembler refuses the name). Every addition is an **implementation choice** (`isa-db/provenance.yaml`: `mxm.acc_bits`, `extensions`, `wide_accumulator`, `block_fp8_format`): the published sources give 32-bit accumulators and name neither a wider accumulator nor a block format.

**The wide accumulator (`wide_acc`, key `mxm.acc_bits`).** `mxm.acc_bits` is 32 or 128, and 128 exactly when `extensions` lists `wide_acc` (`timing_config_error` checks the pair; so does the Rust profile check). With the extension an ABC of a floating-point type (f16, fp8, bfp8) keeps, besides the f32 product, the **exact** sum of the exact products of each row as a signed integer in units of 2^-48 (a NaN, an infinity or an infinity times zero keeps a special value instead, as the f32 product does). The new accumulator type `x128` of ACC (type code 0; the codes 2 and 3 keep i32 and f32) takes that exact value: replace stores it in accumulator a (the index of §6, bit 12 and bits 11 to 8), accumulate adds it to the accumulator's lane in exact integer arithmetic that **wraps at 128 bits** (two's complement; unreachable by 2^38 accumulations of f16 products, whose sum stays below 2^91 units). A special value is sticky in the lane: NaN, or +Inf plus -Inf, gives NaN; an infinity stays infinite; the read-out gives the canonical f32 NaN and the f32 infinities. A zero lane is -0 only when every term added was -0. The stream result of ACC `x128` is the **read-out of the lane after the update, rounded once to f32 (round to nearest even)**; the lane itself stays exact, so no accumulation step rounds, and the sum of any number of ABCs is rounded once, when it is read. The result of a replace equals the f32 ABC product (the same exact sum rounded once). An integer (i8 or u8) ABC has no wide form: ACC `x128` after it is OTS-E-OPR-001, as `acc.f32` after it is. A bf16 ABC  has none either: its exact sum is in units of 2^-266, which a lane of 2^-48 units cannot hold, so ACC `x128` after a bf16 ABC is OTS-E-OPR-001 (`acc.f32` follows it). The wide accumulators are `mxm.acc_depth` further vectors per plane (one per accumulator index, lane count `mxm.rows`), separate from the 32-bit ones: `acc.i32` and `acc.f32` keep using the 32-bit ones, so a program may mix the forms. Poison (§15) follows the accumulator index for both forms: the poison mask of accumulator a belongs to the last ACC that wrote it, whichever type. The staged part is accumulator a (§1), so two ACCs on one accumulator in one cycle clash whatever their types. Timing and the ECC and check paths are those of `acc.f32` (the ACC row, `mxm_acc`).

**Block-scaled fp8 (`block_fp8`).** The type **bfp8** (LW, IW, IWS and ABC; type code 5: the **type extension bit 12 set** with bits 21..20 = 1, the 3-bit type being bit 12 @ bits 21..20, so i8 0, f16 1, u8 2, fp8 3, bf16 4 (bit 12 set, bits 21..20 = 0) and bfp8 5; bit 12 is zero for every other type and is reserved zero in an ABC8) is a **stream pair**, like f16: the first stream value of the pair holds **e4m3** elements and the second the **block scales**. A block is the 16 lanes of one superlane (a profile with S superlanes has S blocks; the stream is the unit). The scale of a block is the **low four bits of the byte at the block's first lane** read as a two's-complement exponent -8..7; the upper four bits and the bytes of the other 15 lanes are not read. The value of lane k is its e4m3 element times 2 to the power of the scale of its block. The storage, plane and rate rules are f16's: a weight row takes two stream values (the data row 2r and the scale row 2r + 1 of the buffer, `mxm.rows / 2` rows per plane), bfp8 runs on the even plane of a plane pair and blocks the odd one, an ABC with an activation pair reads streams s and s + 1, and the plane's MACCs are held `timing.mxm_abc.occupancy_f16` cycles. bfp8 weights need a bfp8 ABC and the reverse (OTS-E-RES-001, as for f16 and fp8). The products and their sum are exact (units of 2^-48; an e4m3 product is at least 2^-18 and the scales move it by 2^-16.. 2^14, so every product is a multiple of 2^-34) and rounded once to f32, as the f16 and fp8 forms; an e4m3 NaN gives the canonical NaN, e4m3 has no infinity, a zero sum is -0 only if every product is -0. The matrix check (§18) works on the exact value of every element including its scale (a bfp8 sum stays below 2^74 units of 2^-34, inside the 96-bit sums). `acc.f32` and `acc.x128` follow a bfp8 ABC; `acc.i32` does not (OTS-E-OPR-001). The four-bit scale range, instead of the eight-bit power-of-two scale of published microscaling formats, keeps the exact sums inside those 96 bits; a wider scale is left to a later extension.

## 7. SXM (`slices/sxm/*`)

- **Per hemisphere** (HC34 p.31): 4 distributors, 2 transposers, 2 shifters, 1 permuter, 1 select. Each SXM holds 16 maps of 320 ten-bit entries, which start as the identity.
- **Shift** moves lanes up or down across the vector, with zero fill. The amount is at most `vlanes − 1` of the profile.
- **Timing of Shift and Permute.** A source superlane can lag the output superlane by up to `superlanes − 1` cycles. Requiring one processing cycle after its arrival gives `d_func − d_skew >= superlanes`. Both effective rows, including overrides, obey this bound. Their reference rows use 20/0; this is a causal lower bound chosen for the model, not a measured permutation circuit delay. It is a **minimum** that ignores intra-chip transport: an implementation that cannot move a lane over `superlanes - 1 - k` tiles in `1 + k` cycles declares a larger `d_func` for these rows under the profile rule (§12). Distribute, Rotate, SelectS and map-loading operations use their documented superlane-local semantics and configured timing. Transpose has its own row (5/0 in shipped profiles), an implementation choice; the model reads its 16 input streams at the same superlane-0 execution time.
- **sxselect a, b, c, sel, dst** (the select unit; ISCA20 Fig. 8). Per lane, sel 0, 1 or 2 picks a (unshifted), b (north-shifted) or c (south-shifted). A lane whose sel is above 2 is zero, the other lanes are selected and written, and the instruction reports **one** OTS-E-OPR-001 (each lane acts alone, an exception to "a diagnostic means no effect", §8). With two shifters it forms the north/south shift of Fig. 8. The mnemonic differs from the VXM's `select`.
- **Permute** applies a map: output lane l takes input lane m[l], or zero when m[l] ≥ `vlanes` (a masked lane). Masked entries may repeat; the entries below `vlanes` must be distinct, i.e. the map must be **bijective** (OTS-E-SXM-001, see "Map readiness" below). **Distribute** remaps within a superlane, or zero-fills.
- **Mask operand of Distribute and Permute: opentsp decision.** HC34 p.31: "Distributor: 4 per hemisphere perform unto mapping of input + mask to output stream within a 16 byte superlane … Permuter / Shifter: arbitrary mapping of input + mask, shuffling between 320B vector elements". The sources give no mask operand, encoding or semantics. In opentsp the mask is part of the map: a Distribute map entry ≥ 16 zero-fills its output lane (the masked lanes). A Permute map entry ≥ `vlanes` does the same for a Permute output lane, so both units take the "input + mask" of the source. The entries below `vlanes` must be distinct, and that is the published statement, not a narrowing of it: ISCA20 Table I "Permute map: Bijective permute 320 inputs → outputs", ISCA20 §III-E "a programmed bijection to remap the 320 lanes" and HC34 p.25 say bijection, while "arbitrary mapping of input + mask" on HC34 p.31 is the caption of the combined Permuter / Shifter box. A repeated source lane on the permuter is OTS-E-SXM-001 (Distribute is the unit that fans a lane out); only the masking of the entries at or above `vlanes` is the specification's own. No separate mask stream is encoded. Test: `test/directed/directed.py` "h1 ".
- **LoadMap** and **LoadMapWide** fill a map. They are staged like MXM state (§1). The map-loading mechanism is unpublished, so these are an opentsp decision.
- **Map readiness: decision.** A check of all 320 lanes at the Permute would read lanes of superlane k at k cycles after superlane 0 (`topology.md` §3), and could not be made in the Permute's own cycle. So the check is made when the map is loaded and the Permute only reads its result:
  - LoadMap and LoadMapWide record with the map whether it is **bijective** (its entries below `vlanes` are distinct; entries ≥ `vlanes` are masked and may repeat) and the cycle from which a Permute may use it: **the execute cycle of the load + `timing.sxm_map_ready`** (`geometry.superlanes` in `ref` and `mini`). A load that takes effect (not RES-003) replaces both; the clock restarts at every load of the map.
  - A **Permute that executes before** the map's ready cycle is **OTS-E-RES-001** (map not ready) and has no effect. A Permute with a map that is **not bijective** is **OTS-E-SXM-001** and has no effect. The two are evaluated in that order.
  - A Permute that executes in the execute cycle of a load, or later but before the new ready cycle, therefore sees the old map's flag and ready cycle: the map's value, flag and ready cycle change together, at the end of the load's cycle (§1 step 6), so the result does not depend on the order of the queues.
  - **Distribute is unchanged, and needs no readiness rule (resolved, the premise does not hold).** It is superlane-local (class `sxm`): every lane reads only the map entries and the data of its own superlane, which the stagger (`topology.md` §3) delivers to that superlane together. The map register is written at the end of the load's cycle and is usable from the next cycle, so a Distribute that executes in the load's own cycle reads the old map and one a cycle later reads the new map; nothing in this is racy in hardware, and no published source states a rule for it. A diagnostic would be an invented rule, so there is none, and the one-cycle gap is legal. A Permute differs because its map must physically reach all superlanes before it can be read (this, above). A Distribute has no flag (every entry is legal). The boundary is pinned by the directed test "" (`test/directed/directed.py`): the old map in the load's cycle, the new map the next cycle, no diagnostic.
  - The reset maps are the identity: bijective and ready (ready cycle 0).
  - **Why `superlanes`:** it is the distance the stagger puts between the first and the last superlane to have supplied an entry (ISCA20 §II: "The data for successive 16-element superlanes are lagging by 1 cycle"; **derived**); the existing relation `geometry.superlanes` ≤ `timing.sxm_cross.d_func` bounds the Permute's own latency by the same number. The delay is the profile key `timing.sxm_map_ready`, whose default in `ref` and `mini` is the superlane count; a profile may set any value from 1 to 63.
- **Rotate src, n, dst** (n = 3 or 4) produces n² streams. In each superlane g, lanes 0..n²−1 of the source form an n × n tile, row r at lanes r·n..r·n+n−1. Output t = tr·n + tc (t = 0..n²−1) goes to stream dst + t and holds the tile cyclically shifted by tr rows and tc columns: lane 16g + r·n + c = source lane 16g + ((r + tr) mod n)·n + (c + tc) mod n, for r, c < n; every other lane is zero. It is a cyclic 2-D shift of the tile, not a geometric rotation. dst + n² > 32 is OTS-E-OPR-002.
- **Transpose src, dst** turns 16 streams into 16 (bases 0 or 16): output c, lane 16g + r = input r, lane 16g + c. The 16 input streams are read in one cycle, like the 16-stream groups of LW and IWS, and the 16 outputs commit together at d_func (5, an implementation choice). A bound of 16 would follow only if the inputs arrived one per cycle, which no published source states; a profile that models that sets the Transpose row to 16.
- **Turn-out and the OR.** TSP, SHF, PRM and SEL write the other row at gap 4, i.e. into register 5. HC34 p.31 draws the SEL and TSP outputs entering register 5 through an OR, so a SEL write and a TSP write of the same hemisphere to the same stream in the same cycle merge by bitwise OR (§2) instead of reporting SRF-002; PRM and SHF do not feed the OR and still collide. A program can use this to combine a selected vector with a transposed one in one cycle, for example when the two have disjoint non-zero lanes.

## 8. Diagnostics (`core/diagnostics.sail`)

A diagnostic is reported as `(cycle, queue, code)`. The control channel reports as queue 65535.

**Effect of a diagnosed instruction.** A diagnostic does not by itself mean that no result exists. Dispatch still consumes text and updates scheduling state according to the queue rules. For execution effects, apply the table below and the detailed integrity rules in §§15–17. Ordinary operand/resource failures suppress the affected instruction result, except for the three OPR-001 cases with explicitly partial tile/lane results. Integrity diagnostics can accompany poisoned output and RAS side effects. Consumers must propagate that poison rather than treating the output as absent.

| Instruction | Effect when it reports | What takes effect |
|---|---|---|
| `gather` | per tile | a tile with an address outside the segment or the slice drives zero on its lane; every good tile drives its lane; the instruction reports one OTS-E-OPR-001 |
| `scatter` | per tile | a tile with an address outside the segment writes nothing; every good tile writes its lane of its word, in ascending tile order; the instruction reports one OTS-E-OPR-001 |
| `sxselect` | per lane | a lane whose sel is above 2 is zero; every other lane is selected and written; the instruction reports one OTS-E-OPR-001 |
| OTS-E-ECC-001 | poisoned or partially usable data and RAS effects, per §15 | consumers may still write results carrying poison; logs, counters and interrupts can change |
| Receive reporting OTS-E-LNK-004 | the received vector is still written, per §17 | affected superlanes carry poison; link/RAS state records the error |
| other execution operand/resource failures | the affected payload/state update is suppressed | subject to the explicit commit/collision rules below; this does not roll back text consumption or earlier pipeline stages |
| a stream commit that collides (OTS-E-SRF-002) | the lowest writer's value is kept | it is the effect of the colliding writes, not of one instruction; the kept writer is the lowest queue (§1) |
| OTS-E-RES-003 | the clashing changes are dropped | none of the instructions that changed the same unit-state part in that cycle takes effect (§1 step 6) |

The three OPR-001 partial-result cases are marked `DIAG-EFFECT` in the Sail model and pinned by the directed tests of `test/directed/directed.py` (""); the same test checks that the markers, the header of `core/diagnostics.sail` and this table list the same three instructions. Directed tests of the sweep also pin "no effect" for a Permute (RES-001 and SXM-001), a Rotate, a VXM add and a Write.

| Code | Raised when | Queue | Class |
|---|---|---|---|
| DEC-003 | The instruction does not decode: tags 6 and 7, an unknown opcode, a reserved bit set, an illegal type or mode, or a word with bits 63..32 and no wide tag (`encoding.md` ("Word formats"); why the 64-bit patterns decode to one entry at most is argued in [`validation.md`](validation.md) §4, "This is the complete statement of the argument"). It takes its units from the IQ and has no effect | the instruction's queue | schedule (data for a unit fetched from SRAM) |
| QUE-001 | A parcel of two or more instructions that breaks the slot rule of §3: two instructions in one slot, a whole-queue instruction with another, an instruction that does not decode or a NOP among several; on a non-MEM queue, any parcel of two or more instructions (one report per instruction of the parcel). **This is the only meaning:** a busy, parked or held queue makes a parcel wait and reports nothing | the instruction's queue | schedule |
| QUE-002 | Instruction on a queue whose unit lacks it, including the control-channel restriction and every instruction on the queue of an absent MEM slice (§3) | the instruction's queue | schedule |
| IQ-002 | IQ overflow (§3): fetched text arrives at a full IQ (`icu.iq_depth`) and the units that did not fit are lost. Once per queue and cycle, by Enqueue; the lost units are the effect | the queue that overflowed | data (the fetched text decides how many units there are) |

**IQ underflow is a lint, not a diagnostic**: OTS-W-IQ-001 (the fetched text that completes the head parcel arrived after the parcel was due and the queue was free in the cycle, ISCA20 §III-A3; at the parcel's dispatch), reported through `lint_callback` and `tsp_sim --lint` as `T lint` lines (§12). A lint is non-normative: not an exception, not counted in the `E` line, not part of the golden vectors, and an implementation need not report it. `validation.md` §5 lists the lints and says how to add one. **IQ overflow is a diagnostic** (it was the lint OTS-W-IQ-002 ): the IQ lost fetched text, which changes the program of the queue, so every implementation reports it, and the lost units are the defined effect.

**Diagnostic classes** (decision of the RTL rule, `platform.md` §7.1). The last column of the table gives every code one class. A **`schedule`** code is raised by a rule that reads only the text, the configuration and the timing state of the machine (the host script and the traffic of other chips included): two runs of an object give the same `schedule` codes whatever the data, so it says that the object breaks a placement or scheduling rule, and a toolchain can check it before a run. A **`data`** code is raised by a rule that reads data values: the SRAM words and stream values, and the text of a fetch, whose units decode to whatever the fetched words are, so the DEC-003 of a fetched unit is a data event (the table class `schedule` of DEC-003 describes the text of the object itself). A **`fault`** code is raised only by an integrity event: it needs an injected or physical fault, never reads a program value, and reports an event that the chip also records in its error registers (§16). A data-dependent diagnostic removes an earlier instruction's effect (no stream write, no unit-state change, no fetched text), so later `schedule` codes of a run that raised a `data` code can differ from those of a run that did not; the class of a code is a property of its rule, and *well-formed* (the rule of `platform.md` §7.1) is decided on a run in which the object raises no `data` code. The ISS decides the same question with `tsp-iss verify`: exit 0 well-formed, exit 1 ill-formed, exit 3 data-dependent or not decided over the link latencies, with its domain for a manifest stated in [assembly, "Scheduling constraints"](assembly.md#scheduling-constraints) (exit 2 is an input error). What an RTL implementation must reproduce is defined once, in [`platform.md` §7.1](platform.md#71-rtl-conformance); this section and §12 define the model's and the ISS's exact output.

The class column is the single list; the ordered lists below place every code of the table (`tests/docs/test_rtl_rule_text.py` checks that the table, the reporting order and the check order name the same codes).

**Reporting order within a cycle:** golden vectors compare diagnostic lists exactly, so the order is part of the specification. It follows `tick`:
0. OTS-E-LNK-002 from the harness (§10), links in ascending order, one report per dropped vector; the harness reports it before it calls `tick` for the cycle (and a cycle in which a vector is dropped but nothing else happens is not ticked);
1. OTS-E-IQ-002 from Enqueue (a unit lost to a full IQ), queues 0..143 in ascending order and the control channel last (the delivery happens before the cycle's commits);
2. SRF-002 from the commits, in ascending queue order;
3. the execution diagnostics of the elements dispatched earlier whose execute cycle is this cycle (d_skew > 0), in dispatch order (the instruction's own codes: TIM-001, DIR-001, OPR-001, OPR-002, RES-001, RES-002, SXM-001, IQ-003, LNK-001, LNK-003, HIO-001, MEM-001 of an AGT reference);
4. the control channel (QUE-001, QUE-002, DEC-003, and ECC-002 of a lone control instruction, in the position of its decode step);
4a. OTS-E-ECC-001 is part of an instruction's execution report: it follows the instruction's own diagnostic, if any (§15), in the position of that instruction in steps 3 and 5; OTS-E-ECC-003 is part of an ABC's execution report in the same way (§18), after the ABC's own checks; the operand ECC events of an instruction (`T ecc`, §15) always precede its sum-check event (§16, §18); OTS-E-LNK-004 is part of a Receive's execution report (§17): it follows the Receive's checks (the Receive is issued, so it has no diagnostic of its own) and precedes an OTS-E-ECC-001 of the same instruction, which a Receive cannot have;
5. queues 0..143 in order; within a queue, the lint OTS-W-IQ-001 first (if the head parcel arrived late; `--lint` only), then in the order of "Order within a queue's cycle" below (an element with d_skew = 0 reports its execution diagnostics there); the dispatch checks QUE-001, QUE-002, DEC-003, ECC-002 and MEM-001 report at the dispatch cycle of the parcel, ECC-002 in the decode step of the check order;
6. RES-003 from the flush, in ascending queue order;
7. OTS-E-IQ-004 from `model_finish`, after the last cycle: queues in ascending order, the control channel last (an end-of-run record: it follows every run-time record, §12; in the chip it is appended at quiescence and is not ordered by its stamp, [`platform.md` §5](platform.md#5-hardware-time)).

OTS-E-IQ-002, OTS-E-IQ-004, SRF-002, LNK-002 and RES-003 belong to the cycle or to the run, not to one instruction; they have a place in this list only. Every other code of the table is also placed in the check order below.

A dispatch check reports at the dispatch cycle, which is the cycle the parcel dispatches (not the cycle it was due, when it waited); an element's execution (an operand, SRAM or unit-state diagnostic) reports at its execute cycle, dispatch + d_skew (+ k for AGT reference k). An AGT reference or Repeat iteration is dispatched at the cycle it issues.

**Check order per (queue, cycle)** (`parcel_held`, `hold_check`, `dispatch`, `classify`, `decode_k`, `dispatch_check`, `dispatch_slots` and `control` in `postlude/tick.sail`). A parcel first **waits** until it is due and complete and nothing holds it (the hold conditions of §3; no report). When it dispatches, the first step that applies decides; later steps are not evaluated, so **one** instruction yields at most one code from steps 2 to 6. Each rule is pinned by a directed test (`test/directed/directed.py`, section "diagnostics", tests `R1.n`).

**Pure helpers (structure only, no behaviour).** The decisions of the cycle driver are written as functions of explicit values, so that each can be tested and proved without the machine state, and the code that reads or writes the registers is a thin wrapper around them: the hold decision (`hold_decide` over a `hold_view` of the queue flags and the two paths; `hold_check` and `free_at` build the view from the registers), the bank rule of one queue and cycle (`bank_rule` over the `(thread, bank)` tags of the new references, of the AGT references due and of an IfetchM), the port reservation (`path_hold_until`, `fetchm_hold_until`, `fetchm_bank_note`), the AGT updates (`agt_configure_pure`, `agt_refresh_pure`, `agt_finish_config_pure`, `agt_due_pure`, `agt_after_reference`, `agt_opened`, `cfg_path_pick`), the Repeat plan (`repeat_plan`, `repeat_after`), the commit arbitration of one cycle (`commit_scan`, `commit_wins`), the patrol scrub arbitration (`scrub_arbitrate`, `scrub_slot_taken`, `scrub_due_count`) and the slot operations of the stream register file (`srf_slot_write`, `srf_slot_read`, `srf_slot_read_ov`, `srf_slot_best`, `srf_slot_collides`, `srf_slot_chain_ov`, `srf_slot_flip`, `srf_stream_only_downstream`, `srf_rep_merge` in `core/streams.sail`; `srf_write`, `srf_read` and the other register file functions choose the slot and store the result). The cycle driver `tick` calls `tick_queue` for each data queue, and none of its list walks is a `while` loop: they are structural recursions over the list, or `foreach` over an explicit bound (the patrol scrub counts its due cycles with `scrub_due_count`). Traces, cycle counts and the golden vectors are identical to those before this restructuring.

For a **data queue** q at the cycle c in which its head parcel dispatches, with k instructions:
0. **Wait** (no report). The parcel dispatches at the first cycle ≥ its due cycle at which it is complete and not held (§3, "Dispatch or wait"): the queue is not parked (not for the queue's own Sync and Notify), not busy (Deskew, RuntimeDeskew, an AGT reference or Repeat iteration issued this cycle), no Repeat is pending, and the path the instruction needs is neither busy, in a loop's tail, running a loop, nor configuring (unless the instruction is a configuration instruction); an instruction that needs the whole queue needs both paths to be so, a path with an open configuration included (test `test/directed/frontend.py` section 12b, Sail `test_frontend_whole_queue_open_config`). A parcel is held if any instruction of it is. A parcel that breaks the slot rule, or has an instruction that does not decode, or is a lone instruction that does not decode, is held by the whole-queue conditions only.
1. **IQ underflow (a lint, not a diagnostic).** If the parcel arrived late (§3, "Underflow"), the lint OTS-W-IQ-001 for the queue (no diagnostic, no effect on the checks below); the parcel still dispatches. (`test/directed/frontend.py`, "underflow")
1a. **Absent slice** (q is the queue of an absent MEM slice, §3; any k ≥ 1; right after the underflow check and before steps 2 and 3, so neither a slot-rule violation nor an undecodable word is reported as itself) → QUE-002 for each of the k instructions, and nothing else.
2. **Slot rule** (k ≥ 2). On a MEM queue, if every instruction decodes and the instructions fit the slots of §3 (at most one Ifetch/IfetchM; per liquid thread at most one R-type (Read, Gather) and one W-type (Write, Scatter) reference; at most one AGT configuration instruction (Countdown, Step, StreamStep, Iterations); no instruction that needs the whole queue; an IfetchM with no R-type reference of either thread), go to step 6. Otherwise, and on every other queue, **every** instruction is OTS-E-QUE-001 (k reports) and none dispatches. An instruction that does not decode, or whose text word is uncorrectable (ECC-002, §16.1), reports QUE-001, not DEC-003 or ECC-002. (`R1.1`; every accepted and rejected combination: directed tests `R1 slot rule: …`, `V-obligation count-09 …`)
3. **Decode** (k = 1): the instruction does not decode → DEC-003 (an undecodable instruction was held by the whole-queue conditions, so it reports at the cycle it dispatches); a text word of the instruction is uncorrectable → ECC-002 (the text check of §16.1 precedes the decode and substitutes its code for the decode result; the `T ecc... unc text` events of the parcel come first). (`R1.2`; ECC-002: `test/directed/ras_csr.py`)
4. **Unit** (the instruction is not issued by q's unit; k = 1) → QUE-002, also for a word the unit lacks that is busy-held earlier: the wait comes first. (`R1.5`)
5. **Slot group** (k ≥ 1 instructions that fit the slots): each instruction is checked on its own path (an Ifetch needs no path, an IfetchM needs the R path, a configuration instruction needs a configuring path: the holds of step 0 were applied to the parcel as a whole). Then, per liquid thread, a same-thread R + W pair in one bank or with an indirect reference is MEM-001 for each of the two, and neither runs; a new IfetchM and a Write of either thread in bank(a) are MEM-001 for each; in the following cycle its reserved read of a+1 rejects a conflicting later Write only (§3). References of different threads never clash. (`R1.7`, `R1 slot rule: …`)
6. **The instruction's own checks**: everything else (TIM-001, DIR-001, OPR-001, OPR-002, RES-001, RES-002, SXM-001, IQ-003 for a fetch whose staging is full, LNK-001 and LNK-003 for a Send or Transmit, HIO-001 for a PciSend), raised by the execution in the order of "Execution checks" below; at most one per execution. The integrity codes follow the instruction's own checks and are raised only for an instruction that was issued: ECC-001 for a stream operand or an SRAM word that is uncorrectable, LNK-004 for a Receive of a vector with an uncorrectable transfer, ECC-003 for an ABC whose sum check fails; ECC-002 is not here (it replaces the decode, step 3). RES-001 for a Repeat with nothing to repeat is raised here, at dispatch. AGT configuration instructions raise OPR-001 here, at dispatch (stray, fifth level). (`R1.8`)

**Order within a queue's cycle** (`tick`, `dispatch` and `dispatch_slots` in `postlude/tick.sail`). For queue q in cycle c, after the OTS-W-IQ-001 lint of a parcel that arrived late (§3) and the configuration end of §1 step 5:
1. The Repeat iteration due on q (not while q is parked) executes.
2. If the queue has no parcel to dispatch (none due, incomplete or held), or its parcel does not fit the slots (step 2), or it is one instruction that needs the whole queue: the AGT references due on q execute, R path then W path (two references of one thread that clash in a bank are MEM-001 each), and then the parcel: QUE-001 for each instruction of a parcel that does not fit, the DEC-003 of a lone undecodable instruction, or a lone instruction's step 4 and its execution.
3. Otherwise (a MEM-queue parcel that fits the slots, step 5), in this order:
   - (a) the fetch instruction (Ifetch or IfetchM): its dispatch checks; an Ifetch then executes, an IfetchM waits for (e);
   - (b) the configuration instruction: its dispatch checks and its own OPR-001 (stray, fifth level, §4);
   - (c) each reference instruction's dispatch checks, in slot order: R thread 0, R thread 1, W thread 0, W thread 1;
   - (d) the bank rule is evaluated (no report yet);
   - (e) the IfetchM: MEM-001 if it clashes, else it executes;
   - (f) the AGT references due, R path then W path: MEM-001 if blocked, else they execute;
   - (g) the reference instructions that passed (c), in slot order: MEM-001 if they clash, else they execute.

"Executes" means the element runs at once when its d_skew is 0, and reports its execution diagnostic (rule 8) at that point; with d_skew > 0 it runs, and reports, in step 3 of its execute cycle (§1), in dispatch order.

**Execution checks** (rule 8). Two operand rules are used throughout:
- **Read** of a w-stream operand at stream s (w = 1, 2 or 4, or a 16-stream group): no read gap for the issuing unit on s's row → DIR-001; s not aligned (s mod w ≠ 0 or s + w > 32; a 16-stream group's base is 0 or 16 by encoding) → OPR-002; then, over the w streams, a stream whose live writes are all at or downstream of the reader → DIR-001, else a stream with no value visible at the reader's gap in that cycle → TIM-001 (DIR-001 on any stream takes precedence over TIM-001 on another; §2). A chained VXM operand with no write at the station in the previous cycle → TIM-001.
- **Write** of a w-stream result: no write gap for the issuing unit on the row → DIR-001; misaligned → OPR-002.
- **ECC** (§15): a read that passes the checks above also checks the operand's check bits, superlane by superlane. A single-bit error is corrected for the reader (`T ecc corr`); an uncorrectable superlane marks the instruction's result poisoned there and the instruction reports OTS-E-ECC-001 after all of its own checks, only if it was issued (a diagnosed instruction has no effect, and its operand findings are still traced).

An execution evaluates its checks in the order below and reports the first that fails, with no effect, except the per-tile and per-lane checks of Gather, Scatter and sxselect (marked "per tile" / "per lane"): those do not stop the instruction, the good tiles or lanes act, and one OPR-001 is reported (after the checks that precede them have passed; if the write of the destination stream then fails, the OPR-001 is the one reported).

For the **control channel** at the cycle its head parcel dispatches, with k instructions: k ≥ 2 → QUE-001 for every instruction; else decode (DEC-003 for an instruction that does not decode, ECC-002 for one whose text word is uncorrectable); then anything other than Sync, Notify and Config → QUE-002 (so a 64-bit layout is QUE-002). The control channel is never parked and never busy: its own Sync parks only data queues, and nothing holds its parcel.

The cycle reports IQ-002 and then SRF-002 before processing the control channel and data queues.

**Software visibility of errors**. The published sources make some errors visible to software, by two mechanisms:
- ISCA20 §II-D: "Any soft error upsets (SEUs) on operands or instruction text are automatically corrected and recorded in a control and status register (CSR) for an error handler to interrogate later." These are ECC events (9-bit SECDED per 128-bit word, checked by the consuming slice). The specification models ECC (§15), including the `T ecc` trace line and OTS-E-ECC-001); the CSR that records the events is the error log of §16.
- Error detection and reporting in stream spare bits (an error type, a syndrome, and the auxiliary addresses captured with priority Gather, Scatter, then bank conflict) is modelled for the Gather and Scatter bounds errors and for the bank conflict of a Read and a Write dispatched together (§15.5). The diagnostics of §8 report every one of these conditions as well.

The model exposes error observations through the CSR log (§16), the stream spare-bit behavior (§15.5), and the harness diagnostic and ECC trace channels (§12). Exact CSR addresses, spare-bit fields, priorities and diagnostic codes are opentsp interfaces; the public sources do not specify that complete contract. The host can inspect these interfaces, while the instruction set has no conditional branch or CSR-reading instruction. Injected faults come from the harness event protocol; the model does not spontaneously generate soft errors. Operand/resource rejection, partial lane effects and integrity poison follow §8 and §15; a diagnostic is not a general rollback guarantee.

## 10. Multi-chip C2C (`slices/c2c/c2c_insts.sail`, `c_emulator/tsp_sim.c`)

- **Links.** A chip has `c2c.links` = 16 links on `ref` and `mini` (ISCA20 §II: "a total of sixteen (16) ×4 links"), at most 128 in a profile. ISCA22 §2.2 partitions the pin bandwidth into 7 local and 4 global links (11). That conflict is recorded in `isa-db/provenance.yaml` `conflicts: c2c.links`, and a profile may set `c2c.links` = 11. Send, Receive, Transmit and DeskewRecv name a link in their `link` field: 7 bits, the low 4 in bits 9..6 and the upper 3 in bits 5..3 (reserved zero before the field was widened, so every word that was legal keeps its meaning). A link index ≥ `c2c.links` is OTS-E-OPR-001. The CSR counters of the links above 15 are LINK_CORR at 0x500 + (l − 16) and LINK_UNCORR at 0x600 + (l − 16) (`core/csr.sail`). The eight C2C queues are 2 TX and 2 RX per hemisphere, inside the 14-queue SXM blocks of the published split (`topology.md` §5; HC34 p.31 draws the TX and RX stations inside the SXM): west TX 126..127, west RX 128..129, east TX 140..141, east RX 142..143. Any TX (RX) queue may use any link. This is; no source maps links to queues. The model sees only its own end of a link, through the callbacks `c2c_peer`, `c2c_send`, `c2c_recv_ready` and `c2c_recv` (`core/callbacks.sail`). The harness wires the links. Links never apply back pressure (ISCA22 §2.3); software schedules both ends. Two limits make a link finite (bandwidth and receive buffer, below).
- **Link latency.** Every directed link has its own latency L in [`c2c.link_latency_min`, `c2c.link_latency_max`] = [209, 228] (the minimum and maximum of ISCA22 Table 2). The nominal value is `c2c.link_latency` = 216 (the Table 2 mean). A vector sent at cycle c reaches the far end at c + L. Each link delivers in order. By default the harness uses 216 on every link. `--link-latency N` sets every link to N. `--link-latency-seed S` draws each link's latency from the range with a fixed generator, so the same S always gives the same latencies. `--link-jitter-seed S` (round 4) varies the latency **per transfer**: each packet sent on a link draws its own latency in [min, max] from a fixed generator per (S, chip, link) (the packets of the control unit, types csr and ctrl, draw from a generator of their own, so that the draws of the vectors do not depend on when such a packet leaves), and arrives at max(sent + drawn, previous arrival on that link + 1), where the previous arrival is that of **any packet type** on the link: the clamp is one per link, so the link still delivers in order, one packet per cycle, and no packet passes an earlier one (HC34 p.45: a link is one serial channel of flits). Source: ISCA22 Table 2 gives a spread of link latencies; it does not give the jitter's distribution, so the uniform draw over the published range is the opentsp choice. The options are mutually exclusive. The generator is splitmix64 (`tsp_sim.c`): state x += 0x9E3779B97F4A7C15, z = (x ⊕ (x ≫ 30)) · 0xBF58476D1CE4E5B9, z = (z ⊕ (z ≫ 27)) · 0x94D049BB133111EB, result z ⊕ (z ≫ 31), all mod 2⁶⁴; a draw is min + result mod (max − min + 1). `--link-latency-seed S` seeds one state with S and draws chip by chip, link 0..15 within a chip, then the same over the links above 15. `--link-jitter-seed S` seeds chip c's link l (l < 16) with S ⊕ ((16c + l + 1) · 0xD1B54A32D192ED03) (a link l ≥ 16 uses the index 8192 + 112c + (l − 16) + 1 in place of 16c + l + 1) and draws once per data or sync vector sent, the control unit's packets drawing from a second state, the bitwise complement of that one. Two Receives on one link in one cycle take from the FIFO in the order they execute (ascending queue when they share a d_skew, as in the shipped profiles). (Two sends on one link in one cycle cannot both be accepted: bandwidth, below.) A program that receives at exactly send + 216 is therefore only correct for one latency. A correct multi-chip program synchronises with Deskew (below), and its result does not depend on the latencies.
- **Link bandwidth (LNK-001).** A link accepts one vector per `c2c.cycles_per_vector` cycles (*derived*, 24 in `ref` and `mini`. ISCA22 §2.3 footnote 2: "in general we operate all the links at the same data rate of 25 Gbps... with a combined bandwidth of 100 Gbps across the four lanes in a link"; a 320-byte vector is 2560 bits, and at the clock of about 900 MHz (ISCA20 §I) a 100 Gb/s link takes 2560 / 100 Gb/s x 900 MHz = 23.04 cycles, rounded up to 24. The same section says the links run "up to 30 Gbps" (ISCA20 §II): that is the capability, the rate of the system whose latencies the other C2C constants come from is 25, and at 30 Gb/s the same arithmetic gives 19.2 cycles, rounded up to 20; the sources give no vector rate beyond the bit rate). A link *accepts* a vector in the execute cycle of a Send or Transmit that sends it. A Send or Transmit that executes fewer than `c2c.cycles_per_vector` cycles after the cycle in which the link last accepted a vector (the same cycle included) is **OTS-E-LNK-001** (link busy): it reads no stream, sends nothing, and does not move the link's window. Two sends in one cycle on one link: the first in execution order (the order of §8's "Order within a queue's cycle": ascending queue within a cycle) is accepted, the second is busy. **Same-cycle link order.** Under a timing override a Transmit can carry a larger `d_skew` than a Send, so two executions that reach one link in the same cycle can come from queues in any order. The order in which they reach the link is the order in which they execute, delayed executions before immediate ones of the same cycle, whatever the queue numbers; the first to reach the link is accepted. Example (`config/test/c2c_tx_delayed.json`, Transmit `d_skew` 2): a Transmit of queue 127 and a Send of queue 126 execute in one cycle; the delayed Transmit is accepted and queue 126 reports OTS-E-LNK-001. The model, the C harness and the Rust ISS agree (`tests/spec/test_harness_contract.py`). Ascending queue order holds inside one execution class. The check comes after OPR-001 (link or chip_id) and before the stream read: an instruction that raises any other code sends nothing and occupies nothing. The model keeps the cycle of each link's last accepted vector (`c2c_accepted`, cleared by reset); the vector reaches the harness through `c2c_send` only when it is accepted. `c2c.cycles_per_vector` = 1 gives no limit beyond one per cycle. A link's bandwidth is a property of the sender: it does not depend on the harness or on the link latency.
- **Receive buffer (LNK-002).** Each link's receive FIFO holds `c2c.rx_depth` vectors (*design choice:* 16; ISCA22 §2.3 describes no buffer). The FIFO holds the vectors that have arrived and that no Receive has taken. A vector that arrives at cycle a finds the FIFO holding every earlier arrival of the link that is neither dropped nor taken by a Receive that **executes before a**; if that number is `c2c.rx_depth`, the vector is **dropped** and the receiving chip reports **OTS-E-LNK-002** (receive overrun) at cycle a, queue 65535 (the chip-level id of the control channel, whose queue it shares), before `tick(a)`, in ascending link order (§8). A Receive that executes in cycle a takes after the arrival, so it has not freed a slot for it; one that executes in cycle a − 1 has. A dropped vector is gone: no Receive gets it. Arrivals are decided in arrival order. The decision belongs to the harness (§12), not to the model: the model's own state does not hold the FIFO. Overruns count in the `E` line like any diagnostic. A run that stops with a vector still in flight reports nothing for it: only an arrival that finds a full FIFO is a cycle the harness must reach (`--max-cycles` applies to it, exit code 3).
- **Send chip, link, s** reads stream s at the TX gap in its execute cycle (dispatch + d_skew) and puts the vector on the link in that cycle. **Receive chip, link, s** takes, in its execute cycle, the oldest vector that has arrived on the link and writes it to stream s at the RX gap, committing at dispatch + d_func (d_func = 1). If nothing has arrived, Receive is OTS-E-TIM-001 and writes nothing. A Receive that fails any check (OPR-001, TIM-001, OPR-002, or a stream its RX unit cannot write: DIR-001) leaves the link FIFO unchanged; the destination is checked before the vector is taken. **Transmit chip, link** sends the notification vector (lane 0 = 1, other lanes 0); the peer consumes it with Receive (ISCA22 §3.2, Fig. 7(b)).
- **Receive destination.** ISCA20 Table I says: "Receive a 320-byte vector, emplacing it in main memory". In the model, Receive writes a stream, and a MEM Write stores that stream in SRAM. This is the same stream data path every slice uses, and together the two instructions emplace the vector in main memory.
- **chip_id** (9 bits: the low 6 in bits 21..16, the upper 3 in bits 2..0, reserved zero ) names the destination chip (Send, Transmit) or the source chip (Receive). If it does not name the chip at the far end of the named link, or the link is not connected, the instruction is OTS-E-OPR-001 and has no effect.
- **HAC and Deskew.** The hardware-aligned counter is modelled as the cycle number mod P, where P = `c2c.hac_period` = 252. Source: ISCA22 §3.2 footnote 4: "the period is the epoch length or 252 clock cycles. The HAC is an 8-bit counter, but 4 values are reserved for special control codes." All modelled chips' HACs are aligned, which is the state the HAC alignment protocol (ISCA22 §3.1) converges to. Deskew issues on any data queue and holds that queue until the next epoch boundary. A Deskew at cycle c occupies its queue for P − (c mod P) cycles (ISCA22 §3.2: "pause issuing subsequent instructions on that functional unit until the next time the HAC overflows"). A parcel for the held queue waits until the epoch boundary.
- **Deterministic synchronisation.** Every link latency is below P (228 < 252). Suppose a sender issues Deskew, then Send at the epoch boundary b. That vector has arrived by b + P on every link. A receiver that issues a Deskew after b (so it is released at b + P) and then Receive therefore gets the vector whatever the latency. This is the ISCA22 Fig. 7(b) scheme **after alignment**: the child exits ⌊L/period⌋ + 1 epochs after the transmit. The model starts every chip at cycle 0 with aligned HACs and no drift. The published polling loop (ISCA22 §3.2: "If that vector has not been transmitted yet, the loop will continue") is the instruction **DeskewRecv chip, link, stream** (C2C opcode 9). The ISA has no branch, so the loop is one instruction of the model, an implementation choice (`isa-db/provenance.yaml`): it holds its queue like Repeat and, at each HAC epoch boundary (a cycle that is a multiple of `c2c.hac_period`) after its dispatch, tests the link as Receive does. If a vector has arrived, the instruction becomes a Receive on that link, dispatched in that cycle, with the stream operand, and the queue goes on; if not, the queue waits for the next boundary. A vector that arrives at cycle a is therefore taken at the first boundary at or after a (not: at a cycle that is no boundary the poll does not run). A child that starts with the polling loop exits ⌊L/period⌋ + 1 epochs after its parent's transmit, which is the published exit time. A start skew between chips is the harness's per-chip `H start`. A vector that never arrives leaves the queue held for good, like a HostWait that is never rung: the run ends without IQ-004 for that queue. Operand errors are reported at dispatch (OTS-E-OPR-001 for a peer other than 0 or a link at or above `c2c.links`, OTS-E-DIR-001 for a stream whose direction is wrong for the queue) and hold nothing. `test/c2c/deskewrecv_directed.py` runs the loop on one chip and on two chips started 1000 cycles apart (`abstractions.hac_sac_drift` still lists clock drift and SAC as not modelled). `test/c2c/c2c_directed.py` runs such a program at latencies 209, 216 and 228, at five random per-link draws and under per-transfer jitter with eight seeds, and expects the same result each time. It also shows that the unsynchronised schedule (Receive at send + 216) fails on a 228-cycle link.
- **RuntimeDeskew t** issues on any data queue and holds it for t ± δt cycles, where δt is the HAC–SAC drift (ISCA22 §3.3). Modelled chips share one clock, so δt = 0 and the queue is held for max(t, `timing.c2c.rtdeskew_floor`) cycles (the floor is 1 in `ref` and `mini`).
- **Topology** (`tsp_sim --chips K`, after the ISCA22 §2.2 node: "The 7 local links are used to provide full connectivity between the group of 8 TSPs"). With one chip, every link loops back to itself, and its peer is chip 0. With K = 2..8 (one node), local link l (0..6) of chip i connects to chip (i + l + 1) mod K, arriving on that chip's link K − 2 − l. Links l ≥ K − 1 and links 7..127 are not connected. With K above 8 there are N = ⌈K/8⌉ nodes: chip i is in node ⌊i/8⌋ and the local links are as above inside each node, a node holding K − 8 (N − 1) chips when it is the last and not full. The 32 global ports of a node (port p = 4·(i mod 8) + g on global link 7 + g, g = 0..3) connect node n's port p to node (n + p + 1) mod N, on that node's port N − 2 − p, when the chip of that port exists. Every pair of nodes is joined by one global link, which is the all-to-all group level of the Dragonfly (ISCA22 §2.1, §2.2). K above 264 is rejected: a system of any other shape, or of up to 512 chips, is given by a topology file (`tsp_sim --topology`, `topology.md` §7). Each chip's lines in the input follow a `C <chip>` line, and each chip's output follows a `C <chip>` line. Chips run in lock-step windows as long as the smallest connected link latency. No vector can cross a window, so the result is the same as running every chip cycle by cycle.
- **Packet types (HC34 p.45).** The published header flit of a link packet carries "Type (data, CSR, Sync, Ctrl)", so every transfer on a link has one of four types (`c2c_ptype` in `core/callbacks.sail`; `c2c_send` names the type). Send's packet is **data**, Transmit's **sync**; a remote CSR access of the control unit (§14, one hop to the chip at the far end of a link) travels as **csr** packets and the control unit's own messages as **ctrl** packets (the content and the sender of ctrl are not published: the harness line `P ctrl <cycle> <link>` makes a chip's control unit send one, and the clock alignment messages of a later feature would use the same path). Data and sync packets carry a vector and enter the receive FIFO of the link (`c2c_ptype_queued`): Receive takes them and OTS-E-LNK-002 counts them. A csr or ctrl packet is **consumed by the control unit of the chip it arrives at**, in its arrival cycle (`T pkt <cycle> csr|ctrl <link>`): it never enters a FIFO, no Receive sees it, and it never counts for LNK-002. The packet is a header flit and 8-byte flits (HC34 p.45): a vector 1 + `vlanes`/8 flits (41 on `ref`), a csr packet 3 (header; operation, chip, address, tag; value), a ctrl packet 2 (header; payload); a packet occupies a link for ⌈`c2c.cycles_per_vector` · flits / (1 + `vlanes`/8)⌉ cycles (`c2c_packet_cycles`: `ref` csr 2, ctrl 2; `mini` csr 24, ctrl 16): a vector for exactly `c2c.cycles_per_vector`, the same bandwidth per flit for every type. **Sharing a link (implementation choice `host.link_share`; the sources are silent).** The packets of a link share one serial channel (HC34 p.45), so they leave in the order in which they are made and do not overlap. The control unit of a chip decides from what it knows at the cycle and nothing of what comes after it (the earlier rule looked ahead for a gap in the program's schedule, so a packet's departure could depend on a packet that arrives after it left,; it is gone): a csr or ctrl packet leaves at the first cycle c ≥ its *ready* cycle (the cycle it arrived at the chip, or was made) at which no earlier packet of the chip still occupies the link (typed packets share it: a packet occupies it for its k cycles) and no data or sync vector that the link accepted before c is still on it (accepted at a < c with a + `c2c.cycles_per_vector` > c); the packets of one link leave in the order (ready cycle, packet number). A **Send or Transmit that the program releases into the cycles c.. c + k − 1 of a packet in flight is a program error, OTS-E-LNK-003** (no effect; the program is compiled for both ends of a link, so a collision is a compile-time error, as OTS-E-LNK-001 is for two vectors; the owner's decision of 2026-11-16, "Yes."). It is checked after OTS-E-LNK-001, through the harness callback `c2c_packet_busy(cycle, link)`. **Why it is the same for every way of running the chips.** The departure cycle is a function of the ready cycle and of the chip's own accepted vectors (its program, the host script and the control packets that reached it) only. The harness (`c_emulator/tsp_sim.c`, "The control unit") fixes a departure only when it is certain: every vector accepted before c is known (the chip has run to c) and every packet that could arrive earlier has been delivered (no packet sent in a window arrives before the window's end); a chip with a waiting packet reports its earliest possible departure as its next time, so the windows do not pass it. `--window N` shortens the lock-step window (any N ≥ 1), and the output is identical for every N (`test/host/host_directed.py`, per fixed, per-link and per-transfer latency). Control packets draw their latency from a generator of their own under `--link-jitter-seed`, so control traffic never changes the latency a vector sees.
- **Harness contract.** The input is the per-queue text images and the SRAM preload (§12); the model decides when each instruction dispatches, so the output does not depend on the order of the `Q` lines of different queues (the lines of one queue append). Input that is not well formed is rejected with exit code 2. Well-formed means: every field present and hex (a `0x` prefix is tolerated); slice < 88 and, for an `S` or `D` line, (slice mod 44) < `geometry.mem_slices_per_hemisphere` (an absent slice has no SRAM, a `Q` line of an absent queue is accepted: its instructions are QUE-002, §3); address < `words_per_slice`; queue 0..143 or 0xFFFF; every text unit at most 0xFFFFFFFF; the image of a queue, after its padding units are dropped, at most `icu.iq_depth` / 4 units. An `S` line has at most `vlanes` bytes (a shorter line is zero-filled); a longer line is an input error that names the line and the lane count. The harness ticks only cycles where something can happen: `model_next_event` (the next parcel due or complete, a pending commit, an AGT reference, a Repeat iteration, a fetch delivery, the end of an AGT configuration or a barrier release). The harness also acts at a cycle in which a vector arrives at a full link FIFO (LNK-002; §12, "Link FIFOs"). It stops when nothing remains (`model_quiescent`: every IQ is empty or its head parcel can never dispatch, no fetch is in flight, and no overrun is due), then calls `model_finish` once, which raises OTS-E-IQ-004 for text left in an IQ (§3). If the run would need a cycle beyond `--max-cycles` (default 10^8), it stops with a message and exit code 3.

## 11. Reset state (`reset` in `postlude/tick.sail`)

The harness calls `reset` once per chip before the first `tick` (sail-riscv `init_model`). `reset` is the model's only reset: it does not clear the SRAM, and calling it again with the harness's SRAM kept is a run of the model as written. What a host-visible cold reset, restart and start keep and clear is defined in `platform.md` §1.1. The architectural state after `reset` is (tested by `test_reset_state` in `model/unit_tests/test_streams.sail` and the directed reset checks):

| State | Reset value | Defined in |
|---|---|---|
| SRAM, every slice and address | **not model state**: `reset` does not touch it. The storage is the platform's (`core/sram.sail`: "Storage is external"; `tsp_sim` allocates it once per process, all zero, and then the `S` lines preload words, §12). A cold reset of a platform clears it; a restart keeps it (`platform.md` §1.1) | `core/sram.sail` (storage in the harness) |
| Stream register file, both rows | empty: a read finds no value (OTS-E-TIM-001) | `srf_reset`, `core/streams.sail` |
| Spare-bit report array (§15.5) | empty: 256 slots, none used, the next new report takes slot 0; no report is pending on any register | `srf_reset` (`srf_reps`, `srf_rep_n`), `core/streams.sail` |
| Pending commits | none | `pending`, `sys/operands.sail` |
| Pending executions (d_skew > 0) | none | `execute_ring`, `postlude/tick.sail` |
| SetVL, every queue | the profile's superlane count (20 in `ref`, 32 at most): every tile active | `masks_reset`, `core/sram.sail` |
| Liquid-thread split, every MEM slice | every tile in thread 0: a thread-1 MEM instruction before any Config touches no tile and drives zero on its whole result stream | `masks_reset` |
| Segment, every MEM slice | the whole slice (`words_per_slice`) | `mem_reset`, `slices/mem/mem_insts.sail` |
| Queues | none busy, no AGT configuration or loop, no pending Repeat, nothing to repeat (a Repeat first on a queue is RES-001), last dispatch cycle −1 (the first parcel is due at cycle 0) | `postlude/tick.sail`, `iq_reset` |
| Barrier | no Sync parked, no Notify seen | `postlude/tick.sail` |
| IQ, every queue | holds the queue's initial image (padding dropped), no fetch in flight, no underflow pending | `iq_reset`, `slices/cu/cu_iq.sail` |
| Control and status registers (§14, §16) | every register 0, except `IRQ_MASK` = 0xFFFF and `ERR_MASK` = 0x0AA; no doorbell rung, no MSI-X vector pending; the error log empty with no first-error record; the diagnostic log (§16.3) empty with its overflow flag clear; no queue parked by HostWait; the PCIe interface has accepted no vector | `host_reset`, `core/csr.sail` |
| MXM, 2 × `mxm.planes_per_hemisphere` planes | empty weight buffer, no installed weights (ABC is RES-001), no ABC results (ACC is RES-001), every accumulator zero, buffer and weight types i8 | `mxm_reset`, `slices/mxm/mxm_regs.sail` |
| SXM, 2 × 16 maps | the identity map (entry l = l), bijective, ready (ready cycle 0) | `sxm_reset`, `slices/sxm/sxm_regs.sail` |
| C2C links | no link has accepted a vector (every link is free in cycle 0); the receive FIFOs are empty; vectors arrive only from Send/Transmit of this run | `c2c_reset`, `slices/c2c/c2c_insts.sail`; `c_emulator/tsp_sim.c` |
| Patrol scrubber (§15) | the pointer of every MEM slice at word 0 and no pending repair | `scrub_ptr`, `scrub_pending`, `postlude/tick.sail` |
| DeskewRecv polling | no queue polling a link | `queue_poll`, `postlude/tick.sail` |

The control and status registers are state: they are listed in the control and status row of the table (§14 and §16 define them). The 256-entry spare-bit report array is state, not a device: its capacity is part of the specification (§15.5), so a model that is reset keeps no report from an earlier run. The remaining variables that `reset` clears are model devices, not architectural state: the commit and execute rings and the other bookkeeping of work in flight (§13), the patrol arbitration counter, the per-slice revision counters that cancel a stale repair, and the last-tick record.

## 12. Harness and trace protocol (`c_emulator/tsp_sim.c`)

`tsp_sim <config.json> [--trace] [--observe] [--lint] [--on-irq stop|continue|replay] [--max-cycles N] [--chips K] [--window N] [--link-latency N | --link-latency-seed S | --link-jitter-seed S]` reads a program on stdin (text images and an SRAM preload, no cycle numbers) and writes its results on stdout. The golden vectors (`conformance/model/*.json`) and the Python oracle compare this output, so an ISS that is to be checked against them must produce it. This section defines the exact output of the model, the ISS and any implementation that exposes the trace interface; what a silicon RTL must reproduce is the narrower rule of [`platform.md` §7.1](platform.md#71-rtl-conformance), which also defines *well-formed* and the diagnostic classes of §8.

**Input**, one item per line; every number is hex without a prefix; blank lines and lines starting with `#` are ignored:

| Line | Meaning |
|---|---|
| `S <slice> <addr> <b0> … <bn>` | preload one SRAM word, byte b0 in lane 0; missing bytes are zero |
| `Q <queue> <u0> <u1> …` | the initial IQ image of a queue: 32-bit text units in hex, in program order; queue `0`..`8f`, or `ffff` for the control channel. Several `Q` lines of one queue append. A unit `ffffffff` is padding and is dropped |
| `D <slice> <addr>` | dump this SRAM word after the run |
| `C <chip>` | the following lines are for chip `<chip>` (`--chips K`) |
| `R <csr>` | print this CSR (address 0..fff) after the run, as an `X` line (§14) |
| `H start <cycle>` | the queues start dispatching at `<cycle>` instead of 0: every queue's last dispatch is `<cycle> − 1` (§14) |
| `H dma <cycle> <b0> … <bn>` | the host's DMA engine pushes a vector (at most `vlanes` bytes, missing bytes zero) at host cycle `<cycle>` (§14) |
| `H db <cycle> <i>` | the host rings doorbell i (i < `host.doorbells`): the same as `H csr <cycle> w 300+i 1` |
| `H csr <cycle> r <addr>` / `H csr <cycle> w <addr> <value>` | the host reads or writes a CSR at `<cycle>`; a read prints `T csr` |
| `P csr <cycle> <link> r <addr>` / `P csr <cycle> <link> w <addr> <value>` | the control unit of the chip sends a csr packet on `<link>` (connected, else an input error; needs `host.remote_csr`): the chip at the far end reads or writes the register in the arrival cycle and answers a read on the link the request came in (§10 packet types, §14 remote CSR access) |
| `P ctrl <cycle> <link>` | the control unit of the chip sends a ctrl packet on `<link>` (connected, else an input error) from `<cycle>` on, as soon as the link is free (§10, packet types) |
| `H inject <cycle> <queue> <u0> <u1> …` | the host pushes text units into a queue's IQ from `<cycle>` (queue 0..8f or ffff; §14) |
| `F sram <cycle> <slice> <addr> <superlane> <bit> [t\|p]` | ECC fault injection (§15): at the start of `<cycle>` (before the tick) bit `<bit>` of superlane `<superlane>` of the stored SRAM word flips. `<bit>`: 0..7f a data bit, 80..88 the check bits c[0..8], 89 the spare bit. The word must be in an existing MEM slice and `<addr>` inside the slice; a second `F` line for the same bit and cycle is an input error. `t` or `p` (transient or persistent, §16.2) marks the fault for `--on-irq replay`: a `t` fault (the default) is gone in the replay, a `p` fault comes again. Without replay the mark has no effect |
| `F srf <cycle> e\|w <stream> <gap> <superlane> <bit> [t\|p]` | the same for the value held in the stream register of row E or W, stream `<stream>`, at gap `<gap>` at the start of `<cycle>`. It flips the value (and its check bits) of the nearest upstream write on that diagonal, so the value is corrupted where it was already produced; a register that holds no value is left alone (no event) |
| `F iq <cycle> <queue> <word> <bit> [t\|p]` | the same for instruction text (§16): at the start of `<cycle>` bit `<bit>` (0..7f a data bit of the 16 bytes of the text word, 80..88 the check bits, 89 the spare bit) of text word `<word>` of queue `<queue>` (0..8f; 90 is the control channel) flips while the word is in the instruction queue. Words are counted from 0 over the queue's text in production order: the initial image, then the units of each Ifetch or IfetchM payload; four consecutive units are a word. A word that is not in the queue at that cycle stops the run with exit code 2 and the message `F iq at cycle <c>: text word <w> of queue <q> is not in the instruction queue` (hex) |
| `F link <cycle> <link> <flit> corr\|uncorr [t\|p]` | link FEC fault injection (§17): the vector this chip sends on `<link>` in `<cycle>` (a Send or Transmit that the model accepted) has flit `<flit>` (0 the header, 1.. vlanes/8−1 the body flits, vlanes/8 the tail: 41 flits on `ref`) marked: `corr` is a simple error the FEC corrects in flight, `uncorr` a burst it detects and cannot correct. `<link>` must be connected and `<flit>` in range (input errors); a line that marks no vector is an input error at the end of the run (`no vector is sent on link L in cycle C`); two lines for one flit of one vector are an input error. With `--chips K` the line follows the sender's `C` line. `t` (the default) is transient and is omitted from a replay; `p` is persistent and is injected again on replay (§16.2) |
| `F mxm <cycle> <plane> <lane> <bit> [t\|p]` | matrix-unit error injection (§18): flips bit `<bit>` (0..95) of the exact 96-bit two's-complement fixed-point sum of lane `<lane>` of the ABC that executes on `<plane>` in `<cycle>` (the cycle of its read, the cycle its `T` lines carry); with `mxm.fp8_rate` 2 two FP8 ABCs can execute on one plane in one cycle, and the plane's fault lines then belong to the **first of them in execution order** (the execute phase of §1: dispatch order), the second one's check sees none (a vector that binds a fault to the second ABC has no way to say so: the line has no queue field, so a test names the first). `<plane>` is 0..3 and `<lane>` below `mxm.rows` (input errors); a lane at or above the installed rows of the plane carries no product, so its flip has no effect; a line that no ABC consumes (none executes on the plane in the cycle, or it stopped before it read its activation) is an input error at the end of that cycle (`F mxm: no ABC executes on plane P in cycle C (chip N)`, exit 2); two lines for one bit in one cycle are an input error. Several lines for one ABC are one check. `t` (the default) is transient and is omitted from a replay; `p` is persistent and is injected again on replay (§16.2) |

The words `start`, `dma`, `db`, `csr`, `inject`, `r`, `w` of an `H` line, the words `sram`, `srf`, `iq`, `link`, `mxm`, `corr` and `uncorr` and the letters `e`, `w`, `t`, `p` of an `F` line are lower-case letters, not hex. Every chip has its own host interface (§14): an `H` line acts on the chip of the last `C` line before it (chip 0 when there is none), so a host script drives several chips at once; `R`, `P` and `H` lines of one chip are independent of those of another. There is no routing of host actions over the links.

Input errors (exit code 2) are listed in §10, "Harness contract".

**Output**, in this order:
1. With `--trace`, one line per event, in the order the model produces it (§1 and §8 give that order):
   - `T srf <cycle> <row>:<stream> gap <gap> <value>`: a stream value committed at `<cycle>` at writer gap `<gap>`, row `E` or `W`, stream 0..31 (`srf_write_callback`). `<value>` is the committed vector **after any merge** (the two liquid threads' OR of a MEM queue,; the SEL and TSP OR of an SXM hemisphere); for a collision (SRF-002) it is the kept writer's value, since one commit gives one line;
   - `T sram <cycle> slice <slice> addr <addr> <value>`: an SRAM word written at `<cycle>` (Write, Scatter; `sram_write_callback`). `<value>` is the **whole word as stored**: after a masked Write (SetVL, liquid threads: the inactive tiles keep their old bytes) or after one Scatter lane. A Scatter writes one line per active tile, in ascending tile order, so the lines of one Scatter show the word growing one lane at a time;
   - `T diag <cycle> queue <queue> <code>`: a diagnostic (§8); `<queue>` is 0..143, or 65535 for the control channel and for the chip-level OTS-E-LNK-002. **After the last cycle** the harness calls `model_finish` once; it raises OTS-E-IQ-004 for each queue whose IQ holds text that cannot complete a parcel (§3), queues 0..143 in ascending order and the control channel last, each at the last cycle in which the queue received or dispatched a unit. Those `T diag` lines come after every other line of the run and count in the `E` line like any diagnostic.
   - `T lint <cycle> queue <queue> <code>` (only with `--lint`, which is independent of `--trace`): a **simulator lint** (`validation.md` §5), code `OTS-W-<area>-<nnn>`. It is not a diagnostic: it is not counted in the `E` line and it is not in the golden vectors, and an implementation need not print it. It appears in the order the model raises it among the other `T` lines.
   - `T ecc <cycle> queue <queue> corr|unc <row>:<stream>|sram <slice>:<addr> sl <superlane> pos <p>` (§15): an ECC finding of a reader, in the order the model finds it (before the OTS-E-ECC-001 of the same instruction, which `T diag` reports). `corr`: a single-bit error that was corrected for this reader; `unc`: the superlane is uncorrectable. `<row>:<stream>` names a stream operand (`E` or `W`, stream 0..31); `sram <slice>:<addr>` an SRAM word of a Gather or Scatter. `<superlane>` is decimal; `<p>` is decimal: the codeword position the syndrome names (0 for the overall-parity bit c[8]; a position above 136 is not a bit; for `unc` the raw syndrome). `<queue>` is the reader's queue. A `T ecc` line is not part of `trace_sha256`; the golden vectors of faults carry them in `expect.ext_events` (below).
   - `T ecc <cycle> link <l> corr|unc flit <f>` (§17): the link FEC's finding for one flit of a vector that arrived on this chip's link `<l>`, at the vector's arrival cycle, in ascending flit order, before the cycle's tick (so before any diagnostic of that cycle). `corr`: the flit had a simple error the FEC corrected in flight; `unc`: a burst the FEC detected and could not correct. It is printed in the section of the receiving chip.
   - Host lines (§14), not part of any conformance digest: `T dma <cycle> in|wait|out` (a DMA vector entered the ingress FIFO; the DMA engine found the FIFO full and waits; PciSend gave the host a vector), `T irq <cycle> msix <n>` (an MSI-X vector reached the host), `T replay start|resolved|persistent` (`--on-irq replay`, §16.2), `T csr <cycle> <addr> <value>` (the result of an `H csr r`; address 3 hex digits, value hex), `T csr <cycle> <chip> <addr> <value>` (the reply of a remote read: the cycle it reaches the chip that asked, the answering chip decimal, in cycle order among that chip's lines), `T pkt <cycle> csr|ctrl <link>` (the control unit took a csr or ctrl packet in: its arrival cycle and the receiving link; §10, packet types).
   All numeric fields are **decimal** except the CSR address and value of `T csr`. A **`<value>`** is one space and then the vector's `vlanes` bytes, **lane 0 first**, each as two lower-case hex digits and no separator: `2 × vlanes` digits (640 on `ref`, 32 on `mini`; unlike a `W` line, no padding to 320 lanes). A `T srf` or `T sram` line always carries its value.

   **Order of `T srf` lines within a cycle**. The stream-register commits of cycle t are applied at the start of t (§1 step 2), before any parcel of t dispatches, so all `T srf` lines of t are consecutive: they follow only the `T diag` lines of t's link overruns (OTS-E-LNK-002, reported by the harness before the tick) and of t's IQ overflows (OTS-E-IQ-002, raised by Enqueue before the commits) and precede every other `T sram`, `T diag` and `T lint` line of t. **Their order among themselves is not specified**: the **canonical order** is ascending (row, stream, gap), with `E` before `W`. The model emits them in the order of its commit list (`commit_due`), which is not canonical; a conforming implementation may emit them in any order. The canonical key is the one before the value, so two lines of one cycle never differ only in the value. Comparisons (`test/oracle/diff_oracle.py --impl`, porting-guide §3) sort each cycle's run of `T srf` lines into canonical order on both sides before comparing, values included; every other line is compared in order. One commit gives one line, since colliding writes (SRF-002) leave one value.
2. `E <code> <cycle> <count>`: the first diagnostic of the run (its code and decimal cycle) and the decimal number of diagnostics; with none, `E - -1 0`. This line is printed with or without `--trace`.
3. `W <slice> <addr> <b0> … <b(N-1)>` per `D` line, in input order: slice and address in hex, then max(320, vlanes) two-digit hex bytes (lane 0 first; lanes at or beyond the profile's `vlanes` are `00`, so a `mini` line has 16 data bytes and 304 bytes `00`, while `sl32` has 512 data bytes). `--link-latency N`, `--link-latency-seed S` and `--link-jitter-seed S` (at most one of the three) set the C2C link latencies (§10); an N outside [`c2c.link_latency_min`, `c2c.link_latency_max`] is an input error (exit 2).

3a. `Y <cycle> <b0> … <b(vlanes-1)>` per vector `PciSend` gave the host, in cycle order: the decimal execute cycle, then `vlanes` two-digit hex bytes (lane 0 first). 3b. `X <csr> <value>` per `R` line, in input order: the address as three hex digits and the value in hex without padding.

With `--chips K > 1`, each chip's output (items 1 to 3) follows a `C <chip>` line, chips in ascending order. Exit codes: 0 success, 2 input error, 3 `--max-cycles` exceeded (output incomplete), 4 internal error, 5 an error interrupt ended the run under `--on-irq stop`, or a fault was still there in the second run of `--on-irq replay` (§16.2).

**Link FIFOs (`c_emulator/tsp_sim.c`).** The harness owns each link's receive FIFO, the wiring and the latency (§10); the model keeps only the sender's bandwidth state (LNK-001). The rule every implementation follows, per link of a chip, with `D` = `c2c.rx_depth`:
- the entries of a link are its arrivals in arrival order (strictly increasing: one send per `c2c.cycles_per_vector` ≥ 1 cycles and in-order delivery), each *pending*, *queued*, *taken at cycle e* or *dropped*;
- to **decide** the arrival at cycle a: count the earlier entries that are queued or taken at a cycle ≥ a. If the count is at least `D`, the entry is dropped and an LNK-002 report (cycle a, queue 65535) is stored; else it is queued. Entries are decided in arrival order;
- before `tick(t)` the harness decides every pending entry that arrived by t and then writes the stored reports with cycle ≤ t, ascending (cycle, link); `c2c_recv_ready(c, l)` first decides the entries of l that arrived by c (a Receive that executes at c = t + d_skew sees them), is true when the first queued entry has arrived by c, and `c2c_recv(c, l)` marks that entry taken at c;
- the cycles the harness acts at are the model's next event, the cycle of a stored report, and the arrival of an entry that **could** overrun: an entry for which (earlier entries queued, pending or taken at or after its arrival) ≥ `D`, counting no future Receive. Other arrivals are not events (a run that only sends a few vectors does not reach their cycles);
- a csr or ctrl packet is not an entry (§10, packet types): the control unit consumes it at its arrival and it is not counted;
- with several chips, the parent routes each chip's outbound packets (vectors and control packets) at the end of a window, each chip then reports its next time again (it may now have an overrun to report), and the next window starts at the smallest of these times.

**Golden-vector files** (`conformance/model/ref.json`, `tools/gen_model_vectors.py`): a JSON object with `schema` (`opentsp.conformance.model`), `spec_version` (`0.1`), `profile`, `config_sha256` (the SHA-256 of the profile's configuration as canonical JSON: keys sorted, separators `,` and `:`, after the keys the file leaves out are set to their defaults: `ras.diag_depth` = 16), `text` (a human-readable description of the vectors' `text` field) and `vectors`. Each vector has:
- `name`;
- `instructions`, `units`: the catalogue names and unit names the vector exercises (coverage metadata);
- `text`: an object from queue number (decimal; 65535 is the control channel) to the queue's initial IQ image: the 32-bit units in hex, 8 digits each, separated by a space, in program order (an empty image is omitted);
- `sram`: preloads, key `"<slice>:<addr>"` in **decimal**, value the word as a hex string, lane 0 first;
- `dump`: the dumped words, keys as in `sram`;
- `expect.diagnostics`: every `T diag` line, in order, as `{"cycle", "queue", "code"}`;
- `expect.words`: the dumped words, keys as in `sram`, each a hex string of 2 × `vlanes` digits (`vlanes` bytes, lane 0 first: 640 digits on `ref`, 32 on `mini`);
- `expect.trace_sha256`: the SHA-256 (hex) of the **canonical trace**: the `T srf` and `T sram` lines of the run, values included, in the canonical order above (a cycle's `T srf` run sorted), each followed by a newline. `T diag` lines are left out (`expect.diagnostics` has them);
- `expect.events` (only for a vector with at most 64 such lines, which is most of them): those lines in that order, each without its leading `T `, e.g. `"srf 17 E:5 gap 18 0102…"`. An implementation whose digest differs compares its events with these on the small vectors, and with the emulator's `--trace` on the large ones (: storing every event would add about 11 MB to `ref.json`).

A conforming implementation, run with the profile's configuration (`config_sha256`), matches `expect.diagnostics` exactly (codes, cycles, queues and order), `expect.words` byte for byte, and the stream and SRAM values of the trace: the digest of its canonical trace equals `expect.trace_sha256`. So the vectors check the stream values, not only the final SRAM. The Python differential compares the full trace as well, on random programs.

**Conformance is per profile.** The cycle numbers of a trace follow from the profile's latencies, gaps and constants (`timing.*.d_func`, `d_skew`, `layout.*`, `barrier.release_latency`, `icu.*`, `c2c.*`), none of which the specification fixes: `ref` and `mini` are two profiles among others, and `test/ref_slow` (longer MEM, VXM and SXM latencies) is a third that the directed tests also pass. An implementation **declares its profile**, a configuration file that passes `config/schema.json`, and conforms to it when it matches the vectors generated from that file by the frozen model. The vectors of `ref` and `mini` are committed; for any other profile `tools/gen_model_vectors.py <tsp_sim> <config.json> <out.json>` produces them with the same programs, and `--check` rejects vectors whose `config_sha256` is not the digest of the given file. `ref` is a scheduling reference, not an implementability claim (§1, "Granularity and status of the rows"): an implementation conforms to the profile it declares, and the RTL rule of [`platform.md` §7.1](platform.md#71-rtl-conformance) applies to that profile.

## 13. Notes for hardware implementations (informative)

This section explains the distinction between observable behaviour and the structures the model uses to express it. The RTL conformance rule is in [`platform.md` §7.1](platform.md#71-rtl-conformance), and this section is informative. The host interface, hardware time t + k + K and the control channel loaded before start are in `platform.md` (§5, §8).

- **Stream register file.** Observable: per row and stream, a value written at gap g in cycle c is in register g + 1 at cycle c + 1 and moves one register per cycle in the row's direction; a reader at gap G sees register G; it falls off after register 44 (§2, `topology.md` §4). That is a 45-stage shift register per (row, stream, superlane). The 64-slot diagonal ring and the "largest gap below the reader" lookup of `core/streams.sail` are an encoding of that shift register. TIM-001 needs a valid bit per register; DIR-001 also needs, per live value, whether its writer is upstream of the reader (`srf_only_downstream`). DIR-001 is a `schedule` code (§8): for a well-formed object an RTL need not report it ([`platform.md` §7.1](platform.md#71-rtl-conformance)). After a `data` record, though, the cascade rule makes an RTL reproduce the effect of a later `schedule` code, and an instruction that finds no operand (TIM-001) and one that finds it only downstream of its slot (DIR-001) both get no operand and have the same effect, so an RTL need not tell DIR-001 from TIM-001 for its effects; the direction flag serves only the report. **What the cascade rule costs in hardware:** the effects of the schedule rules after a data record are the valid bit per stream register of TIM-001, the lowest-writer rule of SRF-002, the bank rejections of MEM-001 and the suppression of an instruction whose operand is missing. The schedule class saves the reporting logic and the codes' log entries, not that effect logic; a design that does not want it limits its claim to the objects that raise no `data` code.
- **Commit and execute rings.** The 128-slot commit ring and the 16-slot execute ring hold work in flight. Any pipeline that commits at dispatch + d_func and executes at dispatch + d_skew, in the orders of §1 and §8, conforms.
- **Staged unit state.** "State as at the start of the cycle, changes applied at the end" (§1) is ordinary register semantics; RES-003 is a same-cycle write-conflict detector per MXM plane part and per SXM map.
- **SXM map state.** Observable per map: its 320 entries, a bijective bit and a ready cycle (a counter loaded with `superlanes` at the LoadMap's execute cycle, then counting down). The bit is computed while the entries are written (a 320-bit "seen" mask, one pass; the entries arrive one superlane per cycle under the stagger); the Permute reads only the bit and the counter (§7).
- **ABC results.** The plane's list of ABC entries is a modelling device. An ACC takes the newest product committed by its dispatch cycle; for the permitted pair of FP8 ABCs at one dispatch, the even and odd ACC indices select the first and second products respectively (§6). Let D be the largest effective ABC/ABC8 `d_func` on the profile and R = `mxm.fp8_rate`. At most R × D products are in flight per plane; retaining those and the R newest committed products gives the conservative capacity bound R × (D + 1). R = 2 permits two FP8 ABCs; other types still issue at most one per plane per cycle. On `ref` and `mini`, R = 1 and this reduces to D + 1. IW with d_func 1 implies double-buffered weights in the multipliers.
- **f16 dot product.** The exact sum of 320 exact f16 × f16 products needs a fixed-point accumulator of about 90 bits: products range from 2⁻⁴⁸ (two smallest subnormals) to about 2³² (65504²), plus 9 bits for 320 terms and a sign. The sum is rounded once to f32 (§6).
- **Subnormals.** Every f16 and f32 operation keeps subnormal inputs and outputs. Flush-to-zero or denormals-are-zero arithmetic does not conform.
- **Vector length per queue.** SetVL sets the length of the issuing queue (`core/sram.sail`), so an implementation keeps one length per queue: three per MXM plane and sixteen in the VXM, not one per slice.
- **Multi-chip alignment (outside 0.1 hardware conformance).** The model starts every chip at cycle 0 with aligned HACs and no drift. An implementation must provide a mechanism that makes the HACs of its chips equal at start; the published system characterises each link by reflection, aligns the counters and re-synchronises against drift at run time (ISCA22 sections 3.1 to 3.3, link latencies 209 to 228 cycles in its Table 2). The mechanism, the start offset and the drift are not specified. Programs are written for an aligned start or begin with a Deskew pattern (§10); a program with a fixed receive schedule fails under a start skew (`H start`).
- **Host-visible timing.** Host-visible state, interrupts and `ERR_FIRST` are defined in superlane-0 time; the fixed delay, the reorder window and the meaning of `--on-irq stop` are in `platform.md` §5.
- **Harness-only behaviour.** Idle fast-forward (`model_next_event`) and the ring storage of the IQ units in the harness are properties of the model and harness, not of the hardware. The IQ itself, its capacity, the fetch latency and rate, and the parcel and hold rules of §3 are architecture.


## 14. The CSR space and the host interface (`core/csr.sail`, `c_emulator/tsp_sim.c`)

The published sources place the PCIe host interface in the C2C module: "a lightweight DMA engine to emplace a model onto the TSP memory", an entry point for bootstrapping the execution and a general mechanism for passing interrupts to the host (ISCA20 §II-6); the link is PCIe Gen4 x16 at 900 MHz (ISCA22 §5.2). They publish the host's role of loading the model and collecting results, and no register map, descriptor format, pacing or instruction encoding: those are implementation choices (`isa-db/provenance.yaml`, `host.*` and the four instructions). **Every chip has its own host interface** (ISCA20 §II-6 and ISCA22 §5.2 give each chip its PCIe host interface in the C2C module; the serving pipeline of the SHIP paper §2.1 and §7.1.1 takes its input at the first chip and gives its output at the last, so both ends need a host interface on one system): each chip has its own CSR space (`CHIP_ID`), ingress FIFO, DMA engine, doorbells and interrupt delivery, and no host action is routed over the links. Every chip has this interface. A profile containing `host.chip` is rejected. The host of a chip is outside the chip; the harness models it as a **script of timed actions** (the `H` lines of §12 after the chip's `C` line), applied before the tick of their cycle. A script of `H` lines is a conformance test for hardware only when a cycle-accurate host model applies each action at the cycle named; for asynchronous host traffic an implementation guarantees ordering and the semantics of `IRQ_CAUSE` and the doorbells only (`platform.md` §5).

**CSR space.** 4,096 registers of 64 bits per chip, the base address register of the host. A register that is not listed reads 0 and ignores writes, as does a write to a read-only one. No instruction reads or writes a CSR (the published instruction list has none), so a program's results never depend on one. The table lists the control registers. Section 16 describes the error registers beginning at `0x010`.

| Address | Name | Access | Content |
|---|---|---|---|
| 0x000 | `CHIP_ID` | RO | the chip number (`--chips`; 0 with one chip) |
| 0x030 | `IRQ_CAUSE` | W1C | bit n: MSI-X vector n was raised since the bit was cleared |
| 0x031 | `IRQ_MASK` | RW | bit n set: vector n is enabled; reset 0xFFFF. A disabled vector sets its cause bit and gives no interrupt until it is enabled; writing the register delivers every vector the write enables whose cause bit is set (one interrupt each, in the cycle of the write, ascending) |
| 0x032 | `IRQ_COUNT` | RO | interrupts delivered to the host |
| 0x200 + l | `LINK_CORR[l]` | RO | l < min(`c2c.links`, 16): the flits of arriving vectors on link l that the link FEC corrected in flight (§17), counted at the vector's arrival cycle |
| 0x210 + l | `LINK_UNCORR[l]` | RO | l < min(`c2c.links`, 16): the flits of arriving vectors on link l that the FEC detected and could not correct (§17) |
| 0x500 + (l - 16) | `LINK_CORR[l]` | RO | 16 <= l < `c2c.links` (at most 128 links): the same counter as `0x200 + l` for a link above 15, so that no two counters share an address (0x210 + l with l >= 16 would be `LINK_UNCORR[l - 16]`) |
| 0x600 + (l - 16) | `LINK_UNCORR[l]` | RO | 16 <= l < `c2c.links`: the same counter as `0x210 + l` for a link above 15 |
| 0x300 + i | `DOORBELL[i]` | RW | i < `host.doorbells`; a write with bit 0 set rings it, a write with bit 0 clear clears it; a read gives 1 while a ring is pending |
| 0x400 to 0x402, 0x410 + i | `DIAG_COUNT`, `DIAG_POP`, `DIAG_STATUS`, `DIAG[i]` | RO, WO, W1C, RO | the diagnostic log of the codes of class `data` (§16.3), `ras.diag_depth` entries |

MSI-X vector 0 is reserved for the error interrupt of the RAS group; vectors 1..15 are raised by HostNotify. `H db` is a write of 1. **Interrupt delivery (the definition, no state beyond `IRQ_CAUSE` and `IRQ_MASK`):** an interrupt is delivered whenever a cause bit is set and its vector is enabled: HostNotify delivers at once on an enabled vector, and enabling a vector whose cause bit is set delivers it; a cause bit stays set until the host clears it (W1C), so a masked vector is not lost and a vector enabled again with its bit still set is delivered again. The sources give no interrupt rule beyond "a general mechanism for passing interrupts to the host" (ISCA20 §II-6); this is the least restrictive deterministic rule and the one MSI-X defines for its pending bit (implementation choice).

**No performance counters, by design.** The CSR space has error and link counters only (§16, §17): there is no counter of dispatches, holds, stalls, bytes fetched or cycles busy, and the schedule-slip lint OTS-W-IQ-001 is a simulator lint that an implementation need not report (§3). A program whose holds depend on data therefore cannot be profiled on silicon from this specification alone. See [bring-up](bring-up.md) for the observers and diagnostics available in 0.1.

**Host DMA (the ingress FIFO).** A vector requested by `H dma` at host cycle h is *eligible* at e = max(h, previous arrival + `host.cycles_per_vector`) (an implementation choice derived from the published link: a PCIe Gen4 x16 link at 900 MHz carries about 35 bytes per cycle, so a 320-byte vector takes about 9.1 cycles, rounded up to 10, the default; the figure is an estimate; `mini` keeps the value 10 of `ref` so that one program has the same timing on both profiles) and **enters** the ingress FIFO at e if the FIFO holds fewer than `host.ingress_depth` vectors. Otherwise the DMA engine **waits** and nothing is dropped (`T dma <e> wait`): the vector enters in the cycle after the PciReceive that frees a slot. This is the least restrictive causal rule: the engine knows the FIFO at the cycle, never what the program will do (a lossless link with a bus-master DMA engine does not lose data,; OTS-E-HIO-002 is retired and no diagnostic replaces it). A vector the program never takes stays in the engine at the end of the run. The FIFO holds the vectors that entered and that no PciReceive has taken; a PciReceive that executes in cycle a takes after the entry of cycle a. The existing program load (the Q and S lines) is the DMA emplacement of the published sources at cycle 0; `H start <cycle>` moves the bootstrap entry point: the queues start dispatching at that cycle (a program without host traffic gives the same run shifted by it).

**Instructions** (C2C slice tag 5, opcodes 5..8; always decoded). `PciReceive s` (RX queues 128, 129, 142, 143) takes the oldest arrived vector and writes it to stream s at the RX gap, which must be S24..S31 of either row (else OTS-E-DEC-003); nothing arrived is OTS-E-TIM-001; the MEM Write that commits it is a second step; that the receive is two steps, an instruction and a Write, is the model's choice. `PciSend s` (TX queues 126, 127, 140, 141) reads stream s at the TX gap and gives the vector to the host of this chip (a `Y` line of this chip's section; the chip-to-host direction is published in the SHIP paper §7.1.1: the pipeline gives its output at the last chip); **optional and an implementation choice**: the published sources give the host's role of collecting results and no instruction form or pacing for the chip-to-host direction, so the instruction and the pacing (the same as the host-to-chip direction) are the model's; the interface accepts one per `host.cycles_per_vector` cycles and a sooner one is **OTS-E-HIO-001** with no effect, checked after the OPR checks and before the stream is read. `HostWait i` (any data queue; i ≥ `host.doorbells` is OTS-E-OPR-001) parks its queue at dispatch until the host rings doorbell i, which it takes: the next parcel dispatches the cycle after the ring; a ring that came earlier is taken at once and the queue is held one cycle. One ring releases one HostWait (the lowest queue first). A queue parked by a HostWait is held for Sync and Notify as well (unlike a barrier park), and a queue left parked at the end of the run is not reported as stranded text (as a Sync nobody releases). `HostNotify n` (any data queue; n = 1..15, 0 does not decode) sets IRQ_CAUSE bit n and, if IRQ_MASK bit n is set, delivers the interrupt at its execute cycle (`T irq <cycle> msix <n>`; a masked vector is delivered when the host enables it). It reaches the host of the chip that executes it. Timing classes: PciReceive and PciSend `c2c`; HostWait and HostNotify `cu`.

**Instruction injection.** `H inject <cycle> <queue> <units…>` appends text to a queue's IQ through the fetch FIFO of the queue, entering the IQ from that cycle on at the fetch rate, with the overflow rule of the IQ (OTS-E-IQ-002). The host script supplies units to the fill FIFO without the instruction-fetch staging admission check. They still share the delivery bandwidth and IQ capacity. A hardware host adapter must pace admission or buffer its input to reproduce the supported event schedule. OpenTSP specifies the event interface and leaves physical host buffering to the implementation. A stream fetch instead needs two consecutive values on the same stream (§3).

**Harness.** A host action of cycle t that changes the chip (a CSR write, an injection) makes the harness tick t, so that the model's next events are recomputed from it; a DMA entry and a CSR read need no tick. Every chip has its own script, so with `--chips K` a host script drives several chips at once (input to chip 0 and output from chip K − 1 on one system, for the pipeline of the SHIP paper); it is local to its chip, so the lock-step windows of §10 are unchanged. **Remote CSR access** (`host.remote_csr`). The packet type csr is published (HC34 p.45); the operation is ours and is one hop, with no routing. `P csr <cycle> <link> r|w <addr> [<value>]` makes the control unit of the chip send a **csr** packet (§10, packet types) on the link from `<cycle>`, as soon as the link is free (the sharing rule of §10); the control unit of the chip at the far end reads or writes the CSR in the arrival cycle, before that cycle's tick (a doorbell write releases a HostWait), and a read is answered by a csr packet on the link the request came in, printed as `T csr <cycle> <chip> <addr> <value>` in the section of the chip that asked when the reply arrives. A write is not answered. With no program traffic on the link a request and its reply take only the link latencies (h + 2L). Remote CSR commands are link-local. Each chip has its own host interface (`host.link_hop`). `host.remote_csr` false makes a `P csr` line an input error (exit 2). The reply format is an implementation choice (`host.remote_reply`), as are the IRQ_MASK reset value 0xFFFF (`host.irq_mask_reset`) and one ring per HostWait (`host.doorbell_one_ring`). A remote read returns any register of the CSR space, the error registers of §16 included.

## 15. SECDED ECC on SRAM words, stream registers and data paths (`core/ecc.sail`, `core/streams.sail`, `sys/operands.sail`, `slices/mem/mem_insts.sail`, `c_emulator/tsp_sim.c`)

The ECC is part of the base model: **there is no gate and no profile key**. Programs without injected faults run through the same architectural instruction and timing rules. The published sources give the scheme; the parity-check matrix and the details below are the model's, labelled as such.

**Published** (ISCA20 §II-D, ISCA22 §4.5, HC34 p.56, p.57, p.59):
- The ECC that protects SRAM "is also used as they flow on the stream registers on-chip"; the check bits are generated "only at the producer" and "stored alongside the 128-bit memory word as 9-bit ECC, 137-bits in total"; the scheme "implements SECDED"; a functional slice that consumes a stream "will check the ECC bits to ensure data integrity before operating on it" (ISCA20 §II-D).
- SECDED protects the stream registers (45 stations of 138 bits per superlane row), the SRAM and the datapaths, and the logic corrects single-bit errors and detects multiple-bit errors (HC34 p.56, p.57, p.59; ISCA22 §4.5: every single-bit error is corrected in situ, every multi-bit error is detected).
- The 138-bit stream-register word is 128 data bits, the 9 check bits and one more bit (HC34 p.57); the published text calls the remaining bits "spare".

**The code** [implementation choice: the sources publish no matrix and no bit positions; any (137, 128) SECDED code has the published behaviour]. The unit of protection is one **superlane word**: the 128 data bits of one superlane (the 16 bytes of lanes 16g..16g+15; byte l bit b is bit 8 l + b), 9 check bits c[0..8] and one spare bit: 138 bits (bit numbers of the `F` lines: 0..127 data, 128..136 the check bits c[0..8], 137 the spare bit). It is the extended Hamming code (137, 128): data bit j takes codeword position P(j), the j-th integer ≥ 3 that is not a power of two (3, 5, 6, 7, 9, …, 136, so data bit 0 is at position 3, data bit 5 at 10, data bit 127 at 136); c[i] (i < 8) is the XOR of the data bits whose position has bit i set; c[8] is the XOR of the 136 bits at positions 1..136 (the data bits and c[0..7]). The check of a word computes the syndrome s (8 bits: the XOR of the positions of the bits that disagree) and the overall parity q:
- s = 0 and q = 0: no error;
- q = 1 and s = 0: c[8] itself flipped: corrected (no data change);
- q = 1 and s a power of two: a check bit c[log₂ s] flipped: corrected;
- q = 1 and s ≥ 3, not a power of two, s ≤ 136: data bit j = s − ⌊log₂ s⌋ − 2 flipped: corrected;
- q = 1 and s > 136: **uncorrectable** (three or more bits);
- q = 0 and s ≠ 0: **uncorrectable** (two bits, or an even number of more).
A flip of the spare bit is no error of the code and is neither corrected nor reported as an ECC error (it is outside the code); a consumer finds it set and logs it as an error report (§15.5). `test/unit_tests` (Sail, `unit_tests/test_ecc.sail`) checks the whole table against an independent decoder: every one of the 137 single flips corrects, every one of the 9316 pairs of flips is uncorrectable.

**Representation** (a modelling device; observable behaviour is the same as storing the check bits). A superlane word is held as its 128 data bits **as stored** (a flipped bit is flipped there) and a 10-bit **overlay** e: e[8:0] = (the stored check bits) XOR (the check bits of the stored data), e[9] = the stored spare bit. e[8:0] = 0 holds exactly when the stored word is a valid codeword, so a word with no fault has overlay zero and its check is one comparison. A producer generates a fresh code, so a result written by an instruction has overlay zero. Overlays live beside the stream-register values (`core/streams.sail`), the commit ring (`sys/operands.sail`) and, sparsely, the SRAM (`c_emulator/tsp_sim.c` `read_sram_ecc`, `write_sram_ecc`; an unfaulted word has none).

**Who generates and who checks** (the producer-consumer rule is published; the roles of the units below are the model's choice, with the reason):
- A **producer generates**: every instruction that writes a stream writes a valid code, except where the rules below carry a poison or a forwarded overlay. This is the published rule.
- A **consumer checks**: every instruction that reads a stream operand checks it superlane by superlane before it operates on it: the VXM, the MXM (LW, IW, ABC), the SXM, `Send` and `PciSend`, a Gather or Scatter's map (an address stream is an operand like any other, so an address with a single flip is corrected before it is used) and a Scatter's data. A single-bit error is **corrected for that reader**; the stored copy is not written back (an implementation choice: the published text says only "corrected"; not writing back makes the correction cost no cycle, so no timing changes). Every later reader of the same stored word finds and corrects the error again, and reports it again.
- **MEM Read and MEM Write do not check** (implementation choice; the published rule is that a slice checks the stream it "operates on", and a Read or a Write moves the word and its check bits without operating on the value): a Read puts the word's data bits on the stream with the word's overlay, and a Write stores the stream's data bits with the stream's overlay, so the code travels with the word and the first operating consumer decides. A masked Write (SetVL or liquid threads) merges the overlay per superlane exactly as it merges the bytes.
- A **Gather** reads the SRAM tiles of its map, a **Scatter** reads the old SRAM word to merge: each checks the word's superlane (the superlane of the lane the tile serves) as a consumer. A tile whose **map** superlane is uncorrectable makes no access (a Gather lane is zero and poisoned, a Scatter tile writes nothing) and the instruction reports OTS-E-ECC-001 [implementation choice: an address known to be bad is not used]. A Scatter regenerates the code of the word it writes (it is a producer of the stored word, so its overlay is zero, or the poison if the old superlane was uncorrectable).
- **Merges** [implementation choice: the sources are silent]: when two threads' commits, or the SEL and TSP commits of an SXM hemisphere, are OR-merged (§1), the overlays of the merged values are OR-merged as well. A merge in which one side has overlay zero therefore keeps the other side's overlay; only a merge of two faulted values is not a code of the merged value, and its result is then simply whatever the OR of the overlays gives (a deterministic, least-restrictive choice that never turns a faulted value into a valid one).

**An uncorrectable superlane** (a *detected* multi-bit error; ISCA22 §4.5): the instruction that reads it reports **OTS-E-ECC-001** (§8), once, after its own checks. The result of the instruction carries the **poison** in every superlane whose operand was uncorrectable: the data bits are what the instruction computed from the (uncorrected) operand, the code is an invalid word that every consumer will find uncorrectable (c[0] and c[1] inverted, the spare bit clear: syndrome 3, even parity [implementation choice]), so the error is not silently used: **every later consumer reports it again unless a further error hits the stored poisoned word** ("Residual risk" below). A unit whose output superlane depends on several input superlanes (an SXM Shift or Permute) poisons **every** output superlane when any input superlane is uncorrectable (`ecc_dep_all`); a VXM operation is lane-wise, so only the bad superlanes are poisoned; the good superlanes hold the correct result. The MEM Write stores the poison with the word. An operand/resource rejection suppresses the result, subject to the partial-effect cases of §8; its `T ecc` findings are still traced (the operands were read).

**Residual risk: a stored poisoned word.** A MEM Write stores the poison with the word, in the stored form the overlay `0b0000000011` (c[0] and c[1] inverted, the spare bit clear: syndrome 3, even parity). Every single further upset of the stored word except one whose syndrome is above 136 makes the next consumer classify the word as a single-bit error: the report is *corrected*, not uncorrectable, and the correction changes the data. Four cases: a flip of a **check bit** moves the syndrome from 3 to the syndrome of another position, and the correction flips that position, so a data bit of the poisoned result changes; a flip of a **data bit**, the commonest upset, gives a syndrome that names a valid position (the correction flips it: the word then holds two wrong data bits, the flipped bit and the "corrected" one, logged as one corrected error); a flip whose syndrome is above 136 (outside the 137 positions) stays uncorrectable; a flip of the **spare bit** (bit 137) is outside the code, so it leaves the syndrome 3 and the word uncorrectable, and it adds a spare-bit report (§15.5). The statement "every neighbour of every syndrome is a valid position" is not true, since a syndrome above 136 has none. No choice of poison pattern removes the effect for the data-bit and check-bit flips; only a poison bit stored out of band with each word would, and the choice among patterns changes only which flips reach a syndrome above 136. The first error was already logged, counted and interrupted (§16), and the second needs another upset on the same resident word. The published system answers an uncorrectable error with a fault and a software replay of the inference (ISCA22 sections 4.4 and 4.5), not with poison that survives storage; the poison here is an opentsp addition, and a design that needs it to survive further upsets needs a poison bit stored out of band with each word (a 139-bit stored word instead of 138), which is a version-level change and not part of 0.1.

**The MXM and C2C carry the poison (completed)** [implementation choice for every rule below; the published sources say only that an uncorrectable error is detected and that data paths are protected end to end (ISCA22 §4.5; HC34 p.56-59), not how a matrix product or a link carries it]:

- **MXM.** An **ABC** whose activation read found an uncorrectable superlane poisons **every** superlane of its product (each product lane is a sum over all lanes of the activation). A **weight row** that was read uncorrectable (by an LW or an IWS; the flag moves with the row through the buffer and an IW into the installed matrix) poisons product lane r, that is superlane r / 16 (an f16 row r is buffer rows 2r and 2r + 1). The product keeps its poison mask; an **ACC** writes it into the result superlanes and into the accumulator (`acc_poison`): a replacing ACC takes the product's mask, an accumulating ACC the product's mask ORed with the accumulator's. The mask is kept per accumulator index `a`, not per physical accumulator: `acc_poison[a]` is shared by `acc[a]` and, with `wide_acc`, `acc128[a]`, so it belongs to the last ACC that wrote index `a`, and an accumulating ACC on that index inherits it even from the other physical accumulator, which it does not read. This over-approximation is required behaviour (the model and the ISS keep one mask per index), not an option of an implementation. The poison of an ACC result is **inherited**, not found: the ACC reports no OTS-E-ECC-001 for it (it read no bad operand), and the first consumer of the result reports it (`T ecc... unc`, OTS-E-ECC-001), like any poisoned stream. The model keeps the mask in `abc_entry.poison`, `mxm_plane.buf_bad`, `w_bad` and `acc_poison`, and the instruction's `ecc_inherit` register (`core/ecc.sail`) adds it to `ecc_poison_mask`; `read_planes16` records which of the 16 streams was bad (`ecc_g16`).
- **C2C.** A **Send** whose stream operand has an uncorrectable superlane reports it as any consumer (OTS-E-ECC-001 at the Send) and puts the vector on the link **with the mask of those superlanes**; a **Receive** writes the vector to its stream poisoned in the same superlanes (inherited, so the Receive reports nothing; the consumer of the received vector does). The harness callbacks are `c2c_send(..., poison)` and `c2c_recv_poison(cycle, link)`; a vector that nobody poisoned has mask 0. A Transmit's notification and a control packet are never poisoned. The mask is not a packet field of the published links; it stands for the invalid code the vector would carry over the wire.

**Not modelled in ** (named so that nothing is silently dropped): the ICU buffers' own storage beyond instruction text (HC34 p.57) is 's (§16); the error CSR log is §16; the transient and persistent distinction of a fault and the replay are 's (§16.2).

**SRAM scrubbing by software**  [implementation choice: no published source mentions scrubbing; it follows from the rules above]. A stored single-bit error stays in the SRAM: a Read does not check the word and a correction is made for the reader only (no write-back). Every later consumer corrects it again, but a second upset of the same word then makes the word uncorrectable (OTS-E-ECC-001). The sequence below removes the first error with no new state, on one MEM queue and one VXM queue; the VXM checks the operand (a single-bit error is corrected in its copy, `T ecc... corr`, once per operand read) and generates fresh check bits, and the Write stores them:

```
        mem.read  a -> E:0        ; at t - d_skew(MEM) - d_func(MEM) - (21 - gap)   (the word, as stored, with its check bits)
        vxm: max.i8 W:8, E:0, E:0 ; at t                                           (identity: corrects the copy, writes a valid code)
        mem.write W:8 -> a        ; at t + d_func(VXM) + ...                         (stores the corrected word)
```

`test/directed/ras_scrub.py` (every profile, the Sail emulator and the ISS) runs it: a single upset followed by the sequence leaves the word as it was written, and a second upset of the same word after the sequence is corrected, where without the sequence it is uncorrectable.

**The patrol scrubber** (`scrub.period`, an opentsp implementation choice). Period P=0 disables patrol. At each eligible slot m divisible by P, a present MEM slice performs at most one SRAM operation. If it has no pending correction, it reads the word at its patrol pointer, checks each superlane, captures any corrected word/check bits, and advances the pointer modulo `words_per_slice`. If it has a captured correction, a later idle slot writes it back instead of reading another word. Any intervening mutation of that slice, including an integrity-only injected fault, invalidates the captured correction; the slot discards it without writing. The write notification is metadata, not an extra SRAM read. This conservative policy prevents stale repair from overwriting newer program data or fault state.

Foreground SRAM activity has priority. Patrol yields to occupied paths, accounting for their common operand skew and the two cycles of IfetchM. **Patrol timing is implementation-defined and outside conformance comparisons.** The model skips a patrol slot of a slice in every cycle in which that slice's queue dispatches any parcel, even one that touches no SRAM, and in the cycles an in-flight instruction holds a path; an implementation may skip more or fewer slots, so the cycle of a patrol read (and with it the `T ecc... scrub` lines and the log entries it makes) is not compared across implementations. Patrol never delays the instruction schedule. Correctable and uncorrectable observations are reported when the patrol reads: `T ecc <m> scrub slice <s> addr <a> sl <g>` (with ` unc` for uncorrectable), and the error log/counter/interrupt behavior is specified in §16. A correction report describes the decoder’s result; physical writeback may occur later or be canceled. Uncorrectable superlanes are retained unchanged, even when another superlane of that word is corrected. The pointer can report an uncorrectable word again on a later pass.

Patrol runs only through the last program/host event; pending repair does not keep a run alive. Reset clears the pointer and pending repair. The tests in `test/directed/ras_patrol.py` distinguish read from writeback, foreground contention, stale data and stale check-bit corrections.

**Fault injection and observability**: `F` lines (§12) flip one bit of a stored SRAM word or of a value in a stream register at the start of a cycle. The observable results are the data, the `T ecc` lines and OTS-E-ECC-001 (§12). `ras.py` (`test/directed/ras.py`) pins them on every profile, and `ras_poison.py` (`test/directed/ras_poison.py`: the MXM and C2C poison, on the model, the ISS and the Python oracle) the rules above; `unit_tests/test_ecc.sail` pins the code; the golden vectors of faults (`ecc-NNN`, §12) pin them for an ISS.

### 15.5 Error reports in the spare bits (`core/streams.sail`, `core/ecc.sail`, `core/csr.sail`, `slices/mem/mem_insts.sail`)

The spare bit (bit 137) of each superlane of the 138-bit stream-register word belongs to the error report; a fault-free system has every spare bit clear. The poison of §15 does **not** use it: a poisoned superlane is the uncorrectable pattern in the check bits alone (c[0] and c[1] inverted) [implementation choice], so that a set spare bit always means a report. (Moving the poison out of bit 137 changes no result: the classification of a word never read the spare bit; the golden vectors, traces, diagnostics and cycle counts are unchanged.)

**OpenTSP error-report layout.** For each superlane x, streams 0, 1 and 2 carry the Gather bounds, Scatter bounds and bank-conflict flags in their spare bits. Stream 3 carries their even parity. When flags coincide all flags survive. The auxiliary address and stream fields describe the highest-priority event, in the order Gather, Scatter, bank conflict. The layout below is **required for the model and ISS** (the golden vectors and the directed tests pin it bit for bit); an RTL provides an error report carrying the same facts (that an event occurred, its kind among Gather bounds, Scatter bounds and bank conflict, and the address and stream of the highest-priority event), not necessarily in these spare bits (`platform.md` §7.1). **The address is the low 13 bits** on every profile: the model and the ISS report no more (see the next bullet), so a golden vector or a test of a profile with `sram.addr_bits` above 13 binds an RTL to those 13 bits and no further; an RTL may carry the full address, and a comparison against the model reads the low 13 bits of it. On such a profile the bank bit can lie above bit 12 (`topology.md`: `bank_bit` 15 on `w16`), so the reported bits of the two addresses of a bank conflict need not contain the bit that put them in one bank, and the reported bits of an out-of-range Gather tile can equal those of an in-range address (carrying the upper bits needs a wider layout, and the bank-conflict layout has no free stream for them: an open decision of the ).

- *Who writes it.* A Gather or Scatter that has tiles outside the segment or the slice (OTS-E-OPR-001, which is still reported) writes a report in the **commit cycle** of the instruction at the **write gap** of its slice, on the row of its **data stream** (the destination of a Gather, the source of a Scatter), for each such tile in its own superlane x.
- *What it writes.* S[0][x] (Gather) or S[1][x] (Scatter); S[3][x] the parity of the merged S[0..2][x]; auxiliary streams S[4..16][x] the low 13 bits of the address the tile took from its map (bit i on stream 4 + i; a profile with a wider address (`sram.addr_bits` above 13) does not report the bits above bit 12, the layout has no stream left for them), S[17..22][x] the map stream (the row bit, W = 1, then the 5-bit id, low bit first), S[23..28][x] the data stream in the same layout. Where two reports meet in one register, the auxiliary streams of the higher priority win in each superlane, equal priorities are ORed, and S[0..2] are ORed.
- *The report is a write of spare bits only.* It does not change data or check bits and creates no value: it travels on the diagonal of the register, beside the values, and a reader at a gap above the report that finds a value on the diagonal sees the report's spare bits with it, unless a data write of that diagonal at a gap between them replaced the register. A report on a register no value passes is seen by nobody. The spare bit flows with the value it belongs to: a MEM Write stores it in the SRAM word and a later Read forwards it; a unit that generates a new result writes a clear spare bit.
- *Who logs it.* Every stream operand read (not a chained read) whose spare bit is set in some superlane is logged by its consumer, once per stream and superlane, before the superlane's ECC check: the trace line `T ecc <cycle> queue <q> spare <row>:<stream> sl <x> pos <S[0..3]>` (`pos` is S[0], S[1], S[2], S[3] of the superlane as bits 0..3, read at the consumer's register), a log entry of kind 9 in the error CSRs (§16: the location of a stream register, the superlane, S[0..3] in the position field) and `ERR_STATUS` bit 8. `ERR_MASK` resets with bit 8 clear: no interrupt. No instruction reads the spare bits as data.
- *The bank conflict.* A pair of references of one MEM queue that meet in a bank (OTS-E-MEM-001, §8: neither runs; a new reference or an AGT reference of either path) writes a report in the commit cycle of the instruction (dispatch + d_func of MEM) at the write gap of its slice, on the row of the data stream of the pair's R-type reference (the destination of its Read or Gather, plus the AGT stream offset), in **superlane 0** (a conflict belongs to the slice, not to a tile): S[2][0], S[3][0] their parity, S[4..16][0] the low 13 bits of the address of the W-type reference (bit i on stream 4 + i), S[17..29][0] the low 13 bits of the address of the R-type reference (bit i on stream 17 + i); the bits above bit 12 of a wider address are not reported; the addresses include the AGT offset of the cycle's reference, and an indirect reference (Gather, Scatter) has no address at dispatch, so its field is zero. Priority 1: where a Gather or Scatter report meets it in the same register, S[0..2] are ORed (both are noted) and the auxiliary streams of the Gather or Scatter win. The two instructions of a pair give the same report. A pair with an IfetchM (it has no data stream) is still OTS-E-MEM-001 and writes no report. The stream-register spare plane has 30 streams (0..29) for this layout.
- *Report retention.* The model keeps the **256 latest** reports, one per (row, register, cycle): a report on a register that has none takes the slot of the oldest one, which is then gone. A reader finds a report only while it is in its row (at most 44 cycles), so unrelated reports in that window (a program that raises bank conflicts or Gather/Scatter errors on many slices in the same cycles) can hide a pending one. The capacity is part of the specification; per-diagonal retention is not built. When the report that is overwritten was still in its row, the simulator lint **OTS-W-RAS-001** (`--lint`, validation.md) says so, at the cycle of the instruction that wrote the new report; it has no architectural effect and is not in the golden vectors (an implementation need not report it). `test/directed/ras_spare.py` pins it (`spare-11`: two observations and no lint; `spare-12`: none and the lint).
- *Not modelled yet.* An injected flip of a spare bit (`F... 89`) is a report with no S[0..3] at the consumer (`pos 0`).

`test/directed/ras_bank.py` pins the bank-conflict report on the model, the ISS and the Python oracle (same-bank pair: S[2] and S[3], both addresses, the clear bits, different banks: nothing, an AGT loop reference with and without Step, a Gather bounds error in the same register: both noted, the Gather's auxiliary data kept). `test/directed/ras_spare.py` pins the rules for Gather and Scatter on the model, the ISS and the Python oracle (a Gather with one bad tile: S[0] and S[3] of its superlane, `pos 9`; the address bits; a Scatter: S[1] and S[3], `pos 10`; the error registers). The golden vectors keep every earlier record; one earlier vector, `ecc-007` (an injected flip of the spare bit of a stored word), now has the consumer's report as an external event (`T ecc... spare`), and the new records are appended.

## 16. The error CSRs and the error interrupt (`core/csr.sail`, `c_emulator/tsp_sim.c`)

The error registers belong to the base model and exist in every profile. `ras.log_depth` defaults to 8. A vector recording an interrupt includes a `T irq` line in `ext_events`. The canonical `trace_sha256` excludes those lines. No instruction reads or writes these registers: the host reads them through the CSR space of §14 (`H csr r` and `R` lines in the harness) and a remote chip through a csr packet (`P csr`).

**Published** (ISCA20 §II-D, §II-6; ISCA22 §4.5; HC34 p.60). Corrected soft errors "are automatically corrected and recorded in a control and status register (CSR) for an error handler to interrogate later"; the host interface "provides a general mechanism for passing interrupts to the host, which may be necessary in the event we observe a multi-bit memory error"; the runtime replays the inference after a detected multi-bit error (ISCA22 §4.5), and one-shot replay tells a transient fault from a persistent one (HC34 p.60). **Not published:** every address, field, width and depth, the clearing rule, the interrupt's register interface and timing, whether the chip stops: all of them are implementation choices (`isa-db/provenance.yaml`, section `ras`).

**The registers** (CSR space of §14; `core/csr.sail` has the layout in its header):

| Address | Name | Access | Content |
|---|---|---|---|
| 0x010 | `ERR_STATUS` | W1C | the error register: bit 0 corrected data error, 1 uncorrectable data error, 2 corrected text error, 3 uncorrectable text error, 4 matrix corrected, 5 matrix uncorrectable, 6 link corrected, 7 link uncorrectable, 8 spare-bit report, 9 log entry dropped (bits 4 and 5 are set by the matrix-unit check events of §18 and bits 6 and 7 by the link FEC events of §17; bit 8 is set by the feature that reports spare-bit use and reads 0 until then) |
| 0x011 | `ERR_SEVERITY` | RO | 2 when bit 1, 3, 5 or 7 of `ERR_STATUS` is set, else 1 when bit 0, 2, 4, 6 or 8 is set, else 0 |
| 0x012 | `SBE_COUNT` | W1C-all | corrected errors, saturating at 2³² − 1; a write of any value clears it |
| 0x013 | `MBE_COUNT` | W1C-all | uncorrectable errors, the same |
| 0x014 | `LOG_COUNT` | RO | entries in the log (0.. `ras.log_depth`) |
| 0x015 | `LOG_POP` | WO | a write removes the oldest entry |
| 0x016 | `ERR_MASK` | RW | bit n set: a 0 to 1 change of `ERR_STATUS` bit n raises the error interrupt; reset 0x0AA |
| 0x020 + 2 i, 0x021 + 2 i | `LOG[i]` | RO | entry i (0 the oldest, i < `ras.log_depth`) |
| 0x0F0, 0x0F1 | `FIRST_ERR0/1` | RO | a copy of the first log entry since `ERR_STATUS` was last cleared to zero |
| 0x100 + q | `FETCH_RT[q]` | RO | q = 0..143: the fetch latency of queue q, `icu.fetch_latency` (the profile key stays the authority) |

A log entry has two words. Word 0: cycle (bits 47..0), kind (51..48: 1 corrected data, 2 uncorrectable data, 3 corrected text, 4 uncorrectable text, 5 and 6 matrix, 7 and 8 link, 9 spare-bit report), queue (63..52; the control channel is 0x090, an event of no queue 0xFFF). Word 1: location (bits 42..0: for a stream register the row at bit 0 (1 = W), the stream at 5..1 and the **reader's gap** at 11..6; for an SRAM word the slice at 6..0 and the address at 22..7 (16 bits; 19..7 on a 13-bit profile, the bits above the address are zero); for instruction text the queue at 7..0 and the text word at 31..8), superlane (47..43), syndrome position (56..48: the position the check names for a corrected error, the raw syndrome of an uncorrectable one). Events of one cycle are logged in the order of the `T ecc` lines; the operand ECC events of an ABC precede its sum-check event (§18). A new event when the log is full is dropped and sets `ERR_STATUS` bit 9; the counters still count and `FIRST_ERR` still keeps the first event. The log has at most 8 entries (16 registers, 0x020..0x02F): the design note allowed up to 64, which would reach the interrupt registers at 0x030, so the profile key `ras.log_depth` is 1..8 (default 8).

**Matrix-unit and link FEC events.** The events of §17 and §18 are recorded like the data and text events, with the layout of the log words below the table (implementation choice, `isa-db/provenance.yaml` section `ras`, rows `ras.mxm_events` and `ras.link_events`):
- **a corrected lane of an ABC** (§18): kind 5, `ERR_STATUS` bit 4, counted in `SBE_COUNT`; queue the ABC's; the cycle the ABC executes (the cycle of its `T ecc... mxm corr` line); word 1 = plane << 16 | lane;
- **an uncorrectable ABC** (OTS-E-ECC-003): kind 6, bit 5, `MBE_COUNT`; the same queue and cycle (the cycle of the diagnostic); word 1 = plane << 16 | 0xFFFF: the check located no lane, so the lane field holds 0xFFFF, a value no lane has (a plane has fewer than 0xFFFF rows);
- **a corrected flit of an arriving vector** (§17): kind 7, bit 6, `SBE_COUNT`; no queue (0xFFF); the arrival cycle of the vector (the cycle of the `T ecc... link... corr flit` line); word 1 = link << 16 | flit, the link (bits 22..16, 7 bits, since a chip has up to 128 links) being the receiving chip's and the flit in bits 15..0;
- **an uncorrectable flit**: kind 8, bit 7, `MBE_COUNT`; the same fields.
One flit is one event (as the link counters 0x200, 0x210, 0x500 and 0x600 count it), so a vector with several marked flits makes several entries, in ascending flit order; `LINK_CORR` and `LINK_UNCORR` are unchanged. The superlane and position fields of word 1 are 0 for these events. The error interrupt is governed by `ERR_MASK` as for data and text errors: at reset an uncorrectable matrix or link event (bit 5 or 7) raises vector 0 in the cycle of the event, after its `T ecc` line, and a corrected one does not unless the host sets bit 4 or 6. The OTS-E-ECC-003 diagnostic of the ABC follows the interrupt in the trace.

**The error interrupt.** MSI-X vector 0 of §14 is the error interrupt. An event that makes a bit of `ERR_STATUS` change from 0 to 1 while that bit is set in `ERR_MASK` (reset 0x0AA: the uncorrectable bits 1, 3, 5 and 7) delivers vector 0 in the cycle of the event (`T irq <cycle> msix 0`): the cause bit 0 of `IRQ_CAUSE` is set and, when `IRQ_MASK` bit 0 is set (reset: all vectors), the host is interrupted and `IRQ_COUNT` counts it, as for any vector (§14). A bit that stays set raises no second interrupt; once the host has cleared it the next event raises it again. A corrected error raises none at reset (the host can enable bit 0, 2, 4, 6 or 8 in `ERR_MASK`). **The chip does not stop** (HC34 p.55: no reactive components in the datapaths, §1): the program runs on, its results as computed, and the response is the runtime's. What the runtime does, a replay, is the harness's policy (§16.2).

**Not implemented, and why.** The design note's `FEATURES` register (one bit per optional feature) does not exist: with no feature gate every feature is part of the base model and there is nothing to report. The log is limited to 8 entries (above). The design note's reset mask 0x0AA is used as the number says, although its prose also names the overflow and permission bits.

### 16.1 ECC on instruction text (`slices/cu/cu_iq.sail`, `postlude/iq.sail`, `postlude/tick.sail`, `core/diagnostics.sail`)

Instruction-text ECC belongs to the base model. A text word with no fault carries a valid code.

**Published** (ISCA20 §II-D; HC34 p.57). "Any soft error upsets (SEUs) on operands or instruction text are automatically corrected and recorded in a control and status register (CSR) for an error handler to interrogate later"; the instruction buffers and the instruction queues (x144 each) are protected (ECC Everywhere). **Implementation choices** (`isa-db/provenance.yaml`, section `ras`, rows `text_*`): everything below.

- **The text word** is 16 bytes of text: four consecutive units of the queue's text in production order (the initial image first, then the units of each Ifetch or IfetchM payload, whose superlanes are text words). It carries the code of §15 (the overlay of §15 per word: the stored check bits XOR the code of the stored data, plus the spare bit).
- **Check point.** An instruction is checked when its parcel dispatches, before its fields act: the instruction queue is decoded as the corrected text (a single flipped data bit is repaired in the view), and an instruction whose word is uncorrectable is not executed: it is **OTS-E-ECC-002** (a diagnostic of its own, without a result; the width is read from the raw first unit, so the parcels keep their boundaries and the timing NOP of the parcel is reported too). An instruction of two units checks both of its words (the pair), so a double flip in a unit it does not use still makes it OTS-E-ECC-002; an instruction in the other word runs. Every instruction of the parcel checks, the timing prefix included, in program order.
- **A corrected error** is reported once (`T ecc <c> queue <q> corr text word <w> pos <s>`, one log entry of kind 3, `ERR_STATUS` bit 2, `SBE_COUNT`) and **written back**: the repaired data bit is fixed in the queue and the word's code is made valid, so one fault is one event (the data of §15 is not written back; a text word stays in the queue for several cycles and every instruction of it is a reader). A check bit that flips is corrected the same way; a flip of the spare bit is no error.
- **An uncorrectable word** is reported by every instruction that has a unit in it (`T ecc <c> queue <q> unc text word <w> pos <s>`, kind 4, `ERR_STATUS` bit 3, `MBE_COUNT`) before the diagnostic of that instruction, and the word stays uncorrectable. The first 0 to 1 change of `ERR_STATUS` bit 3 raises the error interrupt (§16); the chip does not stop.
- **Fetched text.** An IfetchM fetches the two SRAM words with their stored codes (a fault in the SRAM word is found when the fetched text is used, not when it is fetched). An Ifetch whose operand read found an uncorrectable superlane fetches an invalid code for that superlane (the poison of §15); the operand's own check is as for any consumer.
- **Not covered.** Text injected by the host (`H inject`) belongs to no word (no code); the ICU buffer and the instruction queue are one structure here (one overlay per word, kept while the word is in the queue); `F iq` is the only way to fault text.
- **Fault injection** is the `F iq` line (§12).
- **Model-defined details, outside RTL conformance.** (1) *Padding.* The code of a fetched payload covers the 16 bytes of one superlane, padding units included: a padding unit is dropped at enqueue and never occupies the IQ, but it is part of the word its superlane carries. (2) *Numbering.* The text words of an `F iq` line are counted over the queue's text in production order: the initial image (padding already dropped) and then the units of each Ifetch or IfetchM payload (padding units included), so the same text has different word numbers depending on how it arrived. (3) *NOP timing.* The leading NOPs of a parcel are checked like every other unit and the due cycle of the parcel is re-evaluated each cycle from the prefix as it stands, so a fault on a waiting NOP prefix ends the wait and the issue cycle of the parcel depends on the cycle of the injection. These are defined by the model and the ISS; the cycles of a parcel after a text fault are not an obligation of an RTL.
- **Evidence.** `test/directed/ras_csr.py` (sections 10, 11) on every profile, the model and the ISS; the golden vectors of the text faults (the `ecc-NNN` vectors whose `host` lines hold an `F iq` line) pin the observable lines for an ISS.


### 16.2 The replay policy (`c_emulator/tsp_sim.c`, `--on-irq`)

**Published** (ISCA22 §4.5; HC34 p.60): after a detected multi-bit error the runtime replays the inference, and a one-shot replay tells a transient fault from a persistent one. **Implementation choice:** the replay is a **policy of the harness**, not chip state: the chip keeps no replay register and never stops by itself (§16). The harness option `--on-irq stop|continue|replay` (single chip only; with `--chips K > 1` `stop` and `replay` are refused with exit code 2) selects what the harness does when the error interrupt (MSI-X vector 0, §14) is raised:

| Policy | Behaviour |
|---|---|
| `continue` (default) | The run goes on: the output is that of a run without the option, exit code 0 |
| `stop` | The run ends at the end of the cycle of the first error interrupt: the output (trace lines, `E`, `W`, `X` and `Y` lines) is what stands then, with no `IQ-004` check of the remaining text, exit code **5** |
| `replay` | The first run is the run of `continue`. If it raised no error interrupt, that is the output and the exit code is 0. If it did, the harness prints `T replay start`, resets the chip and runs the same input a second time with only the **persistent** faults (`F... p`): the faults marked `t` (the default) are gone, as a soft error is. The second run's output follows. The last line is `T replay persistent` (the second run raised the error interrupt again: exit code **5**) or `T replay resolved` (it did not: exit code 0). A run that fails (exit code 2, 3 or 4) is not replayed |

The `T replay` lines are printed with or without `--trace`. Host lines (`H`), preloads and programs are the same in both runs; only `F` lines can differ. `F` lines (§12) take a last word `t` (transient) or `p` (persistent); the rule holds for every kind of `F` line: `sram`, `srf`, `iq`, `link` (§17) and `mxm` (§18). `test/directed/ras_replay_marks.py` shows it for `link` and `mxm`: a line marked `p` acts again in the replay run (its `T ecc` line is in the second run), one marked `t` or not marked is dropped.

**Evidence.** `test/directed/ras_replay.py` (the model and the ISS on every profile): the three policies, a transient, a persistent and a mixed fault, a corrected error (no replay), the refusals. The ISS has the same option and the same output (`tsp-iss run --on-irq`).

**Serving after a fault.** The harness replay above runs a single-chip test input a second time. TinyStories and GPT-2 instead terminate requests exposed to an unsafe step. Masking or acknowledging the IRQ cannot authorize publication. For GPT-2, one unsafe stage fences the entire 16-chip domain. Only a successful cold recovery or service clearance followed by healthy startup can return the domain to fresh work. [Management evidence, publication and re-entry](production-ras.md)

### 16.3 The diagnostic log (`core/csr.sail`, `core/queues.sail` `diag_report`)

The diagnostic codes of the table of §8 reach the host of a model run as `T diag` lines and the `E` summary, and reach the host of a **silicon chip** only through its CSR space. The CSR space therefore has a log of the codes of class `data`: the rules that read SRAM words, stream values or instruction text, which `platform.md` §7.1 says an RTL must report for a well-formed object. The log is **fed in the reporting order of §8** (it is filled by the one function that reports a diagnostic to the harness, `diag_report`), so an RTL that implements it reproduces the order of the vectors.

| Address | Name | Access | Content |
|---|---|---|---|
| 0x400 | `DIAG_COUNT` | RO | entries in the log (0.. `ras.diag_depth`) |
| 0x401 | `DIAG_POP` | WO | a write removes the oldest entry (nothing when the log is empty) |
| 0x402 | `DIAG_STATUS` | W1C | bit 0: the overflow flag, set when a record found the log full (the record is dropped); a write with bit 0 set clears it. The dropped records are not counted |
| 0x410 + i | `DIAG[i]` | RO | entry i (0 the oldest, i < `ras.diag_depth`), one word: cycle (bits 47..0, the superlane-0 cycle of the report), code (55..48: the position of the code in the `diag` type of `core/diagnostics.sail`, below), queue (63..56: 0..143, the control channel is 144). An address at or above `0x410 + ras.diag_depth` reads 0 |

Code numbers (bits 55..48): 0 DEC-003, 1 QUE-001, 2 QUE-002, 3 TIM-001, 4 DIR-001, 5 SRF-002, 6 MEM-001, 7 OPR-001, 8 OPR-002, 9 RES-001, 10 RES-002, 11 RES-003, 12 SXM-001, 13 LNK-001, 14 LNK-002, 15 LNK-003, 16 IQ-002, 17 IQ-003, 18 IQ-004, 19 HIO-001, 20 ECC-001, 21 LNK-004, 22 ECC-003, 23 ECC-002. The **log filter** admits a superset of the codes of class `data`: **SXM-001, DEC-003, IQ-002 and IQ-004** on any queue; **OPR-001** on a MEM queue and on an `sxselect` (`*_SEL`) queue; **TIM-001** on a C2C receive queue. (The table of §8 gives OPR-001, DEC-003 and TIM-001 the class `schedule`, with a data exception for a Gather or Scatter tile address, an `sxselect` select, a unit fetched from SRAM and a Receive whose vector depends on the remote chip. A diagnostic does not say which instruction raised it, so the log keeps every OPR-001 of a MEM or `*_SEL` queue and every DEC-003: the superset also used by the platform FIFO in `platform.md` §7.) Every other code is not logged: a `schedule` code that the filter does not admit is checked by the toolchain before the image is loaded ([`platform.md` §7.1](platform.md#71-rtl-conformance)), and a `fault` code is reported through the integrity log of §16.

**Depth: the profile key `ras.diag_depth`** (1..64; **optional: a profile that leaves it out has depth 16**, the value of every shipped profile and the minimum depth of the platform FIFO; every loader reads the missing key as 16, and a given value outside 1..64 is refused). The registers exist in every profile. **The platform's `ERR_FIFO` mirrors this log**: the wrapper FIFO of `platform.md` §7 holds the same records in the same order, has the depth of the key, and its `fifo_overflow` flag is `DIAG_STATUS` bit 0 (`tests/platform.rs` compares the two). `DIAG_POP` is the chip's `ERR_FIFO` pop. The log is reset by the cold reset of §11. Tests: `test/directed/ras_diag.py` (model and ISS), `model/unit_tests/test_ras.sail`, the golden vectors `ecc-NNN` that read it.

## 17. C2C link FEC and link error reporting (`slices/c2c/c2c_insts.sail`, `core/csr.sail`, `core/ecc.sail`, `c_emulator/tsp_sim.c`)

Link FEC is part of the base model and applies to every profile.

**Published** (ISCA22 §4 and §4.5, HC34 p.41, p.45, p.56): "we use forward error correction (FEC) on every link to correct simple transmission errors and detect uncorrectable burst errors", which "allows the system to correct transmission errors in situ, and flag any critical errors that require the runtime system to 'replay' the inference" (ISCA22 §4.5); forward error correction "to avoid reactive link-layer replay" is one of the network's design points (ISCA22 §4); the FEC "corrects most transmission errors deterministically" (HC34 p.41) and corrects single-bit errors and detects multiple-bit errors (HC34 p.56); the packet is a 320-byte vector in flits of 8 bytes with a header flit and a tail flit, no hardware flow control and no virtual channel information (HC34 p.45).

**Not published:** the FEC code, the per-link error counters, and what a receiver does with an uncorrectable vector. Everything below that says "implementation choice" is the model's, with its reason in `isa-db/provenance.yaml` (`link_fec.*`).

**The transfer** (HC34 p.45). The header contains payload bytes0–4; body flit f contains bytes `5+8(f−1)` through `12+8(f−1)`; the tail contains the last three payload bytes. Thus a vector uses `1 + ceil(vlanes/8)` flits: 41 on `ref`, 3 on `mini`. The same count determines packet serialization and valid fault coordinates. A body fault marks every superlane containing one of its eight payload bytes: for example, flit2 covers bytes13–20 and affects both superlanes0 and1. Header/tail corruption conservatively marks every superlane because those flits also contain control information; that policy is an opentsp choice. The vector-level FEC outcome model is not an implementation of an unpublished physical error-correction code.

**Outcome per flit** [implementation choice: the code is not published; a harness line marks the outcome]. The fault line `F link` (§12) marks a flit of the vector the chip sends in a cycle as `corr` (a simple error: the FEC corrects it in flight and the vector arrives intact) or `uncorr` (a burst: detected and not corrected). The finding is made in the **arrival cycle** of the vector at the receiving chip, before that cycle's tick, once per marked flit in ascending flit order, in ascending link order together with the link overruns of that cycle (a finding of a link comes before the OTS-E-LNK-002 of the same link and cycle: the FEC acts before the receive FIFO sees the vector, so a vector that is then dropped is still counted):
- **corr:** the vector is delivered unchanged; `T ecc <cycle> link <l> corr flit <f>` (§12); the receiving chip's counter `LINK_CORR[l]` (CSR 0x200 + l for l < 16, 0x500 + (l - 16) above, §14) increments; no diagnostic.
- **uncorr:** the vector is delivered with the superlanes covered by the bad flits **poisoned** (the poison of §15: its data bits are the sent ones, its code is invalid); `T ecc <cycle> link <l> unc flit <f>`; `LINK_UNCORR[l]` (0x210 + l for l < 16, 0x600 + (l - 16) above, §14) increments. The Receive that takes the vector **still writes it** (poisoned), and reports **OTS-E-LNK-004** after its own checks, **once** for the vector (§8). The poison then travels as in §15: the MEM Write stores it, a Read forwards it, and the first consumer that operates on it reports OTS-E-ECC-001 and poisons its result. `l` is the **receiving** chip's link index (the far end of the link the chip sent on); with one chip every link loops back, so it is the sending link.
- **timing:** none. The FEC is deterministic (HC34 p.41), the latency of a link is a profile value (§10), and the link FEC adds no cycle.

**The diagnostic code.** OTS-E-LNK-004 is the model's code for the uncorrectable link transfer. (The design of this feature named it OTS-E-LNK-003; LNK-003 was already taken by the packet-in-flight rule of  (§8, §10), so the next free number is used.) It is in the same class as ECC-001: reported after the instruction's own checks, no effect on the instruction's own result other than the poison, never a function of a program value.

**Counters and the error log.** The two counter registers are the only state added; they are read-only, count flits, and are cleared by reset. They are read through the CSR space (`R 200`, `H csr`, a remote csr packet, §14). Every flit event is also recorded in the error registers of §16 (kind 7 and 8, `ERR_STATUS` bits 6 and 7, `SBE_COUNT` and `MBE_COUNT`, log word 1 = link << 16 | flit, as in §14) and an uncorrectable one raises the error interrupt; the observables are the `T ecc` line, the `T irq` line, the two counters, the error registers and OTS-E-LNK-004. **Replay** is the runtime's decision after the run (ISCA22 §4.5, HC34 p.60), outside the chip.

**Fault injection and tests.** `F link` lines (§12) mark flits; `test/directed/link_fec.py` pins the rules on every profile (a corrected flit on a header, payload and tail flit; an uncorrectable payload flit with the poisoned superlane read by a consumer; header and tail; a burst over several flits with a corrected flit beside it; the counters per link; two chips; every input error); `unit_tests/test_c2c.sail` (`test_link_fec`) pins the flit-to-superlane map and the counters; the golden vectors `ecc-NNN` of the single-chip programs pin them for an ISS (§12).

**FEC scope.** The model covers injected faults and their architectural effects for data packets. The physical FEC code and latency, faults on control-unit CSR and control packets, and chip or link retries are outside that scope.

## 18. Matrix-unit computation error detection and correction (`slices/mxm/mxm_insts.sail`, `core/ecc.sail`, `c_emulator/tsp_sim.c`)

The sum check is part of the base model: **there is no gate and no profile key**. Without an injected matrix fault, an ABC uses the normal exact arithmetic path.

**Published:** the published TSP sources (HC34 p.60) say that NaN and Inf "may arise due to SDC or SEUs in SRAMs or critical hardware structures (ie. matrix unit)", so the matrix unit is a structure whose computation can be corrupted. **No** ISCA20, ISCA22 or HC34 page describes a check on a matrix product. The redundant per-row checker below is therefore **implementation choice**, with its rationale in `isa-db/provenance.yaml` (`mxm_check.*`).

**The check** [implementation choice]. For installed weights W, activation x and installed rows r < R, compute primary exact row products p[r] = Σ_k W[r][k]·x[k] in row-major order. Independently recompute nominal row products n[r] from the same captured W and x in column-major order. After applying every admitted injected 96-bit toggle to the primary products, compare each final p[r] with n[r]:
- **No changed row:** no matrix event.
- **Exactly one changed row:** report that exact row as corrected, `T ecc <cycle> queue <q> mxm corr plane <p> lane <r>`, no diagnostic. The architectural ABC product is computed from the unchanged captured operands.
- **Two or more changed rows:** OTS-E-ECC-003 at the ABC execute cycle and no ABC result entry. This detects every final multirow error, even when errors cancel in arithmetic aggregates. Count changed row values, not fault entries: multiple flips in one row remain one error, cancellations that restore a row leave no row error, and an out-of-installed-row fault has no effect.
- **Exact values:** integer products retain their signs; f16 uses units of 2^-48, fp8 units of 2^-32, bfp8 units of 2^-34 and bf16 units of 2^-266. A nonfinite operand contributes zero to both checker paths; nominal arithmetic still produces the specified special value. There is no rounding tolerance.
- **Fault representation:** `F mxm` toggles a bit of the 96-bit two’s-complement projection of a primary exact row sum (`flip96`), including for bf16 sums wider than96 bits. Classification uses the final projected value against the full independent nominal value. Faults are confined to the primary checker sums; captured operands, the independent checker and control are trusted in this fault model.
- **Order:** operand ECC events occur first; a corrected matrix event precedes its RAS updates, and an uncorrectable matrix RAS event precedes the outer ECC003 diagnostic. Existing fault consumption, error logs, interrupts and retained partial effects are unchanged.
- **Timing and scope:** the abstract check adds no architectural cycle and runs only when faults are pending; the no-fault fast path is unchanged. This is explicit redundant computation and per-row comparison, not a physical repair implementation. A circuit implementation must provide an independently protected checker and captured operands; its area, energy, memory-port and timing cost is not established by this model. Sharing the faulty datapath without equivalent protection does not meet the stated guarantee.

`F mxmw` weight faults remain outside this version; this check does not claim protection against faults in shared captured weights, activation or the checker itself.

**Re-execution and error rate** (the sources of the feature mention both) are the runtime's decisions after a run that reported OTS-E-ECC-003: the runtime issues the ABC again (the second ABC of an uncorrectable one, with no fault, gives the product: `mxm_check.py`). The events here are recorded in the error registers of §16 and an uncorrectable ABC raises the error interrupt (kind 5 and 6, `ERR_STATUS` bits 4 and 5, `SBE_COUNT` and `MBE_COUNT`, log word 1 = plane << 16 | lane, the lane field 0xFFFF for an uncorrectable ABC).

**Tests.** `test/directed/mxm_check.py` (every profile with 44 MEM slices per hemisphere: i8 and f16, seven single flips on the lanes and bits of the range, two flips in one lane, two lanes, two lanes with the same bit, a lane beyond the installed rows, a second ABC after an uncorrectable one, every input error); `unit_tests/test_vxm_mxm.sail` (`test_mxm_check`); the golden vectors `ecc-NNN` pin them for an ISS (§12).

## Implementing the fetch and shared-resource edges

For one chip, the C environment first advances patrol through the **previous** cycle. It admits link arrivals, applies scheduled host actions and faults, processes arrived control packets and handles departures due before the current tick. A mutation can make this cycle runnable. Within Sail, the local second read precedes IQ service. Barrier retirement and stream commit precede the stream second read. Delayed executions precede the control queue, which precedes ascending data queues and their immediate executions. Unit-state flush and this cycle's eligible patrol close the tick. External inputs include timed packets, the backing stores, the host DMA head and the fault schedule. Trace, IRQ and egress callbacks report outputs. A circuit with independent internal clocks must present these same ordering relations at the architectural interface. For tile k the physical sampling edges are t+k and t+1+k. The Sail vector operation represents this stagger in tile-0 coordinates. It carries one vector and integrity mask per sample. It does not expose k independent hardware probe points throughout the chip. Each data queue needs storage for one pending stream sample with a valid bit and next-edge enable. A pending sample survives an otherwise idle cycle. Reset clears it. Checking space on the first sample does not reserve a completed FIFO slot. Same-edge external injection or a local completion can occupy that slot before the second stream sample. On failed admission the pair is discarded with IQ-003. Source and queue order break ties. IQ service spends its byte budget on padding as well as text and can discard an arriving unit when the ring is full (IQ-002).

A hardware ECC implementation can associate a word's check state with resident/in-flight storage. Sail's logical production indices distinguish successive uses of a physical IQ slot. The host-injection sentinel must be distinct from every protected index, including after 2³² units. The error-record address field deliberately truncates the reported location. That field is unsuitable as the internal lookup key. Physical ECC placement and finite tag recycling require a lifetime argument covering staged and still-resident units of straddling words.

One possible finite implementation keeps a word descriptor until both its staging reference and its last IQ-unit reference have gone. It can then recycle the descriptor. Let U = iq_depth/4, D = fetch_staging_depth and S = superlanes. A conservative per-queue bound on distinct protected words at a clock boundary is U + 2SD + 2S. Each resident unit can name at most one word. Each admitted chip payload contributes at most two vectors of S words. The final term allows one first vector on each of the local and stream capture paths at a MEM issuer. Host-injected units need no protected descriptor. A descriptor shared between stages is counted twice in this bound. Retain the architected low address bits for reporting and keep the simulator's full source identity when servicing absolute-index fault injection or debug observations. Retiring the descriptor on the first dispatch from a word would lose protection for later units. Storage for timed host input belongs to the host interface, whose service and ordering the adapter must preserve.
