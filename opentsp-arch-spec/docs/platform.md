# Platform interface (non-ISA)

A host prepares SRAM and instruction queues, starts execution, then collects results and diagnostics. Sections 1–4 and 7 define the observable load, reset, completion and error behavior. Section 6 gives one register layout for implementing those operations. A platform may document different offsets and widths. Section 9 describes chip-visible host events and refers to the Sail and harness protocol that implements them. Simulator starvation warnings use a separate lint channel.

## 1. Start and done

- **Cycle 0.** The machine is reset (§1.1: every state of `microarchitecture.md` §11 at its reset value, every IQ empty, the cycle counter 0), the SRAM holds the contents the host intends (all zero after a cold reset, the previous run's words after a restart, §1.1), the program and the data are loaded (§2, §3), and then the host writes the **start** bit. The write of the start bit defines cycle 0 of the model: the first cycle in which the queues dequeue from their IQs. Before it nothing executes and nothing is fetched. On a multi-chip system every chip's start is made at the same hardware-aligned cycle (the hardware-aligned counters of the chips stay aligned at start, `microarchitecture.md` §10); the host's job is to start the chips together, the interface does not define a start offset. **Multi-chip start alignment and clock drift are outside the hardware conformance of 0.1.** An implementation must provide a mechanism that makes the hardware-aligned counters of its chips equal at start (the published system characterises each link by reflection, aligns the counters and re-synchronises at run time against the drift of the free-running counters: ISCA22 sections 3.1 to 3.3); the model assumes aligned counters and no drift. A program is written for an aligned start or begins with a Deskew pattern (microarchitecture §10): a program that receives at a fixed cycle after the send (the generated link schedules use a fixed latency of 228 cycles) fails under a start skew, which `H start <cycle>` can script for one chip.
- **Done.** The machine is **quiescent** when `model_quiescent` holds ("Completion" in `assembly.md` §4): nothing remains to happen, and a queue parked at an unreleased Sync, HostWait or DeskewRecv may still hold text. At that point the machine also checks the IQs: text left in an IQ that cannot complete a parcel (the last instruction has its bundle bit, or half of a two-unit instruction) is **OTS-E-IQ-004** (`model_finish`), so a truncated image does not end as a silent "done". The status register shows `quiescent` and, if enabled, an interrupt is raised. A run that never becomes quiescent is ended by the host (**stop**), as `tsp_sim --max-cycles` ends one.
- **Stop.** The stop bit freezes the machine in the current cycle. The SRAM, the cycle counter and the error registers stay readable. A stopped machine, like a finished one, is started again only after a cold reset or a restart (§1.1); a start without one is not defined.

### 1.1 Reset, restart and start

**What the model contains.** `reset` (`postlude/tick.sail`) returns every state of the table in `microarchitecture.md` §11 to its reset value, with every queue's IQ loaded from the initial images the harness supplies. It holds **no SRAM contents**: the SRAM is storage outside the model (`core/sram.sail`: "Storage is external"), which the platform provides, in `tsp_sim` once per process (`c_emulator/tsp_sim.c`). Whether a reset clears the SRAM is therefore a property of the platform, and this document defines two resets.

| | **Cold reset** (`CTRL.reset`) | **Restart** (`CTRL.restart`, optional) | **Start** (`CTRL.start`) |
|---|---|---|---|
| The model state of `microarchitecture.md` §11 (stream registers, pending commits and executions, queue, AGT, Repeat and barrier state, SetVL, liquid-thread split, segments, MXM planes with their installed weights and buffers, SXM maps, C2C windows) | reset values | reset values | unchanged |
| SRAM, every slice and word, and with it every weight, table, constant and cache the host placed in it | cleared to zero by the platform | **kept** | unchanged |
| IQ images (the program) | every IQ empty, then the host loads the program (§3) | every IQ empty, then the host loads the program again: the images of the previous run are not kept | unchanged; the windows close |
| Cycle counter, error FIFO, `ERR_FIRST`, `STATUS` flags | cleared | cleared: the host reads the diagnostics of a run before it restarts | the counter starts at 0 |
| Host configuration registers (`C2C_PEER`, `IRQ_ENABLE`) | kept (wiring and host configuration) | kept | unchanged |
| `SRAM_ADDR`, `IQ_SELECT` (the address and queue selects) | cleared | cleared | unchanged |
| C2C link receive FIFOs and vectors in flight (the platform's, `microarchitecture.md` §12 "Link FIFOs") | empty | empty (a multi-chip system restarts every chip together; a multi-chip restart is not probed) | unchanged |

**A cold reset is the only reset that a 0.1 implementation must provide;** it is the state a program of the golden vectors starts from (a program that relies on non-zero memory loads it, §2). **A restart is optional**: an implementation that offers it conforms to the equivalence below, and one that does not is still conforming. A host that needs the SRAM across runs (a resident model: weights and a cache loaded once, inputs and outputs moved per run) uses a restart where there is one and otherwise reloads through the aperture.

**The equivalence that defines a restart (normative).** A restart followed by loading a program P is the same run as a cold reset followed by preloading, through the aperture (the `S` lines of the harness), exactly the SRAM words that the restart keeps, followed by loading P: the same `T` lines, the same cycles, the same diagnostics, the same SRAM at quiescence. It holds because a reset returns everything a run can observe other than the SRAM to the same values (`microarchitecture.md` §11 lists it), and the model reads and writes the SRAM only through the platform. The golden vectors are cold starts and stay valid; a restart adds no vector. The probe of the review checked the equivalence on the model with a program pair (a word that run 1 wrote is read by run 2, a segment that run 1 set is gone in run 2, the cycle counter restarts, run 2's trace equal to a cold start with the words preloaded).

Restart preserves SRAM **data bytes**, while resetting integrity overlays to the same state as a fresh host preload. It therefore does not preserve a physical stuck-bit fault or establish recovery from one. Persistent injected faults are governed separately by the bounded replay policy. External link FIFOs and host state are reset according to the harness contract; the single-chip equivalence above is not a proof of arbitrary multi-chip restart recovery.

The serving binding checks retained SRAM before an ordinary restart. Following an unsafe step, management closes admission, isolates the old device and invalidates its KV state. A permitted cold recovery reloads the trusted, tests the implicated address and checks a private inference before admitting fresh work. [Serving recovery](production-ras.md)

**Start.** The start bit changes no state: it fixes cycle 0 (above). It is neither a reset nor a restart, so it does not clear or keep anything; the machine must have been reset or restarted, and loaded, before it.

### 1.2 Words that look alike

Three different things are called "replay" in the repository and in the sources. The table distinguishes their meanings.

| What | Name here |
|---|---|
| The published chip's re-running of an inference after an error was reported (HC34, ISCA22 §4, the resiliency paragraphs) | **software replay**: a published recovery concept; the harness implements a bounded one-shot policy (`microarchitecture.md` §16.2), not a general fault-recovery guarantee |
| The ISS binding's `restart_mode("replay")`: a cold reset, then writing back every SRAM word the host recorded | **write-back restart**: by the equivalence of §1.1 it is a restart done with a cold reset and aperture writes; not a platform feature |
| The ISS's recorded and replayed dispatch schedule of one program (`tsp-iss run --record`, `--replay`, the compiled replay) | **schedule playback**: an ISS speed device; it has no architectural meaning |

### 1.3 The ISS's interface extensions and the specification

For each extension of the ISS and its binding, what the specification carries. Only the restart is carried; the rest are tools of a software implementation.

| ISS extension | Carried by the specification? |
|---|---|

| `restart_mode("replay")`: write-back restart | No: a cold reset plus aperture writes (§1.2), both already allowed |

## 2. SRAM aperture

- Host access to the SRAM is addressed by **(slice, word, superlane)**, with the slice numbering of `topology.md` §6, the word number `0.. sram.words_per_slice − 1` and the superlane `0.. superlanes − 1`; one access moves the 16 lane bytes of one tile of one word. A host may offer a wider burst as a sequence of such accesses.
- The aperture is usable only while the machine is not running (before start, after done or stop). An access while it runs is an implementation choice (it may be refused); no program may depend on one.
- **A cold reset clears the SRAM** (the platform does it: the model's `reset` holds no SRAM contents, §1.1); a restart keeps it. A program that relies on non-zero memory loads it or relies on a restart's equivalence.
- The preload of the harness (the `S` lines of `porting-guide.md`: the SRAM contents at cycle 0) is written through the aperture before start. Instruction buffers that later `Ifetch` instructions read are part of that preload.

## 3. IQ load window

The program is **per-queue text**: for each queue q (0..143, and the control channel `ffff`) an initial IQ image of 32-bit units, in the IQ at cycle 0. See §7.1 for RTL conformance, the word formats in `encoding.md`, and object lowering in `assembly.md` §4.

- Each queue has one **IQ load window**: a write-only register (or a small address range) to which the host appends units, in order, as the harness `Q <queue> <u0> <u1>...` line does (several appends to one queue append in order). A control register selects the queue (or the queue is part of the address).
- Padding units (`0xFFFFFFFF`) are dropped as at Enqueue. An image that is longer than `icu.iq_depth` bytes after that is a **load error**: the window refuses the append and sets the load-error status bit (the harness exits with 2). A well-formed object never causes it.
- Initial IQ load windows are writable only before start, including the control channel’s window. During a run, Ifetch/IfetchM fill data queues through the fetch-driven front end. Explicit timed `H inject` is a separate modeled runtime interface (`microarchitecture.md` §14), capable of appending text to data or control IQs through the enqueue path at its delivery rate, subject to IQ overflow. Runtime injection does not reopen the initial-load windows.
- The fetch CSRs (the unpublished items of  §1, "CSR") are the configuration keys `icu.fetch_latency`, `icu.fetch_bytes_per_cycle` and `icu.iq_depth` (§7.8 of that document). They are read-only **identification** registers of an implementation, not a way to program it: they report the values the implementation has, and conformance is relative to the declared values.

## 4. Weight loading

Model weights are carried separately as Safetensors. A physical package binds named word arrays to the ELF object's externs by name and size. For a serving bundle, the host first maps its shared logical weights to physical words using the program's tensor bindings. The ELF may also provide fetched instructions, literals and zero-initialized extents. The host writes physical words to each extern's (slice, address, size) through the SRAM aperture (§2) before the first run that needs them. See [Objects](assembly.md#4-objects) for the formats. After a cold reset load the words again. After an optional SRAM-preserving restart, an unchanged tensor at the same addresses is already present. Reload any overwritten or newly bound region. There is no separate weight-loading path and no host access to the weight buffers of the MXM: the program moves weights from the SRAM into the MXM with its own instructions (`LW`, `IW`, `microarchitecture.md` §6).

## 5. Hardware time

A cycle number of the specification is the cycle of superlane 0 (`topology.md` §3); superlane k runs k cycles later. The cycle counter of the register map (§6) counts **superlane-0 cycles** from the start bit: it is 0 at cycle 0 and increments every cycle while the machine runs. Diagnostics (§7) are stamped with the superlane-0 cycle. An implementation whose pipeline delays the effect of superlane 0 by an implementation constant K (the depth of its front end) still stamps with t, not t + K. The relation (informative): an event the model stamps at t happens at t + k + K on superlane k.

**Host-visible state in hardware (normative).** The host-visible state is the cycle counter, `STATUS`, the error FIFO, `ERR_FIRST`, the CSR space of the chip (§9), the interrupts and the doorbells. The model defines it in superlane-0 time: an event stamped t is in that state at t. A hardware implementation presents it with a **fixed delay** D = (superlanes - 1) + K after the stamp (K is the implementation constant above; an implementation states it): by t + D the last superlane has produced its part of the event, and the host sees the state the model has at t. The stamp of a record stays t, not t + D. Two consequences:
- **Reorder window.** Superlane k of an instruction stamped t reports at t + k + K, so an instruction stamped t + 1 can be detected before the last superlane of the one stamped t. An implementation therefore holds the records of a window of D cycles before it commits the one with the smallest stamp to the FIFO and to `ERR_FIRST`; the FIFO and `ERR_FIRST` order the run-time records by stamp and then by the reporting order of microarchitecture §8, not by detection time (the end-of-run records below are the exception). An interrupt for a record stamped t is delivered at t + D.
- **The matrix sum check** is stated in the same time: an ABC's verdict (a corrected lane, or ECC-003) is stamped at the ABC's execute cycle at superlane 0, although the check needs the activation of every superlane and completes up to superlanes - 1 cycles later, and then needs the time S that the check takes to compute its verdict after the last activation has arrived (the sum-check term: S >= 0 is a second implementation constant, stated with K; an implementation may include it in K). The verdict, the interrupt and the log record that follow it are presented with the delay D + S after the stamp, and the reorder window above is D + S (S is 0 when the implementation includes it in K, and D + S is never shorter than D).
- **End-of-run records (an exception to the stamp ordering).** IQ-004 is the one record that no event of a cycle raises: it is an end-of-run record that reports text left in a queue after the machine has quiesced. The chip's quiescence detection appends it to the diagnostic log at quiescence (the model: `model_finish`, microarchitecture §12), after every run-time record, queue by queue in ascending order with the control channel last, and stamps it with the cycle of the queue's last activity (a unit entering its IQ or a dispatch; 0 for an initial image that never moved). It is visible from quiescence on, not from its stamp, and it stands outside the ordering by stamp stated above: a log that holds an IQ-004 record is not monotone in stamp, and `ERR_FIRST` (§7) is the first record in log order. This states what the model already does; the model is unchanged.
- **Host inputs (the mapping under D).** The `H` and `R` lines name model cycles. A host **write** (a CSR write, a doorbell ring `H db`, `H dma`, an injection) takes effect at the model cycle c that the line names, and a testbench applies it at the real cycle c: model cycle c and real cycle c are the same cycle at the chip's host port, and the delay D is paid only on the way out. A host **read** at real cycle r returns the model state of r - D, so the read that a vector places at model cycle c is compared with an RTL read issued at real cycle c + D, and the `X` lines (read at quiescence) with a read D + S cycles after quiescence (the extra S lets a sum-check verdict that was stamped just before quiescence arrive). The effects of a sum-check verdict stamped t (`ERR_STATUS` bits 4 and 5, `SBE_COUNT`, `MBE_COUNT`, the integrity `LOG`, its interrupt) are in the host-visible state from t + D + S, so a read at a real cycle r < t + D + S does not see them: a testbench that wants one rule reads every register at c + D + S. No vector of the shipped files reads a CSR within S of a sum-check verdict (on `ref` the seven `csr` events are in `host-011`, `host-035` and `ecc-165`, none with an ABC; on `mini` `ecc-143` takes the place of `ecc-165`), so reads at c + D are exact on them. Because a read shows the state of r - D, a host that writes a register at c and reads it back before c + D sees the old value: the read port presents host-written registers through the same delay. A delivery rule that fires in the cycle of a write (an `IRQ_MASK` write that enables a pending cause bit, and the clears of `ERR_STATUS` and `IRQ_CAUSE` by W1C) fires at the model cycle c of that write, and the interrupt is presented to the host at c + D. A doorbell enters the front end directly: `H db` applied at real cycle c releases a HostWait at model cycle c + 1 (microarchitecture §14), which is real cycle c + 1 + K at superlane 0 (the depth K of the front end is part of D, the superlane term is not), not c + 1 + D.

`--on-irq stop` of `tsp_sim` and `tsp-iss` is a model construct with no hardware counterpart: it ends a run at the end of the cycle of the first error interrupt, whereas a chip does not stop (microarchitecture §16). Vectors with `H` lines are conformance tests only for an implementation driven by a cycle-accurate host model that applies each action at the cycle named. For asynchronous host traffic an implementation guarantees ordering and the semantics of `IRQ_CAUSE` and the doorbells (microarchitecture §14): the CSR accesses of the host take effect in the order issued, a doorbell ring releases at most one HostWait, and a cause bit stays set until the host clears it; no cycle-exact effect is promised.

### 5.1 Fault points

The `F` lines of the harness (microarchitecture §12) name faults in the coordinates of the model. Each kind maps to an architectural boundary as follows; a test mode of an implementation that reproduces the vectors must inject at that boundary, and an implementation without one is outside the fault vectors.

| `F` kind | Coordinate in the model | Architectural boundary |
|---|---|---|
| `sram` | (cycle, slice, word, superlane, bit): bit 0..127 data, 128..136 check bits, 137 spare, of the stored superlane word | a cell of the stored word of one slice, before any consumer reads it |
| `srf` | (cycle, row, stream, gap, superlane, bit): the value of the nearest upstream write on the diagonal | the value where its producer wrote it; every register of the diagonal downstream of the producer then holds the flipped value, so a physical fault in one downstream register corrupts only the readers beyond it |
| `iq` | (cycle, queue, text word, bit): the word counted over the queue's text in production order | a word of the instruction queue storage, identified by production order and not by physical slot |
| `link` | (cycle, link, flit, `corr` or `uncorr`): the outcome of the link FEC for one flit of a vector the chip sends | the FEC outcome at the receiving end; the wire bits are not modelled (the code is not published) |
| `mxm` | (cycle, plane, lane, bit 0..95): a bit of the exact two's-complement sum of one lane of an ABC | the model's exact sum has no counterpart in an implementation (a datapath holds a rounded lane result, not a 96-bit sum), so an `F mxm` vector has no boundary to inject at: the `F mxm` vectors are for the model and the ISS only (§7.1 lists them as excluded). An RTL tests its sum check with flips of its own lane results and compares the outcome, a corrected lane or ECC-003, with the rule of microarchitecture §18, without a golden vector |

**Fault envelope.** A single flipped bit of a protected SRAM word, stream register or instruction is corrected before use. A detected uncorrectable error poisons the affected results and is reported. See the ECC rules in [microarchitecture](microarchitecture.md). The matrix checker recomputes each exact installed row product from captured operands. One changed row is reported as corrected. Two or more changed rows produce OTS-E-ECC-003 and the ABC produces no result. This check is part of every profile. Its guarantee assumes reliable captured operands and an independent checker, as specified in §18. Physical fault coverage and residual rates require hardware qualification.

## 7. Diagnostics

The model and ISS report the ordered diagnostic sequence defined by [microarchitecture §8](microarchitecture.md). For hardware conformance, use the class column there (§7.1). A compiler can check parcel placement before loading an image. By contrast a Gather address comes from data, fetched text may fail decode, and integrity errors depend on the stored or transported bits. On a Gather or Scatter bounds error, valid tiles may have taken effect. On a link integrity failure the received vector can still be written with affected superlanes poisoned. A host must inspect the reported code before using affected outputs.

IQ overflow drops arriving units (IQ-002). Incomplete text at completion can raise IQ-004. A fetch that cannot stage its payload raises IQ-003. The optional starvation warning OTS-W-IQ-001 belongs to the simulator lint channel. The platform error FIFO below mirrors the chip's CSR diagnostic log (§9.1 and microarchitecture §16.3); the chip's CSR integrity log (§9 and microarchitecture §16) is the other, separate interface.

The reporting is by two structures:

1. **Error FIFO.** Records of (superlane-0 cycle, queue, code), in the order of `microarchitecture.md` §8's reporting order within a cycle, **`ras.diag_depth`** entries deep (a profile key, 1..64, optional, 16 when the profile leaves it out). A full FIFO drops further records and sets the **overflow** flag (`STATUS.fifo_overflow`); the dropped records are not counted. `ERR_FIFO` pops the oldest record; the host reads until `ERR_COUNT` is 0. **The FIFO mirrors the chip's diagnostic log** (`microarchitecture.md` §16.3): the chip's CSR space holds the same records (`DIAG_COUNT`, `DIAG[i]`, `DIAG_POP`, the overflow flag) in the same order with the depth `ras.diag_depth`, so a silicon chip reports through the CSR space alone every record that the log filter of §16.3 admits (a superset of the codes of class `data`). A `schedule` code that the filter does not admit is not reported by the chip: the toolchain checks it before the image is loaded (§7.1).
2. **Sticky first-error register.** `ERR_FIRST` holds the first record of the diagnostic log since reset, in log order (the same three fields and a valid bit): the first record that the filter of §16.3 admitted. It is not necessarily the record with the smallest stamp, because the log is in reporting order and an end-of-run IQ-004 record follows records with later stamps (§5). It is written once and not overwritten, so the first error survives a FIFO overflow, and it is cleared only by reset. It has no source for a code that the log does not admit.

### 7.1 RTL conformance

This subsection is the one normative statement of what an RTL implementation reproduces. Sections 12 and 13 of [microarchitecture](microarchitecture.md) (the exact output of the model and the ISS, and the notes for hardware) refer to it.

- **Classes.** Every code of the table of [microarchitecture §8](microarchitecture.md) has one class. A `schedule` code is raised by a rule that reads only the text, the configuration and the timing state: it says that the object breaks a placement or scheduling rule, and a toolchain can check it before the image is loaded. A `data` code is raised by a rule that reads data values or fetched text. A `fault` code reports an integrity event (ECC-001, ECC-002, ECC-003, LNK-004): it needs an injected or physical fault and reads no program value.
- **Well-formed.** An object is **well-formed** when a fault-free run of it raises no `schedule` code and no `data` code but the end-of-run record IQ-004. For a program of several chips (a manifest) the run is every run the profile allows: every directed link with any latency in [`c2c.link_latency_min`, `c2c.link_latency_max`], also varying per transfer, under the declared host script; a `schedule` code in one such run makes the manifest ill-formed (a Receive can find its vector in time on one link and not on another). A `schedule` code reads only the text, the configuration and the timing state, so a run in which every instruction took effect raises every `schedule` code that the object has: one such run decides the object for every data. A `data` code removes the effect of an instruction (SXM-001 leaves a Permute without its map, IQ-002 loses units, a fetched DEC-003 drops an instruction), and the instruction it removed can be the one that would have raised a `schedule` code on other data, so a run that raises a `data` code decides nothing about its object, whether or not a `schedule` code follows it. IQ-004 removes no effect of a run-time instruction and is not counted. The decision on one run is three-valued: **well-formed** (the run raises no `schedule` code and no `data` code but IQ-004), **ill-formed** (the run raises a `schedule` code and no `data` code before it, so that code is genuine) and **data-dependent** (the run raises a `data` code other than IQ-004 and no `schedule` code before it: a `schedule` code that follows can be a cascade of the data code, and a `schedule` code that the data code hid was never raised, so this run cannot decide; the object is judged with other data, for example the weight and program-text packages of its real run, or a run on data that raise no `data` code, a witness). `tsp-iss verify`, the verifier of the toolchain, runs the object and reports one of the three (exit 0, 1 and 3). A fourth outcome is **not judged**: text that ends the run parked behind a wait nothing released (a HostWait without its doorbell, a DeskewRecv whose vector never arrives, a Sync nothing releases) was never run, and the verifier fails it (exit 1) unless told to allow it; a manifest whose schedule depends on the link latencies (a DeskewRecv released at different epochs) is judged at the combinations of the two latency bounds over the links it sends on, and when none of them shows a `schedule` code it is reported as data-dependent (exit 3), because the latencies between the bounds and the jitter of single transfers were not judged. An OPR-001 of a Gather or Scatter tile address or of an `sxselect` select is a `data` code (the data of the run decides it), so a run that raises one is data-dependent too, and the object is judged by a run on other data. A loader or runtime of a workflow that relies on well-formed objects **verifies the object before the image is loaded**: an object that is not well-formed carries no obligation (below), and an RTL may run, stall or reject it.
- **What an RTL reproduces.** For a well-formed object, run with the declared profile and no fault: (a) the records that the log filter of microarchitecture §16.3 admits (a superset of class `data`), in the reporting order of microarchitecture §8, as the FIFO of this section holds them (as long as it did not overflow); (b) every SRAM word at quiescence; (c) the egress vectors, the vectors of `PciSend` (the `Y` lines), in order, each with its data and with its cycle mapped by the delay D (§5); (d) the `HostNotify` interrupts (MSI-X vectors 1 to 15, the `irq` events), in order, with their cycles mapped by D; (e) the value of every CSR that the vector reads, at the cycle it names (the `csr` events, with the input mapping of §5) and at quiescence (the `X` lines). The obligation holds on any data of a well-formed object, those that raise `data` codes included. On a run that shows an object well-formed the FIFO holds at most the IQ-004 records. These five comparisons are the whole obligation of a silicon RTL, and the table below states, for every field of a golden vector, whether they compare it or it is excluded. The exact trace (`T srf`, `T sram`, the cycle of every dispatch) is the comparison of an implementation that exposes the model's trace interface (the ISS, a simulation of the RTL with a trace port, microarchitecture §12), a stronger test that the vectors support but the RTL rule does not demand.
- **Cascades.** A `data` code can start a cascade: a data-dependent SXM-001 leaves a map unloaded, a later Permute then raises TIM-001 and a Write is suppressed. So, after a `data` record, the RTL reproduces the effects (the suppression, the partial effects) of every later code, `schedule` codes included, in the compared outputs (a) to (e); it need not report a `schedule` code that the log filter does not admit. The cascade rule is the obligation on the data of a well-formed object that raise a `data` code; the object is shown well-formed by a witness run on other data, so a `schedule` code on the data that raise the `data` code is never genuine.
- **Objects that are not well-formed.** Conformance is by the model and the ISS only. An RTL may run, stall or reject such an object and has no obligation on the result or on the diagnostics.
- **The scope of each golden vector.** The frozen vector files carry no field for it, so it is recorded beside them: `opentsp-arch-spec/conformance/rtl/<profile>.json` (generated by `tools/gen_rtl_obligations.py`, which gives each vector's program, data and host script to `tsp-iss verify`; `just iss-vectors` fails when the file is stale) names for every vector `pass`, `none` or `undecided`. `pass`: the run is well-formed, and the comparisons (a) to (e) bind the RTL on this vector. `none`: no obligation: the run is ill-formed, or it injects faults (an RTL with the test mode of §5.1 compares it, any other is outside it), or it is an `F mxm` vector (model and ISS only). `undecided`: the run is data-dependent (its data raise a `data` code), or the text uses a link, which `verify` judges only as the manifest of a program; it binds an RTL only if a witness run shows the object well-formed, and until then a mismatch is a question for the verification lead and not a failure. The cascade vectors (a `data` code before a `schedule` code) are of the `undecided` kind; an entry may carry a `witness` (the program on other data, which `verify` finds well-formed, so the object is well-formed and the vector binds the RTL as a cascade test), and the two SXM-001 cascade vectors of each profile carry one. [bring-up](bring-up.md) §2 says how to use the three values.
- **`PciSend` is part of every 0.1 implementation.** The word "optional" in the instruction catalogue and in the table of §9 means that the form and the pacing of the chip-to-host instruction are an opentsp choice that the published sources do not give, not that an implementation may leave it out: its egress is compared by (c) and a vector with a `Y` line is `pass` when it is well-formed. (The catalogue word is in a frozen file and changes with the next erratum.)
- **Fault class.** An RTL detects the events the `fault` codes name and reports each as an error report that carries the same facts as the model's: whether it was corrected, the kind, the location and the cycle (the error registers of microarchitecture §16; the spare-bit report of §15.5). The platform FIFO need not carry a `fault` code. Runs with injected faults are compared with an RTL through a test-mode mapping of the `F` lines (§5.1), or are excluded from its conformance. The `F mxm` vectors are excluded in every case: they are for the model and the ISS only, because the 96-bit exact sum of the model has no bit on the rounded lane result of an RTL (§5.1).
- **Profile.** The cycle numbers of every record are those of the profile the implementation declares (microarchitecture §12, "Conformance is per profile"). `config/ref.json` is a scheduling reference, not an implementability claim: its `timing.overrides` rows (Exp, Log, RSqrt and TanH at 5 and 2, Permute at 20 and 0) and the class rows it keeps (the multiply, ABC and Shift rows and the map-ready time) are placeholders or causal bounds that give programs a stable timing; hardware declares a profile of its own. `config/test/ref_hw.json` is a test profile with slower rows for Exp, Log, RSqrt, Permute and Reduce (d_func 16, 16, 18, 24 and 12; an opentsp choice, not a published value). It is not an implementability claim either: TanH, the multiply rows, ABC, Shift and the map-ready time stay on the placeholders of `ref` or on their causal bounds.
- **Host-visible state** is stated in superlane-0 time, with the delay and reorder window of §5, which also states the mapping of host inputs and the end-of-run exception for IQ-004.

| Vector field | Content | Obligation |
|---|---|---|
| `expect.diagnostics` | every diagnostic, in order (`T diag`) | compared (a) for the records that the log filter admits; the other codes are not compared (the toolchain checks the `schedule` codes) |
| `expect.words` | the dumped SRAM words | compared (b) |
| `expect.trace_sha256` | digest of the stream-register and SRAM write trace | excluded: it needs the trace interface of an implementation (above) |
| `expect.events` | the same events of the small vectors | excluded, as the digest |

## 8. The control channel and the host

The control channel (queue `ffff`, CU) initially receives its text through the host’s pre-start IQ load window (§3). It has no Ifetch instruction. Explicit timed `H inject` can append control text during a run through the modeled runtime injection path; this is separate from writing the initial-load window. Without injection, the whole control program must fit its initial IQ image. The control channel does not read SRAM data; it carries barrier/configuration instructions and NOP timing prefixes. Any predecoding must preserve the model’s instruction-effect cycles.

A **host-fed sequencer** that writes text while the machine runs is the host interface of `microarchitecture.md` §14: `H inject <cycle> <queue> <units…>` pushes text into the IQ of any queue, the control channel included, from the cycle given, with the IQ's overflow rule (OTS-E-IQ-002). A run that uses it is a run of the model: the input names the cycle and the units.

## 9. The host interface of the chip

Every published chip handles its own PCIe Gen4 host interface in its C2C slice, so every chip of a system has one (the pipeline of the SHIP paper §2.1 and §7.1.1 takes its input at the first chip and gives its output at the last): "a lightweight DMA engine to emplace a model onto the TSP memory", an entry point for bootstrapping the execution and interrupts to the host (ISCA20 §II-6; the link is PCIe Gen4 x16 at 900 MHz, ISCA22 §5.2). The model carries it as follows (the rules are in `microarchitecture.md` §14; the interface to an implementation is the `H`, `R`, `X`, `Y` lines of §12):

| Function | In the model | Source or choice |
|---|---|---|
| Model emplacement (DMA) | the program load at cycle 0 (the `S` and `Q` lines) is the emplacement; `H dma` pushes further vectors into the chip's ingress FIFO at `host.cycles_per_vector` cycles per vector, `host.ingress_depth` deep (a vector that finds it full waits in the DMA engine; nothing is dropped); `PciReceive` + a MEM Write commit a vector to SRAM | published: the DMA engine and the PCIe Gen4 x16 link (ISCA20 §II-6; ISCA22 §5.2); choice: the pacing (10 cycles per 320-byte vector, rounded up from about 9.1 cycles = 320 bytes over the about 35 bytes per cycle that a Gen4 x16 link at 900 MHz carries, an estimate), the incoming streams S24..S31, the FIFO and its depth |
| Bootstrap entry point | `H start <cycle>`: the queues start dispatching at that cycle | published: "an entry point for bootstrapping"; choice: the form |
| Results to the host | `PciSend` appends a vector to the egress list of the host of the chip that executes it (`Y` lines of its section) | an opentsp choice, not published: the instruction form and its pacing; every 0.1 implementation has the instruction (7.1 (c)) (the published sources give the host interface in the C2C module and the host's role of loading the model and collecting results, ISCA20 §II-6, and the output at the last chip of the pipeline, SHIP paper §7.1.1; they give no instruction form or pacing for the chip-to-host direction) |
| Doorbells | CSR 0x300 + i; `HostWait i` waits for one, `H db` rings it | choice |
| Interrupts | `HostNotify n` raises MSI-X vector n of the chip's own host; `IRQ_CAUSE`, `IRQ_MASK`, `IRQ_COUNT`; an interrupt is delivered whenever a cause bit is set and the vector is enabled (a masked vector is delivered when the host enables it) | published: interrupts passed to the host (ISCA20 §II-6); choice: the MSI-X form, numbering and registers |
| Register access | the CSR space of each chip (4,096 registers of 64 bits): `H csr`, `R`; the control unit's access to the chip next to it: `P csr <cycle> <link> r|w <addr>`, one csr packet over the link | published: access through a base address register, the header's packet type (HC34 p.45); choice: the map, the one-hop operation, the reply, how packets share a link |
| Direct text path | `H inject` | OpenTSP host protocol for timed delivery of instruction units to a selected IQ |

The register map of §6 and the status register of §1 are the platform interface, which the FPGA platform realises; its start, stop, load window, aperture and cycle counter are chip functions (§9.1). It is a different interface from the CSR space of the model: the CSR space is the chip's own, reached by the host through the PCIe base address register. Every chip has its own host interface, so no host action is routed over the links; the control unit's remote CSR access (`P csr <cycle> <link> r|w <addr>`) is one csr packet to the chip at the far end of a link, leaving when the link is free (`microarchitecture.md` §10, packet types, and §14); every link transfer has a type (data, csr, sync, ctrl) and only data and sync reach a Receive. The core link protocol models neither chip-to-chip fault-report packets  nor hot-spare substitution. The GPT-2 serving backend collects per-chip evidence through its management interface and fences the complete node on an unsafe step.

### 9.1 Chip CSR registers and the platform registers

The chip's CSR space (`microarchitecture.md` §14, §16) and the register map of §6 are two layers on purpose. The CSR space is what a host reads and writes through the chip's PCIe base address register. The other functions of §6 (start, stop, reset, quiescence, the IQ load window, the SRAM aperture and the cycle counter) are **chip functions** too: only the chip can start its queues, reach its own instruction queues and SRAM, and stamp its diagnostic and integrity logs with a cycle. The specification fixes the set of these functions and what each means (§1 to §3 and §5); the registers, addresses and ports that carry them are **implementation-defined**, in the chip's own register space or through its host interface. The same holds for the rest of the set of §6: the identification registers (`ID`, `SPEC_VERSION`, `PROFILE_DIGEST`: a chip reports the specification version and the digest of the profile it declares, so that bring-up can refuse a profile that is not the one of the vectors; they are not `CHIP_ID`, which is only the chip number), `ERR_FIRST` (a read-only register, or pair, that holds the three fields and a valid bit of the first record that entered the diagnostic log, latched at that moment, cleared only by reset, host-visible with the delay of §5), `STATUS.error` (the diagnostic log is not empty or `ERR_FIRST` is valid), `STATUS.load_error` (a load-window error, §3) and the `quiescent` and `error` interrupt enables of `IRQ_ENABLE` (the chip's own interrupt on quiescence and on a first error; a chip with only the CSR interrupts of §14 and §16 reports quiescence by `STATUS.quiescent` alone and then has no `quiescent` interrupt). The set and the meaning are normative, the register, its address and its port are implementation-defined, as for the functions above. A board wrapper such as the FPGA platform of this document is one realisation of the same functions and not a layer that a silicon chip lacks. The registers of §6 relate to the CSR space as follows.

| Platform register (§6) | Chip CSR | Relation |
|---|---|---|
| `ID`, `SPEC_VERSION`, `PROFILE_DIGEST` | `CHIP_ID` (0x000) | Chip functions with implementation-defined registers (above): the identification of the interface names the interface, the specification version and the profile; the chip's `CHIP_ID` is the chip number of a multi-chip system |
| `CTRL` (`reset`, `restart`, `start`, `stop`), `STATUS.running`, `STATUS.quiescent`, `CYCLE` | none in §14 or §16 | Chip functions with implementation-defined registers: the chip starts, stops and reports quiescence, and it has a cycle counter of its own (it stamps every `DIAG` and `LOG` entry), counting superlane-0 cycles from the start bit (§5) |
| `IQ_SELECT`, `IQ_WINDOW`, `SRAM_ADDR`, `SRAM_DATA` | none in §14 or §16 | Chip functions with implementation-defined registers: only the chip reaches its instruction queues and its SRAM, so the load window and the aperture are its ports (§2, §3); their reset values are in §1.1 |
| `C2C_PEER[link]` | none | Wiring and host configuration of the chip's board (§1.1: kept across resets) |
| `ICU_FETCH_LATENCY`, `ICU_FETCH_BYTES`, `ICU_IQ_DEPTH` | `FETCH_RT[q]` (0x100 + q) | The chip reports the fetch latency per queue; the other two identification values are profile keys that the chip reports from the declared profile |
| `IRQ_ENABLE` | `IRQ_MASK` (0x031), `ERR_MASK` (0x016) | The chip enables per MSI-X vector and per `ERR_STATUS` bit; the platform's `IRQ_ENABLE` gates its own `quiescent` and `error` interrupts, and `quiescent` has no counterpart in the CSR space (the chip's quiescence detection reports it) |
| `STATUS.error` | `ERR_STATUS` (0x010) | `error` is a chip function with an implementation-defined register (the diagnostic log is not empty or `ERR_FIRST` is valid); `ERR_STATUS` holds the chip's per-kind sticky bits of the integrity log, bit 9 being an integrity-log entry dropped, which is a different log from the diagnostic log (`fifo_overflow` is `DIAG_STATUS` bit 0, in the rows below) |
| `ERR_FIRST` | `FIRST_ERR0/1` (0x0F0, 0x0F1) | The chip's copy is the first log entry (an integrity event) since `ERR_STATUS` was last cleared; the platform register holds the first record of the diagnostic log since reset, in log order (§7). It is latched when the first record enters the log and has no CSR counterpart in §14 or §16: it is a chip function with an implementation-defined register (above), and `DIAG[0]` is not it, because `DIAG_POP` removes the oldest entry |
| `ERR_FIFO`, `ERR_COUNT`, `STATUS.fifo_overflow` | `DIAG[i]` (0x410 + i), `DIAG_POP` (0x401), `DIAG_COUNT` (0x400), `DIAG_STATUS` bit 0 (0x402) | The chip's diagnostic log (`microarchitecture.md` §16.3) holds the records that the filter of §16.3 admits (a superset of class `data`; code, queue, cycle in one word) in the reporting order of §8, at most `ras.diag_depth`, and the platform FIFO mirrors it: same records, same order, same depth, the overflow flag the same. A silicon chip exposes the log through the CSR space; the FPGA wrapper's FIFO is a copy of it |
| none | `LOG_COUNT` (0x014), `LOG[i]` (0x020 + 2i), `LOG_POP` (0x015), `SBE_COUNT`, `MBE_COUNT` | The chip's integrity log holds integrity events (kinds 1 to 9) in two words each, at most `ras.log_depth` (`fault` codes and spare-bit reports); it has no platform counterpart |
| none | `IRQ_CAUSE` (0x030), `IRQ_COUNT` (0x032), `DOORBELL[i]` (0x300 + i), `LINK_CORR[l]`, `LINK_UNCORR[l]` | Chip registers with no platform counterpart; the host reaches them through the base address register |

A cold reset clears the platform registers as §1.1 states; the reset values of the chip registers are in `microarchitecture.md` §11. The two layers never name one register twice with different meanings: where the names look alike (`IRQ_ENABLE` and `IRQ_MASK`, `ERR_FIRST` and `FIRST_ERR0/1`), the table above says which holds what.

### 9.2 PowerConfig, DeepSleep and Config

`PowerConfig` and `DeepSleep`, and the power effect of `Config` on a non-MEM queue, are architectural no-ops: they must not change any result, stream value, diagnostic or cycle count, and an implementation may use them as hints (for example to gate clocks) as long as it does. The specification has no wake-up latency key: an implementation that needs cycles to wake a unit hides them, because the compiler's schedule leaves no slack for them.

## RAS responsibilities at the host boundary

An error IRQ is a notification to the host. A detected event updates sticky status, first-error information, a bounded log and the appropriate saturating count. A newly set enabled status bit raises the vector-0 cause. The interrupt mask gates delivery. Enabling a pending vector can deliver it. Acknowledge the cause and error status through their own W1C registers. Check overflow before interpreting consecutive entries as a complete history. Capture the record before reset. The recorded address may have fewer bits than the logical position used internally. HostNotify uses vectors 1–15. Neither an IRQ nor acknowledgement rolls back an instruction that already issued.

The chip detects errors and applies the instruction-local actions in [the microarchitecture chapter](microarchitecture.md). The harness can stop or replay a single run. For TinyStories and GPT-2 serving, the platform checks completion before publishing, fences all affected participants, and retains an incident record across cold recovery. The [serving RAS contract](production-ras.md) specifies the management signals, service policy and evidence still required on a physical target.
