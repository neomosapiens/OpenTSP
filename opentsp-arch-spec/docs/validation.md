# TSP reference architecture: validation

Use the source comparisons to assess fidelity, the directed and differential tests to check software behavior, and the bounded proofs for their named properties. Agreement with the executable specification measures conformance to OpenTSP. Each attribution to published hardware needs a separate source. The standard local entry points are `just model-test` and `just model-prove`. The commands below show the configurations exercised and report their verdicts.

**f32 screening in detail.**
- **Sweep:** every f32 bit pattern, 4 × 2³² evaluations, computed in double precision. An input is *hard* when its double value lies within 2⁻⁴⁰ (relative) of an f32 rounding boundary: a midpoint between consecutive f32 values, including gradual underflow and the overflow threshold 2¹²⁸ − 2¹⁰³. The inference that every unflagged finite input is farther than 2⁻⁴¹ from a boundary depends on a global libm error bound which this test does not prove.
- **Audit of the filter:**
  - The C screen reports `DBL_MANT_DIG` and `LDBL_MANT_DIG`. A long-double comparison runs only when the latter is wider. On platforms where both are 53 bits, agreement supplies no independent precision evidence. 
  - A mandatory separate audit evaluates the actual C screening functions against mpmath at 200 and 400 bits, using edge cases and seeded uniform/stratified samples. It rejects unstable references and relative errors above 2⁻⁴⁸. This is a sampled check, not a global bound; `filter_audit.json` records its scope and results.
  - A random sample of unflagged inputs was checked against the 2⁻⁴¹ bound.
- **Recheck:**
  - Hard inputs re-evaluated with mpmath (200 bits, doubled until decided): 6 124 for TanH, 12 408 for Exp, 44 982 for RSqrt, 45 929 for Log.
  - Also rechecked: every special class (NaN payloads, ±Inf, ±0, subnormals, powers of two and their neighbours, small integers, the rounding and saturation thresholds), plus a seeded random sample of about 4 × 10⁵ inputs per function.

The closest relative distance to a rounding boundary, per function:

| Function | Input | Distance |
|---|---|---|
| TanH | 0x3AC37DE2 | 2⁻⁵⁰·³ |
| Exp | 0xC16912CD | 2⁻⁵²·⁶ |
| RSqrt | 0x013A18E3 | 2⁻⁵¹·⁷ |
| Log | 0x65D890D3 | 2⁻⁵⁷·⁸ |

Every case is within 2⁻⁽²⁴⁺³⁴⁾. The evaluator's refinement resolves any distance down to 2⁻¹⁸⁹⁴ at p = 2048, a margin of more than 1 800 bits.

### Which profile keys keep conformance

A **conformance statement is per profile.** An implementation **declares its profile**, a configuration file valid under `config/schema.json`, and conforms when it matches the vectors that the frozen model generates from that file (`conformance/model/<profile>.json` for the shipped profiles, generated by `tools/gen_model_vectors.py` for any other; every vector file records the digest of its configuration, `config_sha256`). Latencies, gaps and constants are profile values: no particular numbers are part of the frozen specification, and the `ref` values are one profile's, not a requirement. `test/ref_slow` (longer MEM, VXM and SXM latencies) is the test that this is true of the tests too: directed tests runs unchanged on it. The keys below are the ones a profile may change. "Any legal value" means that the model accepts every value the schema allows and that each suite accepts it within the domain stated under "Domain of the suites" below; it does not mean that every suite runs on every value (the directed suite needs 44 MEM slices per hemisphere, the oracle's programs are drawn for 20 superlanes and cut to the profile), with the vectors regenerated; it does not mean one implementation's vectors transfer to another profile.

| Key | Legal values | Keeps conformance | What changes with it |
|---|---|---|---|
| `geometry.superlanes` | 1..32 | any legal value | the lanes `16 × superlanes`; the schema relations on `d_func`; the vectors |
| `sram.addr_bits` | 13..16 | any legal value | the width of every address field (Read, Write, IfetchM, SetSegment, the Gather and Scatter map entry), the words a slice can have |
| `sram.words_per_slice` | a power of two, 256..65536, at most 2^`sram.addr_bits` | any legal value | the addresses that are OTS-E-OPR-001; with `sram.bank_bit` = log₂(`words_per_slice`) − 1 (schema relation), the banks |
| `sram.bank_bit` | log₂(`words_per_slice`) − 1 | only that value | which address pairs clash (MEM-001) |
| `geometry.mem_slices_per_hemisphere` | a multiple of 4, 4..44 | any legal value | which MEM slices exist; the queues of the others are OTS-E-QUE-002; the layout relations count quads |

| `mxm.planes_per_hemisphere` | 1 or 2 | any legal value | which MXM queues exist (the queues of an absent plane are OTS-E-QUE-002), the plane of an east queue, whether an f16 pair exists |

A value outside the schema is refused before the model runs (configuration rejection tests).

**Domain of the suites.** "Any legal value" is the domain of the model, of the `$[test]` unit tests (Sail unit tests, every profile), of the profile-parameter check profile tests (`profile_params.py`), of the superlane-count check superlane tests (`superlanes.py`: SetVL 1..32, Config, the last superlane, the error record) and of the invalid-configuration check configuration rejection tests; they run on `ref`, `mini` and the test profiles, among them `test/sl8` (8 superlanes) and `test/sl32` (32 superlanes, 512 lanes). The programs of the directed suite `test/directed/directed.py` (directed tests) are written for 20 superlanes and read the superlane count, words per slice, bank bit and MXM rows from the profile: its domain is a profile with 44 MEM slices per hemisphere and any superlane count; a scenario written for a larger geometry prints SKIP with its reason and is counted in the last line, and a profile with fewer MEM slices is skipped as a whole. `model_test.sh` runs it on `ref`, `test/ref_slow`, `test/ref_hw` and `mini`; `test/sl8` and `test/sl32` have 44 MEM slices, so the domain admits them, but the gate does not run the suite there (superlane tests covers them). The oracle (Python, `diff_oracle.py`) builds programs of 320 lanes and fits them to the profile (cut to `vlanes` bytes, or zero above lane 320 on a profile with more lanes; the Shift amounts reach `vlanes − 1`); it runs on `ref`, `test/ref_small`, `test/ref_slow`, `test/ref_hw`, `test/link_tight`, `mini`, `test/mid_min`, `test/sl8` and `test/sl32`. The golden vectors fit their programs to the profile (golden vectors: the files of `ref` and `mini`; the variant profiles, `test/sl8` and `test/sl32` among them, at test time). The ISS runs the vectors of `test/sl8` and `test/sl32` (`just iss-vectors-variants`) and the Python programs of `mini`, `test/mid_min`, `test/sl8` and `test/sl32` (`just iss-diff-variants`).

## 3. Mutation testing

Mutation tests deliberately alter a single implementation rule and require a discriminating check to fail. They can reveal missing test coverage and common-mode assumptions; they do not measure a probability of correctness. Keep each mutation's exact input, expected outcome and proof/test domain explicit.

The ordinary proof mutation ratchet is described in §6. Its registered expected survivors remain visible. A timeout, setup failure or missing result is not a semantic detection.

## 4. Rules that bound what validation claims

These are rules of the specification, not open items.
- **Source facts and decisions are separate.** A source fact has a source basis (`paper`, `figure`, `slides` or another recorded source) in `isa-db/provenance.yaml`, and provenance checks checks that each one carries a citation. Every other value is labelled `decision`: encodings, every per-instruction latency (the MXM's 20 cycles included), the per-unit queue split, the SXM unit split and SetVL on every queue. A `decision` claims nothing about the published design, so validation of a decision means only that the model, catalogue, documents and vectors agree on it (the checks above). Where the sources disagree, the `conflicts:` record says which source the model follows.
- **Encoding round trip:** what is proved, and how.
  - The 32-bit space is checked exhaustively (exhaustive encoding check).
  - The 64-bit space is checked per entry by catalogue checks and reference assembler checks: every fixed bit, every excluded value, corner and random fills, and pairwise distinctness of the match patterns. Distinctness plus the per-field checks implies that the 64-bit encoding round-trips: two entries never match the same word, and within an entry each field is placed and extracted independently.
  - The SMT backend is used for the field-level properties (SMT obligations), not for the whole scattered `encdec` mapping, which it cannot finish.
  - **This is the complete statement of the argument.** `encoding.md` says only that the 64-bit patterns are "checked pairwise" and that a decoder is compared "on random words"; the statement here is the one to cite. The per-field checks use 40 random fills per entry (plus the corners), the distinctness of the match patterns is checked in Python (catalogue checks), not in Sail, and no property quantifies over all 2⁶⁴ words. The exact structural check that does not sample is `test/formal/encoding_exact.py` (`just encoding-exact`, run by the formal gate): for every entry of `encoding.json` and every pair of entries of one width it checks that the match pattern has the entry's width, that every field is a contiguous range inside the word (a split field has a second contiguous range), that fields do not overlap and that the wildcard bits are exactly the field bits, and that two patterns that overlap on their fixed bits are separated by field legality; with `--smt` it also runs one Z3 query for the disjointness of two 64-bit patterns, a record that per-clause queries finish. It checks structure, not the meaning of a field: catalogue checks and reference assembler checks still check the meaning by sampling.
- **Vectors per profile and coverage.** The golden vectors are the ISS's gate (porting-guide §3). They exist for **both** shipped profiles, every catalogue entry is in at least one vector of each, and each vector is tagged by the instructions and units it uses (golden vectors). An entry that appears only with a diagnostic (listed by `--check`) has no vector for its results: an ISS step for such an entry is gated by oracle-style differential runs against the emulator as well.
- **The second implementation of record is the ISS.** Its gate is the golden vectors (golden vectors) and the differential method of the Python oracle against the emulator (`porting-guide.md` §3). The Python oracle is a second, independent implementation of the whole ISA; it is a test asset, not a normative source: where it and the model disagree, the model and `microarchitecture.md` decide, and the oracle is fixed.
- **Decoder and timing checks.**
  - *The text decoder.* The width comes from the tag of the first unit only, so there is no prefix ambiguity; tags 6 and 7 consume one unit and are OTS-E-DEC-003 in the model, the ISS and the assembler; every 64-bit entry has a fixed zero bit in its second unit, so the padding unit `0xFFFFFFFF` can never be a second unit; reserved bits are checked; IW and IWS share opcode 1 and differ in bit 13 and bits 19..18 (distinct patterns); a NOP with the bundle bit set, or inside a pending parcel, is kept as an item and becomes OTS-E-QUE-001 in the model and the ISS alike. The random-word comparison of `test/isa_db/json_decoder.py` checks the decoder against the model.
  - *The stagger abstraction.* The model treats the stagger (`topology.md` §3: superlane k of an operand reaches a unit k cycles after superlane 0) as an abstraction that needs no per-superlane state. That is exact for every instruction that does not read a lane of another superlane: Reduce is per 16-lane superlane group, Distribute and Rotate are per superlane, Transpose is 16 x 16 inside a superlane, SxSelect is lane-wise, and Gather and Scatter are per tile. Only Shift, Permute and ABC cross superlanes, and `model/postlude/timing_check.sail` requires `d_func` >= the superlane count for exactly those three (map readiness of Permute is separate, `microarchitecture.md` §7).

## 5. Simulator lints (non-normative)

A **lint** is a note a simulator may give its user about a program that is legal but probably not what was meant. The specification distinguishes lints from the architectural diagnostics (`OTS-E-…`):

- A lint is **not architectural**. It changes no state and no timing, it is not an exception, it is not counted in the `E` line, and it is **not part of the golden vectors** (`conformance/model/`). The hardware rule behind a lint stays as it is: the lint only reports.
- **A conforming implementation need not report any lint** (`porting-guide.md` §2.3 and §3). A harness that wants none implements `lint_callback` as a no-op. A differential test between two implementations (Python, `diff_oracle.py --impl`) compares lint lines only when asked (`--impl-lint`).
- A lint code is `OTS-W-<area>-<nnn>`: `W` for warning, the area as in the diagnostics (`IQ`, …), three digits.
- Reported through its own model callback, `lint_callback(cycle, queue, code)` (`core/callbacks.sail`, the same arguments as `diag_callback`; queue 65535 is the control channel). `tsp_sim` prints `T lint <cycle> queue <q> <code>` lines **only with `--lint`**, interleaved in the order the model raises them with the `T srf`, `T sram` and `T diag` lines of `--trace` (the two flags are independent). Without `--lint` the output of `tsp_sim` is the same as before the lints existed.

| Code | Name in `lints.sail` | Detected when | Rule behind it |
|---|---|---|---|
| OTS-W-IQ-001 | `LINT_IQ_UNDERFLOW` | IQ underflow: a delivery of fetched text completes the head parcel after the cycle it was due, and the queue was free in the previous cycle (not parked, not busy, no Repeat, both AGT paths idle). Reported at the parcel's dispatch, once per such parcel (`microarchitecture.md` §3 "Underflow"). | Logical time was lost (ISCA20 §III-A3: "It is imperative that IQs never go empty"); the parcel still dispatches. |
| OTS-W-RAS-001 | `LINT_RAS_EVICT` | A live spare-bit error report was evicted: a report written on a register that has none takes the slot of the oldest of the 256 reports the model keeps, and that report was still in its row (register d + c <= 44). Reported at the cycle of the instruction that wrote the new report (`microarchitecture.md` §15.5, "Report retention"). | Unrelated traffic can hide a pending report: a reader that would have found it sees nothing. The capacity (256) is architecture; the lint says the program is beyond it. |

**Adding a lint is one line plus one call** (`tools/check_lints.py` keeps the pieces in step):

1. In `model/core/lints.sail` add one line `let LINT_<NAME>: string = "OTS-W-<AREA>-<nnn>"` (a trailing comment says what it detects).
2. At the place the model detects the condition, call `lint(q, c, LINT_<NAME>)` (`q` is a queue 0..143, or 144 for the control channel; `c` the cycle). The call must have no effect on the machine state.
3. Add its row to the table above, and its entry to the `LINT` table of `test/oracle/machine.py` (one line); the oracle raises it with `self.lint(q, c, LINT[...])`.
4. Add a check to the directed test of its area (for the IQ lints, `test/directed/frontend.py`, which reads the `T lint` lines of `tsp_sim --trace --lint`).

No change to `encoding.json`, the catalogue, the generated documents or the golden vectors is needed or allowed: a lint is not part of the interface.

## 6. Assurance for fetch, reporting and queue service

Run `just model-prove` from the repository root with the specification toolchain active. **Bounds of every obligation.** The properties are bounded in three ways, and a counterexample outside a bound is not found. (1) Integer width: Sail's SMT backend represents an integer as a bitvector of at most 128 bits (`sail -smt` without `--smt-int-size`, default 128), and a bitvector of unknown length as 64 bits (`--smt-bits-size`); a counterexample that needs an integer wider than 128 bits is hidden by that pass (a test property `unsigned(x) * 2^100 == 0` is UNSAT by default and SAT with `--smt-int-size 256`). `tools/model_prove.sh` therefore repeats every profile with `--smt-int-size 256` (`PROVE_WIDE=1`, the default) and requires the same verdicts, so a counterexample that needs an integer of 129 to 256 bits is found, and one that needs more than 256 bits is still hidden. The domains stated in the rows below (for example 16-bit start times and intervals of 1 to 256 cycles) are further, property-specific bounds. (2) Time: every solver call is bounded in time. The obligation driver (`tools/check_smt_obligations.py`) asks Z3 for 60 s per query and stops the call after 65 s; the induction file is run with `-T:60`. The toolchain's `z3` wrapper (`$OPENTSP_TOOLCHAIN/zwrap/z3`) rewrites every `-t:` timeout to 60000 ms and every `-T:` limit to 300 s, whatever Sail or a driver asks, so that a loaded machine does not fail Sail's own type check at random. A timeout, an `unknown`, a solver error or a missing result fails the gate (the driver fails closed), so a slower machine cannot turn a failure into a pass, but a property that needs more time than the limit is reported as unproved, not as false. The CI workflow installs the pinned Z3 4.15.4 release archive and checks its recorded digest; the local toolchain uses the same version with the timeout wrapper described above. The gate checks the solver version: `test/formal/z3_version.txt` names 4.15.4, and `tools/check_smt_obligations.py --solver-info` fails the run for another version unless `PROVE_ALLOW_Z3=1` accepts it, with a printed warning. (3) Depth: the obligations are single-step or induction over a stated abstraction, never an unbounded run of the whole machine. Each `p_` query asks Z3 for a counterexample to the property. UNSAT discharges it. Each `c_` query intentionally has a counterexample and must produce SAT. A separate SMT-LIB file, the **accounting argument (abstract)**, checks eight identities over free integer and sequence variables (associativity of concatenation, conservation of counts, FIFO order and grant counts). They are true of the mathematical objects and say nothing by themselves about Sail state: the bridge to the model is the separate statement that the concrete transitions select the prefixes the argument assumes (see "How the abstraction relates to the machine"). It starts at the empty epoch and checks the eight named steps. Its counts describe an abstract front end. The actual queue and environment have additional state, and the eight identities are not independent assurance of the model; the delivery-path refinement (host text FIFO, padding, capture, `iq_deliver` service loop) remains a separate work item. The two `props/frontend.sail` accounting properties (`p_iq_pop_accounting`, `p_iq_push_accounting`) are length restatements of `p_iq_pop_conservation` and `p_iq_append`, not that refinement. [Sail statements](../model/props/props.sail) · [Symbolic ports](../test/formal/fetch_ports.sail) · [Induction statements](../test/formal/frontend_induction.smt2)

**Textual-copy boundary.** The proof-only fetch-port transformation uses a regex-rewritten production-source copy in tools/fetch_port_proof.py and test/formal/fetch_ports.sail. An exact substitution count in each direction detects source drift, but do not remove this boundary. Replacing the copy requires rechecking the relevant source-linked Lean/SMT results.

**Abstract-accounting limit.** The `frontend_induction.smt2` accounting argument proves eight identities over free integer and sequence variables, not properties of Sail state. The bridge to the model (that concrete transitions select the prefixes the argument assumes) is a separate work item; until then the file is not independent assurance of the model.

### Proof-gate mutation ratchet

The registered table has 38 cases, 36 required kills and two expected survivors (`m_l0` and `m_c2`). The directed two-loop bank-conflict test is required to kill `mut_bank`. The normal gate must complete every case and match the table; infrastructure failures and timeouts fail the gate. A survivor is not a successful detection. Stronger source-linked proofs can change a disposition only after an actual semantic rejection has been demonstrated.

Whole-machine formal correctness remains unproved. Local proofs for IQ bounds, resource queries, dispatch frames, producer/commit policy, reporting, numerical components and event boundaries retain explicit hypotheses. They do not discharge complete caller histories, concrete C callback semantics, global resource admission, event-skip refinement or full numerical correctness. See [assurance limitations](../../docs/assurance.md).

The default model-prove recipe checks mini and ref. `just prove-profiles` selects every schema-valid profile, including the shipped and test profiles; profile and SMT-width settings are part of each result's domain. **How the abstraction relates to the machine.** For conservation, count each offered payload position once, including padding. First-beat retention owns those positions until completion or discard. A successful completion moves them and the second beat into the staging sequence. Service removes a prefix from its head, subtracts padding, and appends as many of the remaining units as the ring can accept. Overflow accounts for the rest. Pop consumes a prefix of the ring. Reset closes the observation epoch and discards its outstanding positions before loading a new image. At each boundary, cumulative input equals retained + staged + resident + retired + explicitly discarded. The sequence check proves preservation under a prefix transfer and prefix removal. Whether every concrete scanner path selects exactly such a prefix is a separate obligation. Read the sequence identity together with the accounting invariant. A count alone would allow a duplicated unit to replace a missing one. The symbolic ring operations, native queue tests, and program-level checks provide evidence for different links in that argument. A mechanized induction over the entire concrete Sail tick and C-backed state is still open.

**Finite resource interpretation.** IQ entries and completed chip-fetch slots have configured bounds. Timed host injection can accumulate externally supplied text, and the model can retain historical entries in its sparse text-error overlay until reset. Those data structures cannot be dimensioned as physical on-chip SRAM from their simulator representation. RTL must bound host admission or provide the specified buffering at the interface and establish when it may reclaim integrity metadata for a partially delivered or still-resident word. No RTL refinement, multi-chip containment or product reliability target is established by these suites.

### Independent encoding source

The ISS, assemblers and Python oracle share generated encoding data, so agreement can retain a common-mode encoding error. A separate encoding source remains a design task and documented limit. Literal published examples, structural checks and numerics comparisons provide their stated independent checks; they do not make the whole encoding independent.
